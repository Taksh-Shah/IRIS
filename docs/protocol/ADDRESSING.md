# Addressing

## Address Design Philosophy
IRIS uses cryptographic addresses. No central registry, no DNS, no phone numbers, no usernames that require a server to resolve.

Every node's address is derived mathematically from its Ed25519 public key. This means:
- Any node can generate its own address offline
- No one can take your address away (no central registrar)
- Addresses are globally unique (with cryptographic probability)
- Addresses are self-certifying (address proves key ownership)

The address model is inspired by Tor onion addresses (.onion), Bitcoin addresses, and the Kademlia DHT address space.

## Node Address Format

### Cryptographic Derivation
```
Ed25519 private key    (32 bytes, generated securely at first run)
      ↓
Ed25519 public key     (32 bytes, derived from private key)
      ↓
node_id = BLAKE3(public_key)   (32 bytes = 256 bits)
```

BLAKE3 chosen for: speed (3x SHA-256 on modern hardware), security (no known attacks), Rust implementation quality (`blake3` crate).

Why hash the public key instead of using it directly as the address?
- Ed25519 public keys are already 32 bytes — same size as BLAKE3 output
- Hashing provides one additional layer: if Ed25519 is broken, the hash maintains address integrity temporarily
- Consistent with established practice (Bitcoin, Tor)
- Allows address format to remain stable if key type changes (still 32 bytes)

### Wire Representation
```
node_id: bytes(32)    // 32 raw bytes in CBOR
```

### Human-Readable Representation
For display in UI, sharing, and verbal verification:
```
human_address = "IRIS-" + base32(node_id)[0..8].to_uppercase()

Examples:
  "IRIS-A3BC7E2F"
  "IRIS-X9Q2MNKP"
  "IRIS-7BFTRW4Z"
```

8 base32 characters = 40 bits of address space = ~1 trillion unique addresses.
Probability of collision in a network of 1 million nodes: ~5×10⁻⁴ (negligible).

For complete sharing (when QR code or digital copy):
```
full_address = base32(node_id).to_uppercase()   // 52 characters, full 32 bytes
```

### Address Display in Application
```
Short:  IRIS-A3BC7E2F   (for display in UI, easy to read/say)
Full:   A3BC7E2FXYZ...  (52 chars, for QR code, digital sharing)
```

## Group Addressing

Groups have their own 16-byte addresses:
```
group_id = BLAKE3("iris-group-v1" || creator_node_id || group_name)[0..16]
```

16 bytes (128 bits) for group addresses reduces collision probability while keeping wire size smaller than node addresses. Groups are less numerous than individual nodes.

### Group Address Generation
- Generated by: group creator at group creation time
- Requires: creator's node_id + chosen group_name
- Deterministic: same inputs always produce same group_id
- Offline: no server required

### Group Membership
Group membership is not encoded in the group_id. Membership is:
- Stored locally on each member's device
- Exchanged with contacts (group directory gossip)
- Authenticated by: group creator's signature on the member list

## Broadcast Addressing

Special reserved addresses for broadcast and multicast:

```rust
pub const BROADCAST_ALL: NodeId = [0xFF; 32];
// Meaning: send to all nodes currently in range

pub const EMERGENCY_BROADCAST: NodeId = [0x00; 31].append(0x01);
// Meaning: emergency authority broadcast, authority certificate required

pub const LOCAL_AREA: NodeId = [0x00; 31].append(0x02);
// Meaning: area-restricted broadcast (geographic or network-defined area)

pub const GATEWAY_ANY: NodeId = [0x00; 31].append(0x10);
// Meaning: route to any available gateway
```

### Broadcast Handling
- `BROADCAST_ALL`: relay forwards to all neighbors (no deduplication suppression of relay — but message_id dedup still prevents infinite loops)
- `EMERGENCY_BROADCAST`: authority certificate verified before relay; relays to all neighbors
- `LOCAL_AREA`: relay checks if it is within the declared area (geographic bounding box in payload) before forwarding

## Address Resolution

There is no global address resolution service (requiring one would mean requiring Internet).

Address resolution is local and progressive:

### Resolution Sequence
```
Application requests: resolve "IRIS-A3BC7E2F"
         │
         ▼
Step 1: Check local contacts DB
  (node_id → display name + public key, cached from previous contacts)
  → Found: use cached address. Done.
         │
         ▼
Step 2: Check neighbor table (direct contact)
  (Is this node currently a neighbor?)
  → Found: send directly. Done.
         │
         ▼
Step 3: Check routing table
  (Do I have a route to this address?)
  → Found: send via routing. Done.
         │
         ▼
Step 4: Gossip query
  Broadcast to neighbors: "Who knows node IRIS-A3BC7E2F?"
  → Neighbor responds with: address + last-known contact info
  → Update routing table, proceed.
         │
         ▼
Step 5: Unresolvable
  → Store message with unresolved recipient
  → Re-attempt resolution on each new neighbor contact
  → Message delivered when resolution succeeds (store-carry-forward)
```

### Address Book (Local Contacts)
```sql
CREATE TABLE contacts (
    node_id          BLOB PRIMARY KEY,     -- 32-byte node_id
    display_name     TEXT NOT NULL,        -- User-assigned display name
    public_key       BLOB NOT NULL,        -- Ed25519 public key (for E2EE)
    short_address    TEXT NOT NULL,        -- "IRIS-A3BC7E2F" (indexed for search)
    last_seen        INTEGER,              -- Unix timestamp
    added_at         INTEGER NOT NULL,
    verified_at      INTEGER,              -- When out-of-band verification was done
    trust_level      INTEGER DEFAULT 0,   -- 0=unknown, 1=seen, 2=verified OOB
    notes            TEXT
);
```

## Privacy-Preserving Advertisement

A BLE advertisement that includes the node_id directly allows any scanner to track a device's location over time by correlating its presence across multiple scans. This is unacceptable.

### Rotating Advertisement Identifier
BLE advertisements use a rotating pseudo-random identifier instead of node_id:

```
adv_id(t) = HMAC-SHA256(node_private_key, floor(t / 900))[0..6]
```

Properties:
- Changes every 15 minutes (`floor(t/900)` where t is Unix timestamp)
- 6 bytes (48 bits) = sufficient entropy for the timeframe
- Deterministic: a node's contacts can verify `adv_id` if they know the node's key
- Unlinkable to external observers: correlating adv_id across 15-min windows requires knowledge of private key

### adv_id Resolution
Known contacts can resolve `adv_id → node_id`:
```
For each known contact c:
  candidate = HMAC-SHA256(c.public_key_hash, floor(now / 900))[0..6]
  if candidate == received_adv_id:
    → this advertisement is from contact c
    → initiate GATT connection, exchange CapabilityBundle to confirm
```

For unknown contacts: GATT connection initiated, CapabilityBundle read, `node_id` extracted from CapabilityBundle (which is signed, so node_id is authenticated).

### Wi-Fi Aware Discovery Privacy
Wi-Fi Aware uses the same `adv_id` scheme in the service-specific info field.

### LoRa Discovery Privacy
LoRa HELLO broadcasts include `node_id` directly. Rationale:
- LoRa range is much larger (km) — passive BLE tracking (nearby attacker) is not the threat model
- LoRa networks are typically in rural/remote areas where tracking risk is lower
- LoRa HELLO broadcast is infrequent (every 60 seconds)
- Future: apply adv_id scheme to LoRa if urban LoRa deployments become common

## Address Verification (Out-of-Band)

When two people meet in person and want to add each other as contacts, they need to verify they have the correct public keys (prevent MITM during first contact).

### Verification Code
```
verification_code = base32(BLAKE3(
    local_node_id || contact_node_id
)[0..5]).to_uppercase()

Example: "A3BC7"
```

Both parties compute the verification code independently using each other's node_id. They compare the 5-character code verbally or by reading from screen.

Security: 5 base32 characters = 40 bits = ~1 trillion possible codes.
An attacker performing MITM at the moment of first contact would need to guess the 5-character code in real time, with only one attempt before the user notices mismatch.

### QR Code Contact Exchange
More convenient: display full QR code containing:
```json
{
  "iris_contact": {
    "version": 1,
    "node_id": "base32-encoded-node-id",
    "display_name": "User's chosen display name",
    "public_key": "base32-encoded-ed25519-pubkey",
    "signed_by": "self",
    "timestamp": 1723276800
  }
}
```

QR code signed by private key → scanner verifies signature → authenticates the QR code was generated by the key owner.

## Ephemeral Addresses

For anonymous participation in public channels or one-time communications:
- Generate ephemeral Ed25519 key pair in memory (never persisted)
- Derive ephemeral node_id from ephemeral public key
- Send messages signed by ephemeral key
- Messages cannot be linked to permanent identity unless user explicitly signs with permanent key
- Ephemeral identity is discarded after session

Use case: reporting sensitive information without revealing identity. Reporting a neighbor's emergency without exposing own identity.

Limitation: sender of ephemeral message cannot receive replies (no persistent address for recipient to reply to) unless they establish a short-lived rendezvous.

## Address Namespaces Summary

| Namespace | Size | Example | Purpose |
|-----------|------|---------|---------|
| Node address | 32 bytes | IRIS-A3BC7E2F | Individual node identity |
| Group address | 16 bytes | (hex only) | Group messaging |
| Broadcast ALL | 32 bytes | 0xFF...FF | Flood to all neighbors |
| Emergency broadcast | 32 bytes | 0x00...01 | Authority emergency alert |
| Local area | 32 bytes | 0x00...02 | Area-restricted broadcast |
| Gateway any | 32 bytes | 0x00...10 | Route to any gateway |
