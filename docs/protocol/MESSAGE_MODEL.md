# Message Model

## What Is a Message
A message is the fundamental unit of communication in IRIS. Messages are addressed, prioritized, signed, optionally encrypted, and routed independently. A message is self-contained: it carries everything needed to route, authenticate, and deliver it. No external session or state is required to process a message.

## Message Identity
Every message has a globally unique `message_id`:
- **Format**: UUIDv7 (RFC 9562 — timestamp-ordered UUID)
- **Generated by**: originating node at creation time
- **Immutable**: never changes through the relay chain
- **Uses**: deduplication, ACK correlation, delivery tracking, storage indexing

### Why UUIDv7 (not UUIDv4)
UUIDv7 encodes creation timestamp in the high bits. This enables:
- Chronological ordering in SQLite without a separate timestamp index
- Efficient TTL expiry queries (expire WHERE message_id < cutoff_uuid)
- Debugging: message_id reveals when the message was created

## Message Lifecycle

```
CREATED
  (originating node, timestamp assigned, message_id assigned)
         │
         ▼
PENDING_SEND
  (in outbound queue, waiting for transport)
         │
         ▼
IN_TRANSIT
  (forwarded by at least one relay, copy may exist on multiple nodes)
         │
         ├─────────────────────────────────────────────────────────►──┐
         ▼                                                            │
   DELIVERED                                                    EXPIRED
   (recipient's node received the message, delivered to app)    (TTL elapsed,
         │                                                       message dropped
         ▼                                                       at all nodes)
  ACKNOWLEDGED
  (sender received end-to-end ACK from recipient)
         OR
   DELIVERY_FAILED
   (routing impossible, all paths exhausted)
```

### Lifecycle State Machine (SQLite `status` column)
```sql
-- Valid status values
'PENDING_SEND'      -- Created locally, not yet sent
'IN_TRANSIT'        -- Forwarded to at least one relay (outbound)
'RELAYED'           -- This node is relaying (not originator)
'DELIVERED'         -- Received and delivered to application
'ACKNOWLEDGED'      -- Delivery confirmed by end-to-end ACK
'EXPIRED'           -- TTL elapsed without delivery
'DELIVERY_FAILED'   -- Permanent delivery failure
```

## Message Types and Specifications

### P0 — SOS

```
Purpose:       Emergency SOS distress signal. Person in danger or disaster.
Max wire size: 255 bytes (LoRa-compatible — HARD LIMIT)
TTL:           72 hours (must survive until any rescue contact)
Routing:       Epidemic — every node relays immediately to all neighbors
Delivery:      Multi-path — use ALL available transports simultaneously
ACK:           Required — aggressive retry until ACK received
Encryption:    To known recipient: E2EE. To emergency channel: signed, not encrypted.
Relay policy:  Every node relays regardless of battery state (EMERGENCY_OVERRIDE)
Storage:       NEVER evicted for storage pressure. Retained until TTL expires.
Recipient:     Specific node OR EMERGENCY_BROADCAST (dispatched to all)

P0 payload schema (CBOR, abbreviated):
  {
    type: "SOS",
    text: string,       // Max 90 chars: "HELP. 5 injured. Earthquake. Need rescue."
    gps:  [f32, f32],  // [latitude, longitude], 16 bytes IEEE 754
    alt:  f32?,         // Altitude meters (optional, 4 bytes)
    acc:  f32?,         // GPS accuracy meters (optional)
  }

Receiver UI behavior on P0 receipt:
  - Immediate high-priority notification (bypass do-not-disturb)
  - Display sender location on map
  - Provide options: acknowledge, share with emergency services, relay
  - Log receipt timestamp for response time tracking
```

### P1 — Medical Emergency

```
Purpose:       Medical emergency with clinical context (injury type, condition, count).
Max wire size: 512 bytes
TTL:           24 hours
Routing:       PRoPHET multi-path, use 2 best routes simultaneously
ACK:           Required
Encryption:    E2EE to specific recipient (medical coordinator, hospital)
Storage:       Never evicted for storage pressure.

P1 payload schema:
  {
    type: "MEDICAL",
    patient_count: uint,
    condition: string,         // "Critical", "Serious", "Walking wounded"
    injury_type: [string],     // ["Trauma", "Burns", "Crush injury"]
    location_text: string?,    // Human-readable: "Bhuj bus stand, near water tank"
    gps: [f32, f32]?,
    resources_needed: [string], // ["Ambulance", "Surgeon", "Blood: O+"]
    sender_role: string?,      // "NDRF Medic", "Doctor", "Bystander"
  }
```

### P2 — Location Sharing

```
Purpose:       Share GPS position. Used for: check-in, tracking, search & rescue.
Max wire size: 256 bytes (location data is compact)
TTL:           12 hours (location data stales quickly — 12h-old GPS is low value)
Routing:       Standard PRoPHET routing
ACK:           Optional (location may be broadcast or best-effort)
Encryption:    E2EE for private location, unencrypted for broadcast location
Storage:       Evictable when storage full (P5 and below evicted first, but P2 is lower priority than P0-P1)

P2 payload schema:
  {
    type: "LOCATION",
    gps: [f32, f32],           // Required: [lat, lon]
    alt: f32?,                 // Altitude (meters)
    accuracy: f32?,            // GPS accuracy radius (meters)
    speed: f32?,               // Speed (m/s)
    heading: f32?,             // Heading (degrees, 0=north)
    location_name: string?,    // Optional human label: "Bhuj Railway Station"
    status: string?,           // "Safe", "Need assistance", "Moving to shelter"
    timestamp: uint,           // GPS fix time (may differ from message time)
  }
```

### P3 — Emergency Text

```
Purpose:       Text communication during declared emergency conditions.
Max wire size: 1 KB
TTL:           12 hours
Routing:       PRoPHET, Internet gateway preferred when available
ACK:           Recommended for CONFIRMED_DELIVERY; optional for BEST_EFFORT
Encryption:    E2EE for private messages, group key for group messages
Storage:       Always stored (P3 is emergency priority).

P3 payload schema:
  {
    type: "EMERGENCY_TEXT",
    text: string,              // Max ~800 bytes of UTF-8 text
    reply_to: bytes(16)?,      // Optional: reference to message_id being replied to
    thread_id: bytes(16)?,     // Optional: conversation thread
    attachments: [AttachRef]?, // References to separate P5 attachments (by message_id)
  }
```

### P4 — Normal Text

```
Purpose:       Standard message. Sent when no emergency condition is active.
Max wire size: 64 KB (fragmented for BLE, LoRa restricted, Wi-Fi/Internet full size)
TTL:           8 hours
Routing:       Standard (PRoPHET, direct when neighbor)
ACK:           Optional, user-configurable
Encryption:    E2EE for private, group key for group
Storage:       Default (stored, evictable by P7-P5 first)

P4 payload schema:
  {
    type: "TEXT",
    text: string,
    reply_to: bytes(16)?,
    thread_id: bytes(16)?,
    mentions: [bytes(16)]?,    // List of mentioned node_ids
    attachments: [AttachRef]?,
  }
```

### P5 — Image

```
Purpose:       Photo sharing. Field damage assessment photos, rescue situation photos.
Max wire size: 2 MB (compressed JPEG or WebP, target <500KB for fast transfer)
TTL:           4 hours
Routing:       Direct or Internet gateway. NOT relayed over LoRa (size incompatible).
               NOT forwarded over BLE unless high-bandwidth BLE (Wi-Fi fallback available).
ACK:           No (best-effort delivery)
Encryption:    E2EE
Storage:       Optional (stored if space available; first to be evicted)

P5 payload:
  Compressed image binary (JPEG preferred, WebP accepted)
  Metadata in envelope routing_hints: { width, height, caption }
```

### P6 — Voice Message

```
Purpose:       Voice/audio message where text is insufficient or impractical.
Max wire size: 5 MB (compressed Opus audio, ~3 minutes at 128kbps)
TTL:           2 hours
Routing:       Wi-Fi Direct or Internet only. Not forwarded over BLE or LoRa.
ACK:           No
Encryption:    E2EE
Storage:       No (not stored for relay; too large)
```

### P7 — Video / Bulk Transfer

```
Purpose:       Video messages, large document transfers, bulk data sync.
Max wire size: 50 MB
TTL:           1 hour
Routing:       Internet gateway only. Not forwarded in mesh.
ACK:           No
Encryption:    E2EE
Storage:       No (never stored for relay)
Note:          P7 transfers paused immediately on battery < 30% or DEGRADED network state.
```

## Message Storage Schema

All P0-P4 messages persisted to SQLite immediately on creation or receipt:

```sql
CREATE TABLE messages (
    message_id        TEXT PRIMARY KEY,          -- UUIDv7 (hex string)
    sender_id         BLOB NOT NULL,             -- 32-byte node_id
    recipient_id      BLOB NOT NULL,             -- 32-byte address (node, group, or broadcast)
    priority          INTEGER NOT NULL CHECK (priority BETWEEN 0 AND 7),
    status            TEXT NOT NULL DEFAULT 'PENDING_SEND',
    payload_encrypted BLOB,                      -- Encrypted payload bytes (NULL for relay)
    payload_hash      BLOB NOT NULL,             -- BLAKE3 hash of encrypted payload
    payload_size      INTEGER NOT NULL,
    signature         BLOB NOT NULL,             -- Ed25519 signature (64 bytes)
    delivery_policy   INTEGER NOT NULL DEFAULT 0,
    created_at        INTEGER NOT NULL,          -- Unix timestamp seconds
    expires_at        INTEGER NOT NULL,          -- Unix timestamp seconds (TTL deadline)
    ack_received_at   INTEGER,                   -- NULL until ACK received
    hop_count         INTEGER NOT NULL DEFAULT 0,
    max_hops          INTEGER NOT NULL DEFAULT 20,
    relay_count       INTEGER NOT NULL DEFAULT 0,
    last_relay_node   BLOB,                      -- NodeId of last relay (for routing)
    routing_notes     TEXT                       -- JSON: routing hints, delivery attempts
);

-- Indexes for efficient queue management
CREATE INDEX idx_priority_expires ON messages(priority ASC, expires_at ASC);
CREATE INDEX idx_status_priority ON messages(status, priority);
CREATE INDEX idx_sender ON messages(sender_id);
CREATE INDEX idx_recipient ON messages(recipient_id);
CREATE INDEX idx_created_at ON messages(created_at);

-- TTL cleanup query (run every 60 seconds)
-- DELETE FROM messages WHERE expires_at < strftime('%s','now') AND priority > 1;
-- Note: P0 (priority=0) and P1 (priority=1) handled separately with logging
```

## Message Persistence Policy

| Priority | Persist on Create | Persist on Relay | Evict on Storage Full | Evict on TTL |
|---------|----------------|----------------|----------------------|-------------|
| P0 | Yes (sync write) | Yes | NEVER | Yes (after TTL) |
| P1 | Yes (sync write) | Yes | NEVER | Yes |
| P2 | Yes | Yes | Only if storage critical | Yes |
| P3 | Yes | Yes | After P7, P6, P5 | Yes |
| P4 | Yes | Yes | After P7, P6, P5, and if needed | Yes |
| P5 | If space | No | First to be evicted | Yes |
| P6 | No | No | Not stored | N/A |
| P7 | No | No | Not stored | N/A |

## Message Deduplication

A node must never process (deliver or relay) the same message twice.

### Two-Layer Dedup Cache
**Layer 1: Bloom Filter**
- Parameters: 100,000 entries, 1% false positive rate
- Memory: ~120KB
- Speed: O(1) lookup, extremely fast
- False positives: ~1% of new messages incorrectly flagged as seen
  - Impact: ~1% of messages silently dropped (acceptable for dedup correctness vs. 0% relay for safety)
- Reset: every 24 hours (prevents false positive accumulation)

**Layer 2: Exact LRU Cache**
- Size: last 10,000 message IDs (exact)
- Used for: resolving Bloom false positives
- On Bloom hit: check exact cache. If not in exact cache → Bloom false positive → process message
- Memory: ~160KB (10,000 × 16 bytes)

### Dedup on Relay vs Delivery
- Relay: if message_id seen before → DROP silently (never relay a duplicate)
- Delivery: if message_id seen before → DROP silently (never deliver a duplicate to app)
- Storage: before storing → check dedup (never store a message already stored)

## Message Assembly (Multi-Part Messages)

Messages larger than transport MTU are fragmented (see FRAGMENTATION.md). From the message model perspective:
- Each message has an optional `payload_ref` field in its envelope
- When `payload_ref` is set, payload is transmitted separately as fragments
- Message is only delivered to application after all fragments are received and reassembled
- Fragment timeout: 30 seconds (drop incomplete message after timeout)
- ACK (for CONFIRMED_DELIVERY): sent only after full reassembly

## Message Groups and Threading

### Group Messages
- `recipient_id` = group_id (16-byte group address)
- Payload encrypted with group key
- Each group member's node decrypts with group key
- Group key must be pre-distributed (at group creation)

### Threading
- `thread_id`: optional 16-byte identifier for conversation threading
- `reply_to`: optional `message_id` of the message being replied to
- Threading is informational only — does not affect routing or delivery
- Application layer displays threaded view when thread_id present
