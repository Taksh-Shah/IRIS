# ADR-0004: Use SQLite for Message Store

**Status:** Approved  
**Date:** 2026-02-01  
**Deciders:** Core protocol team  

---

## Context

IRIS requires persistent storage for the DTN bundle store — the "store" in store-carry-forward. When a node receives a bundle it cannot immediately deliver, it stores the bundle until the destination (or a better relay toward the destination) comes into contact range. This store must:

1. **Survive process restarts:** If IRIS is killed by Android's process manager and restarted, in-flight bundles must not be lost.
2. **Support concurrent access:** The relay engine writes bundles while the UI reads them; the contact manager updates TTLs while the routing engine reads delivery probabilities.
3. **Support complex queries:** "Get all bundles with destination X that have not expired, ordered by creation time" is a typical relay query.
4. **Fit within mobile storage constraints:** A node may store up to 1,000 bundles (configurable); each bundle up to 64 KB. Total: up to 64 MB.
5. **Have minimal footprint:** Android apps are sensitive to APK size and runtime memory; the storage engine must not be heavyweight.
6. **Have production-quality Rust binding:** Must be usable from `iris-core` Rust code without unsafe boundary issues.

---

## Options Considered

### Option A: SQLite

**Description:** The most widely deployed relational database engine. Single-file, embedded, no server. Available on all Android and iOS devices as a system library.

**Pros:**
- **Ubiquitous:** SQLite is present on every Android and iOS device as a system library (android.database.sqlite; iOS libsqlite3). No bundling required.
- **WAL mode:** Write-Ahead Logging enables concurrent readers while a writer is active. This matches IRIS's access pattern (relay writer + UI reader + routing reader running concurrently).
- **SQL for complex queries:** Bundle queries (by destination, by TTL, by priority, by hop count) are natural SQL. No application-layer index management required.
- **Small footprint:** SQLite library is ~1 MB; rusqlite bindings add minimal overhead.
- **Rust support:** `rusqlite` crate is mature, production-quality, actively maintained. `sqlx` is an alternative with async support.
- **Battle-tested:** SQLite has been in production on mobile devices for 15+ years; its WAL mode and concurrent access behavior is well-characterized.

**Cons:**
- **Not optimized for high-throughput append:** SQLite's WAL mode handles concurrent reads well but can bottleneck under high-frequency writes (>1,000 writes/second). IRIS gateway nodes may need batch insertion for high-traffic scenarios.
- **Single writer:** Only one writer at a time in WAL mode (readers don't block writers, but writers block each other). Not a problem for IRIS (single relay engine writes; UI and routing engine read).
- **No native time-series operations:** Efficient TTL expiry requires explicit query + delete; no native expire-by-time support. IRIS implements periodic TTL cleanup (every 60 seconds).

### Option B: LevelDB / RocksDB

**Description:** Key-value stores optimized for write-heavy workloads. LevelDB (Google) and its fork RocksDB (Meta) are common choices for append-heavy applications.

**Pros:**
- Higher write throughput than SQLite under heavy write load (LSM tree structure)
- RocksDB is used by MySQL, Kafka, TiKV for exactly this reason

**Cons:**
- **Complex queries require application-layer indexing:** "Get all bundles to destination X with TTL > now" requires maintaining secondary indexes manually (or scanning all keys). This moves query logic into application code, adding complexity and potential bugs.
- **No SQL:** All query logic must be hand-coded.
- **Rust support:** `rocksdb` crate exists but has a large binary footprint and complex build (uses C++ code). Android cross-compilation is difficult.
- **Footprint:** RocksDB adds ~10 MB to binary size; not appropriate for mobile.
- **Overkill:** IRIS write throughput is 10–100 bundles/second, not 1,000+. LevelDB/RocksDB benefits are at higher write rates.

### Option C: Custom File-Based Store

**Description:** Each bundle stored as a file; a small in-memory index maintained for queries.

**Pros:**
- Simplest implementation
- No library dependency
- Files can be inspected by external tools

**Cons:**
- **No atomicity:** Writing a bundle (index update + file write) is not atomic without careful design. Process crash mid-write can corrupt the store.
- **Query performance:** Scanning files for bundle selection requires reading all index entries; O(n) scan for every query. With 1,000 bundles, this is fine; with 10,000 (disaster scenarios), it becomes a bottleneck.
- **No WAL:** Concurrent access requires application-layer locking.
- **Reinventing the wheel:** SQLite solves exactly this problem with 20 years of hardening.

### Option D: Realm

**Description:** Mobile-first object-oriented database. Used by mobile apps for persistent local storage.

**Pros:**
- Mobile-optimized; good Android/iOS support
- Object-oriented API; no SQL

**Cons:**
- **No mature Rust binding:** Realm SDK is Java/Kotlin, Swift, and JavaScript. No production-quality Rust binding exists.
- **Proprietary:** Realm is now owned by MongoDB Atlas (subscription service). The embedded Realm database is free but future licensing is uncertain.
- **Overkill for IRIS:** Realm's object sync (its main differentiator) is not needed; IRIS does not sync with a cloud database.

## Decision

**SQLite** via the `rusqlite` Rust crate, operating in **WAL mode** with the following configuration:

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;   -- fsync on checkpoint, not every write
PRAGMA cache_size = -8192;     -- 8 MB page cache (negative = kilobytes)
PRAGMA busy_timeout = 5000;    -- 5-second timeout on locked writes
PRAGMA foreign_keys = ON;
```

Bundle store schema (simplified):

```sql
CREATE TABLE bundles (
    bundle_id    BLOB PRIMARY KEY,   -- 16-byte random ID
    source_eid   BLOB NOT NULL,      -- 32-byte Ed25519 public key hash
    dest_eid     BLOB NOT NULL,      -- 32-byte Ed25519 public key hash
    created_at   INTEGER NOT NULL,   -- Unix timestamp (seconds)
    expires_at   INTEGER NOT NULL,   -- Unix timestamp; NULL = never
    priority     INTEGER NOT NULL DEFAULT 3,  -- 0 (SOS) to 3 (text)
    payload      BLOB NOT NULL,      -- Encrypted payload (CBOR + ChaCha20)
    hop_count    INTEGER NOT NULL DEFAULT 0,
    relay_count  INTEGER NOT NULL DEFAULT 0,
    status       TEXT NOT NULL DEFAULT 'pending'  -- pending/relayed/delivered
);

CREATE INDEX idx_bundles_dest_expires ON bundles (dest_eid, expires_at);
CREATE INDEX idx_bundles_priority_created ON bundles (priority, created_at);
```

---

## Rationale

1. **Ubiquitous on Android/iOS:** SQLite is a system library on both platforms. `rusqlite` can link against the system SQLite (avoiding bundling). This reduces APK/IPA size significantly.

2. **WAL mode matches access pattern:** The relay engine writes; UI and routing engine read concurrently. WAL mode (concurrent reads + serialized writes) matches exactly.

3. **SQL query expressiveness:** Bundle selection queries are straightforward SQL:
   ```sql
   SELECT bundle_id, payload FROM bundles
   WHERE dest_eid = ? AND expires_at > ? AND hop_count < 10
   ORDER BY priority ASC, created_at ASC LIMIT 10;
   ```
   This would require significant application-layer code with LevelDB.

4. **Proven at scale:** Android uses SQLite for contacts, messages, and media metadata on billions of devices. The write throughput required by IRIS (10–100 bundles/second at peak) is well within SQLite's WAL-mode capability.

5. **Simplicity:** `rusqlite` provides ergonomic Rust bindings; no additional infrastructure.

---

## Consequences

### Positive

- SQL queries for bundle selection are readable and maintainable
- WAL mode enables concurrent UI + routing reads without blocking relay writes
- System SQLite linking reduces binary size
- Schema migrations handled by `rusqlite_migration` crate

### Negative

- **High-frequency writes require batch insertion:** At >100 bundles/second (gateway node in dense event scenarios), individual INSERT per bundle causes WAL checkpoint contention. Mitigation: batch inserts in transactions (`BEGIN TRANSACTION; INSERT × N; COMMIT;`); IRIS relay engine buffers incoming bundles in memory and flushes to SQLite in batches of 50 or every 500ms.
- **TTL cleanup requires explicit periodic query:** No auto-expire. IRIS runs a cleanup task every 60 seconds: `DELETE FROM bundles WHERE expires_at < ?`.
- **SQLite file corruption risk on unclean Android kill:** WAL mode + `PRAGMA synchronous = NORMAL` means a crash between checkpoint and fsync can theoretically corrupt. Android Keystore hardware-backed write barriers reduce (not eliminate) this risk. IRIS validates bundle store integrity on startup (`PRAGMA integrity_check`) and rebuilds from scratch if corrupted (bundles are replicated in the mesh; local loss is recoverable).

### Neutral

- `rusqlite` requires bundling SQLite if system SQLite is not used (iOS requires bundling; Android can use system library)

---

## Implementation Notes

- Crate: `rusqlite` 0.31+ with `bundled-sqlcipher` feature disabled (system SQLite for Android, bundled for iOS/desktop)
- Migrations: `rusqlite_migration` crate; migrations in `crates/iris-core/migrations/`
- Schema: `crates/iris-core/src/store/schema.rs`
- Encryption at rest: SQLite WAL files are not encrypted at the database level; individual bundle payloads are encrypted (ChaCha20-Poly1305) at the application layer. Full database encryption (SQLCipher) is a future option but adds complexity.
