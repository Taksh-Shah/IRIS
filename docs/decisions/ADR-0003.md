# ADR-0003: Use Rust for Core Protocol Implementation

**Status:** Approved  
**Date:** 2026-01-20  
**Deciders:** Architecture / Engineering leads  

---

## Context

IRIS needs a primary implementation language for the core protocol stack: bundle parsing/serialization, DTN routing engine, transport abstraction layer, cryptographic operations, and SQLite bundle store. This core is shared across:
- Android app (via JNI / Android NDK)
- iOS app (via Swift-Rust FFI)
- Linux/Raspberry Pi gateway
- Tauri desktop app (Windows, macOS, Linux)

Requirements for the core language:
1. **Memory safety without GC:** The core handles untrusted network input (bundle parsing). Buffer overflows in parsers are a well-documented attack surface. GC pause is unacceptable in a relay that must forward time-sensitive bundles.
2. **C-level performance:** Gateway nodes (RPi 4) may relay 100+ bundles/second; the core must be fast enough to not bottleneck relay.
3. **Cross-platform FFI:** Must compile to Android arm64-v8a and iOS arm64 without JVM or GC dependency; must produce C-compatible ABI for FFI.
4. **Cross-compilation:** Must cross-compile from Linux x86_64 to: Android arm64, iOS arm64, ARMv7 (RPi 3), aarch64 (RPi 4).
5. **Ecosystem quality:** Cryptography, SQLite, CBOR, BLE libraries must be available and production-quality.

---

## Options Considered

### Option A: C

**Description:** The original systems programming language. Universal FFI compatibility; runs everywhere.

**Pros:**
- Universal cross-platform support; any target architecture
- Zero-overhead; direct control of memory
- Largest ecosystem of systems libraries (OpenSSL, libsqlite3, etc.)
- Easy FFI from any language (C ABI is the universal interface)

**Cons:**
- **Memory unsafety:** C has no memory safety guarantees. Buffer overflows, use-after-free, and integer overflows in C protocol parsers are responsible for the majority of critical vulnerabilities in networking software (CVEs in OpenSSL, network stacks, etc.). IRIS parses untrusted input from any mesh participant — this is a critical attack surface.
- Developer productivity: manual memory management slows development; harder to reason about correctness
- Tooling: AddressSanitizer/Valgrind catch some bugs at runtime but not all; Coverity/clang-analyzer miss subtle bugs
- Test frameworks: less mature test infrastructure than Rust (no property-based testing framework as ergonomic as `proptest`)

### Option B: C++

**Description:** C with classes, templates, RAII, and the C++ standard library.

**Pros:**
- RAII prevents some memory issues; smart pointers prevent some use-after-free
- Rich standard library; better abstractions than C
- Large ecosystem

**Cons:**
- Still memory-unsafe by default; undefined behavior is pervasive
- `std::string::operator[]` out-of-bounds is undefined behavior (not a bounds-checked exception)
- Move semantics help but do not prevent all use-after-move bugs
- Complexity: C++ is notoriously difficult to use correctly; expert-level C++ is required to avoid common pitfalls
- No formal memory safety guarantees

### Option C: Go

**Description:** Google's statically compiled language with garbage collection, goroutines, and a standard library.

**Pros:**
- Memory safe (GC manages allocation/deallocation)
- Fast compilation; excellent standard library
- Good concurrency model (goroutines)
- Cross-compilation support (GOARCH/GOOS)

**Cons:**
- **GC pauses:** Go's GC (even the "stop-the-world-free" Go 1.14+ concurrent GC) produces latency jitter. For a relay node that must process and forward time-critical bundles, GC pause introduces unpredictable delay. This is acceptable for server software; problematic for a real-time relay.
- **CGo for Android/iOS:** Go on mobile requires CGo for JNI/Objective-C interop. CGo significantly complicates cross-compilation and adds overhead.
- **Binary size:** Go binaries are large (5–20 MB minimum). Android/iOS app size is constrained; embedding a large Go binary as a shared library is problematic.
- **No `no_std` equivalent:** Go cannot compile to bare-metal targets; limits future embedded deployment options (ESP32).

### Option D: Rust

**Description:** Mozilla's systems programming language with a borrow checker that enforces memory safety at compile time, no GC.

**Pros:**
- **Memory safety at compile time:** The borrow checker prevents data races, use-after-free, null pointer dereferences, and most buffer overflows without runtime overhead. This is the strongest formal memory safety guarantee available in a systems language.
- **Zero-cost abstractions:** Performance equivalent to C/C++ with idiomatic code. Benchmark comparisons show Rust within 1–5% of equivalent C code in networking tasks.
- **Cross-compilation:** Rust's target triple system supports cross-compilation to Android (arm64-v8a, armeabi-v7a, x86_64), iOS (aarch64-apple-ios), Linux (aarch64-unknown-linux-gnu for RPi), Windows, macOS.
- **C FFI:** Rust can produce C-compatible shared libraries (.so, .dylib, .dll) with `#[no_mangle]` and `extern "C"`. This is the standard mechanism for Rust-Android (JNI) and Rust-iOS (Swift/Obj-C) integration.
- **`no_std` support:** Rust can compile for bare-metal embedded targets (no OS). Future ESP32 port is feasible.
- **Ecosystem:** `ring` (cryptography), `rusqlite` (SQLite), `ciborium` (CBOR), `btleplug` (BLE), `tokio` (async runtime) — all production-quality crates.
- **Test framework:** `proptest` for property-based testing; `cargo-fuzz` for libFuzzer integration; excellent unit test support.

**Cons:**
- **Learning curve:** Rust's borrow checker requires a significant mindset shift from C/C++/Go. New team members require 2–4 weeks to become productive.
- **Smaller talent pool in India:** Experienced Rust developers in India are fewer than experienced Java/Kotlin/Go developers. Hiring is harder.
- **Compilation speed:** Rust compiles slowly compared to Go or C. A full rebuild of iris-core takes 2–3 minutes. Incremental builds are faster but still slower than Go.
- **Async complexity:** Rust async (tokio, async-std) is more complex to understand than Go goroutines.

### Option E: Kotlin (Multiplatform)

**Description:** Kotlin Multiplatform (KMP) compiles Kotlin to JVM (Android), native (iOS, desktop), and JS.

**Pros:**
- Single language for Android, iOS, desktop
- Good coroutines story; familiar to Android developers

**Cons:**
- KMP native (iOS, desktop) is not memory-safe at the language level (Kotlin/Native uses ARC, not a borrow checker)
- KMP performance is lower than Rust/C for protocol parsing
- No FFI to C without wrappers
- Not suitable for bare-metal embedded deployment

---

## Decision

**Rust** for the core protocol implementation (`iris-core` crate), with platform-specific bindings:
- Android: JNI (`iris-android` crate, produces `libiris_android.so`)
- iOS: Swift/Obj-C FFI (`iris-ios` crate, produces `libiris_ios.a`)
- Desktop: Tauri (Rust process directly uses `iris-core`)
- Gateway: Rust binary (`iris-gateway`) runs on Linux/RPi

---

## Rationale

1. **Protocol parsing security:** IRIS parses untrusted bundles from any mesh node, including potentially malicious actors. Memory unsafety in the parser is the highest-impact vulnerability category. Rust's compile-time memory safety eliminates this attack class structurally — not through code review, not through dynamic analysis, but through the type system.

2. **Cross-platform FFI without GC:** Android and iOS require a GC-free shared library. Rust produces exactly this. Go requires CGo (expensive) and carries a runtime; Kotlin/Native is not GC-free on iOS.

3. **Performance:** PRoPHET routing computes P(a,b) for all known destinations on every contact event. A node with 1,000 known destinations performs 1,000 float multiplications per contact. Rust's performance (within 2% of C in micro-benchmarks) ensures this is not a bottleneck on cheap Android SoCs.

4. **Future-proofing for embedded:** LoRa relay functionality on ESP32 or nRF5340 (for permanent gateway nodes without RPi cost) requires `no_std`. Rust's `no_std` support makes this feasible; none of the other options support it.

---

## Consequences

### Positive

- Eliminates memory safety vulnerabilities in protocol parser by construction
- Single core codebase compiled to all targets (no reimplementation for each platform)
- Property-based testing and fuzzing infrastructure is first-class in the Rust ecosystem
- `unsafe` blocks are syntactically visible and auditable — reviewer can focus audit effort on `unsafe` code

### Negative

- **Talent pool:** India has fewer experienced Rust developers than Java/Go/Python. Hiring requires either training or accepting higher compensation. Current mitigation: hire strong engineers and train; budget 4-week Rust onboarding.
- **Compilation speed:** Slow full builds affect developer productivity. Mitigation: `sccache` for CI, incremental builds in development, modular crate structure to minimize rebuild scope.
- **Learning curve:** Borrow checker errors frustrate developers new to Rust. Mitigation: pair programming during onboarding; internal Rust study group.

### Neutral

- Kotlin and Swift handle all UI; only the core protocol is Rust. Android/iOS developers do not need to write Rust for normal feature development.
- The Rust FFI boundary is a defined API surface (`iris.h` C header); platform teams interface only with this header.

---

## Implementation Notes

- Workspace structure: `crates/` contains `iris-core`, `iris-android`, `iris-ios`, `iris-gateway`, `iris-cli`
- Android: `cargo-ndk` for cross-compilation to Android targets; JNI wrappers in `iris-android`
- iOS: `cargo lipo` for universal binary; Swift package wraps C header generated by `cbindgen`
- Cross-compilation targets maintained in `.cargo/config.toml`: `aarch64-linux-android`, `aarch64-apple-ios`, `aarch64-unknown-linux-gnu`
- MSRV (Minimum Supported Rust Version): 1.75.0 (stabilized async-fn-in-trait, required for transport abstraction)
