# ADR-0002: Use Ed25519 for Identity and Signing

**Status:** Approved  
**Date:** 2026-01-15  
**Deciders:** Core protocol team, Security  

---

## Context

IRIS requires a digital signature algorithm for two purposes:
1. **Identity:** Each IRIS node has a permanent identity keypair. The public key is the node's IRIS address (Node ID). Messages are signed by the sender's private key; receivers verify authenticity.
2. **Message authentication:** Every IRIS bundle is signed by its sender. Relay nodes verify the signature before forwarding to prevent relay of corrupted or tampered bundles.

Requirements:
- **Small signatures:** LoRa maximum payload is 222 bytes. A bundle primary block (~60 bytes) + payload + signature must fit. Signature size directly limits payload capacity.
- **Fast verification:** Relay nodes verify every incoming bundle before forwarding. High throughput relays may need to verify hundreds of bundles per minute.
- **Constant-time implementation:** Side-channel attacks via timing are a realistic threat on shared devices.
- **Rust library maturity:** The core is Rust; the signing library must be production-quality.
- **Security margin:** 128-bit security minimum.

---

## Options Considered

### Option A: RSA-2048

**Description:** RSA with 2048-bit key and PKCS#1 v1.5 or PSS padding. Legacy industry standard.

**Signature size:** 256 bytes  
**Public key size:** 256 bytes (modulus) + 3 bytes (exponent) ≈ 294 bytes (DER encoded)  
**Verification speed (ARM Cortex-A53):** ~3,000 verifications/second (OpenSSL benchmark)  
**Constant-time:** RSA implementations require careful implementation to avoid timing side-channels; many do not achieve it  
**Security level:** 112-bit (NIST estimates RSA-2048 ≈ 112-bit security, not 128-bit)

**Critical issue:** 256-byte signature + 256-byte public key = 512 bytes. A LoRa bundle with RSA signature cannot fit the combined 222-byte LoRa payload limit. RSA is ruled out for any LoRa deployment.

### Option B: ECDSA-P256

**Description:** Elliptic Curve Digital Signature Algorithm over NIST P-256. FIPS 186-4 standard.

**Signature size:** 64 bytes (two 32-byte integers r, s; DER encoded: 70-72 bytes)  
**Public key size:** 33 bytes (compressed point)  
**Verification speed (ARM Cortex-A53):** ~20,000 verifications/second  
**Constant-time:** Not guaranteed in all implementations; requires careful constant-time scalar multiplication  
**Security level:** 128-bit

**Security issue:** ECDSA requires a random nonce k per signature. If k is reused (even once across two signatures), the private key is fully recoverable. This is a catastrophic failure mode that has been exploited in practice (PS3, Bitcoin wallets). In disaster scenarios, the random number generator may be in a degraded state (device rebooted multiple times, low entropy from constrained OS); nonce reuse risk is elevated.

**FIPS note:** P-256 is FIPS 140-2/3 approved. Government customers that require FIPS-certified cryptography would require P-256 (or P-384). This is a future requirement risk — see Consequences.

### Option C: Ed25519 (RFC 8032)

**Description:** Edwards-curve Digital Signature Algorithm (EdDSA) over Curve25519 (twisted Edwards form). IETF RFC 8032.

**Signature size:** 64 bytes  
**Public key size:** 32 bytes  
**Verification speed (ARM Cortex-A53):** ~70,000 verifications/second (ring crate benchmark)  
**Constant-time:** Yes, by construction — the algorithm uses only fixed-time operations; no branching on secret data  
**Security level:** 128-bit equivalent (Curve25519 provides ~126-bit security, generally rounded to 128-bit)

**Deterministic:** Ed25519 is deterministic — signatures are derived from private key + message via SHA-512, as specified in RFC 8032. **IRIS uses standard Ed25519 with SHA-512 internally** — this is a fixed property of the algorithm, not configurable. BLAKE3 is used elsewhere in IRIS (for NodeId derivation, payload hashing) but is NOT used inside the Ed25519 signing function. No external random number generator required at signing time. Nonce reuse attacks are impossible.

**Rust support:** `ring` crate (Google-maintained, used by Chromium, AWS, Cloudflare), `ed25519-dalek` (pure Rust, `no_std` compatible for future embedded targets). Both are production-quality.

### Option D: Ed448 (RFC 8032)

**Description:** EdDSA over Curve448 (Goldilocks). Higher security margin than Ed25519.

**Signature size:** 114 bytes  
**Security level:** 224-bit equivalent (overkill for any realistic adversary)  
**Rust support:** Less mature than Ed25519; `ed448-goldilocks` crate

**Reason not chosen:** 114-byte signature is 50 bytes larger than Ed25519. This reduces LoRa payload headroom significantly. 224-bit security is far more than required. Not standardized as widely as Ed25519.

---

## Decision

**Ed25519 (RFC 8032)** using the `ed25519-dalek` crate in Rust for the core protocol.

IRIS Node ID is derived as: `BLAKE3(ed25519_public_key)[0..32]` — the first 32 bytes of the BLAKE3 hash of the Ed25519 public key (32 bytes). This provides a fixed-length identifier and a commitment to the public key without transmitting the full public key in every message (the full public key is transmitted in the first contact announcement; subsequently, only the Node ID is used in bundle headers).

---

## Rationale

1. **Size:** 64-byte signatures fit comfortably within LoRa 222-byte payloads alongside bundle headers and short payloads.

2. **Speed:** 70,000 verifications/second on ARM is 23× faster than RSA-2048. A gateway node relaying at 10 bundles/second spends 0.014% of CPU on signature verification.

3. **Deterministic — no nonce reuse possible:** This is the strongest argument against ECDSA-P256. Ed25519's deterministic construction eliminates the nonce management failure mode entirely.

4. **Constant-time by construction:** Ed25519's formulas are free of data-dependent branching. Timing side-channel resistance is a mathematical property, not an implementation discipline.

5. **Rust ecosystem:** `ed25519-dalek` is well-maintained, `no_std` compatible, and has been reviewed by multiple security researchers.

6. **RFC standard:** RFC 8032 is a widely adopted IETF standard; Ed25519 is used by SSH, TLS 1.3, Signal Protocol, and many others.

---

## Consequences

### Positive

- 64-byte signatures fit within LoRa payload budgets
- Fastest verification of the three options considered
- No nonce management; no nonce reuse failure mode
- Constant-time by construction
- Deterministic: same private key + same message → same signature (useful for testing)

### Negative

- **Not FIPS 140-2/3 certified:** Ed25519 is included in FIPS 186-5 (2023) but older FIPS 140-2 certifications still require P-256. Some government customers may require FIPS-certified cryptography. Risk assessment: NDRF and SDRF are not currently required to use FIPS-certified cryptography in IT systems. If a specific procurement requires FIPS, an ECDSA-P256 variant would need to be developed. This risk is documented and accepted.

- **Not AES-based:** Some enterprise and government security policies specify "must use AES and RSA or ECDSA." Ed25519 is none of these. Same mitigation: document exception and seek waiver if required.

### Neutral

- Ed25519 is less commonly known than RSA/ECDSA in Indian enterprise security circles; team training and documentation required
- The Node ID derivation (BLAKE3 hash of public key) means the full public key must be transmitted before a Node ID can be verified; this is handled by the contact announcement protocol

---

## Implementation Notes

- Crate: `ed25519-dalek` v2.x (supports `no_std`, batch verification)
- Batch verification: `ed25519-dalek` supports verifying multiple signatures simultaneously using Ristretto point batch; used in gateway nodes to batch-verify incoming bundles before forwarding
- Key storage: Android Keystore (hardware-backed if available); iOS Secure Enclave; Linux: file-based with restrictive permissions (0600), encrypted at rest with device key
- Key format on wire: raw 32-byte public key (not DER, not PEM — unnecessary overhead for constrained format)
