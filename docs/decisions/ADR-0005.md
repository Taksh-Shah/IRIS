# ADR-0005: PRoPHET as Primary Opportunistic Routing Algorithm

**Status:** Approved  
**Date:** 2026-02-10  
**Deciders:** Core protocol team, Research  

---

## Context

IRIS needs a routing algorithm for opportunistic, store-carry-forward delivery of bundles in a DTN mesh. The algorithm runs on every IRIS node and answers the question: "When I encounter node X, should I forward bundle B to X?"

Requirements:
- **Delivery ratio:** Maximize the probability that SOS, location, and text bundles reach their destination
- **Overhead control:** Minimize the number of copies of each bundle in the network (storage is finite; LoRa/BLE bandwidth is limited)
- **Latency:** Minimize average delivery time for P0 bundles (SOS target: 30 seconds end-to-end in 3-hop mesh)
- **State:** Minimize the state that must be maintained per-node (memory and storage constraints)
- **Convergence:** Algorithm must function correctly when nodes have incomplete knowledge (they have not met all nodes in the network)
- **Cold start:** Must function when a node has no contact history (new device, fresh install)

---

## Options Considered

### Option A: Epidemic Routing

**Description:** Flooding. Every node replicates every bundle to every encountered node. No routing intelligence; maximum delivery probability.

**Delivery ratio:** Maximum achievable — any node that can reach the destination will carry a copy.

**Overhead ratio:** Very high — O(N) copies per bundle where N is network size. In a 100-node network with 50 bundles, epidemic generates ~5,000 copies. Storage exhaustion is the failure mode.

**State required:** None (no contact history needed).

**Lationale for rejection:** In a resource-constrained disaster mesh (finite storage, limited LoRa/BLE bandwidth), epidemic routing is not deployable at scale. The overhead would consume all available bandwidth and storage, preventing new bundles from being carried. Epidemic is acceptable for P0 SOS bundles only (where delivery probability outweighs overhead concerns).

### Option B: Spray-and-Wait

**Description:** Two-phase routing. Phase 1 (Spray): distribute L copies to L distinct relays. Phase 2 (Wait): each relay waits for direct contact with destination. No routing intelligence; efficient if L is chosen well.

**Delivery ratio:** Approaches epidemic as L → N (network size); lower overhead than epidemic at L << N.

**Overhead ratio:** O(L) — configurable. With L=8 in a 100-node network: 8 copies per bundle.

**State required:** Copy count (2 bits per bundle) — very low.

**Key limitation:** Spray-and-Wait is "routing-agnostic" — it chooses L relays randomly (or by first-contact in basic Spray-and-Wait). It does not prefer relays that are likely to deliver to the destination. In a structured environment (where some nodes frequently contact certain destinations), Spray-and-Wait wastes copies on poor relays.

**Why kept as fallback:** Spray-and-Wait is the best option for cold-start scenarios where no contact history exists. Low state requirement means it works immediately on first use.

### Option C: PRoPHET (Probabilistic Routing Protocol using History of Encounters and Transitivity)

**Description:** Probabilistic routing using learned delivery probability P(a,b) derived from contact history between node a and destination b. Forwards a bundle to node X if X has higher P toward the destination than the current node.

**Delivery ratio:** Higher than Spray-and-Wait (especially in structured mobility); lower than epidemic.

**Overhead ratio:** Lower than epidemic; higher than Spray-and-Wait with small L. In practice: delivery/overhead tradeoff is better than both for structured human mobility patterns.

**State required:** P(a,b) for all known destinations. With 1,000 known nodes: 1,000 float32 values = 4 KB. Manageable.

**Academic validation:** Lindgren et al. (2004) and subsequent work demonstrate PRoPHET outperforms Spray-and-Wait and epidemic on traces of human mobility. Indian disaster mobility (evacuation along roads, congregation at relief camps) is more structured than random waypoint; PRoPHET's advantage over Spray-and-Wait is expected to be larger.

**Key limitation:** PRoPHET requires contact history. A new node with no history has P=0 for all destinations — effectively invisible to the routing algorithm.

### Option D: MaxProp

**Description:** Priority-based routing that combines delivery probability with per-bundle utility scheduling. Maintains a per-bundle ranking for forwarding.

**Delivery ratio:** Higher than PRoPHET in some studies (more complex utility function).

**Overhead ratio:** Comparable to PRoPHET.

**State required:** Per-bundle utility values (more complex than PRoPHET's per-node P values).

**Why rejected:** MaxProp's computational cost is higher than PRoPHET (more complex utility computation per contact event). For IRIS's constrained devices, PRoPHET's delivery/overhead/compute tradeoff is better. MaxProp is documented as a future upgrade candidate if PRoPHET proves insufficient.

### Option E: RAPID (Resource Allocation Protocol for Intentional DTN routing)

**Description:** Utility-based routing that solves a resource allocation problem to maximize a global delivery utility.

**Why rejected:** RAPID requires approximate global state (aggregate statistics of all nodes' contact patterns). This state is not available in partitioned networks. Not suitable for IRIS disaster scenarios where the network is highly partitioned.

---

## Decision

**PRoPHET as primary routing algorithm with Spray-and-Wait (Binary variant) as cold-start fallback.**

**Fallback logic:**

```
for each bundle to forward to node X:
    if contact_history.sample_count(X) >= MIN_SAMPLES:
        use PRoPHET: forward if P(self, dest) < P(X, dest) + EPSILON
    else:
        use Binary Spray-and-Wait with L = DEFAULT_L
```

`MIN_SAMPLES`: configurable; default 3 (node must have 3+ contact events with any node before PRoPHET activates; prevents very noisy P estimates from sparse contacts).

**Epidemic override for P0 bundles (SOS):**

P0 bundles use epidemic routing regardless of PRoPHET or Spray-and-Wait state. The overhead of epidemic routing for SOS is acceptable given the delivery criticality.

---

## Rationale

1. **Better delivery/overhead tradeoff than alternatives:** PRoPHET's contact history enables intelligent routing that Spray-and-Wait (no routing intelligence) and epidemic (unlimited overhead) cannot match.

2. **Human mobility is structured:** Indian disaster scenarios involve evacuation along known roads, congregation at known relief camps, and responder movement between known zones. PRoPHET's contact history captures these patterns; Spray-and-Wait cannot.

3. **State is manageable:** 4 KB for 1,000-node P table is negligible. SQLite stores contact history efficiently.

4. **Literature support:** PRoPHET's performance on human mobility traces (Cambridge, EPFL, MIT) is well-documented. Indian-specific calibration is planned (RESEARCH_GAPS.md GAP-001).

5. **Cold-start coverage:** Binary Spray-and-Wait covers the cold-start scenario without sacrificing correctness.

6. **Epidemic override for SOS:** P0 bundles (SOS) use epidemic because delivery probability must be maximized regardless of overhead.

---

## Consequences

### Positive

- Better delivery ratio than pure Spray-and-Wait in structured mobility environments
- Contact history enables transitivity: IRIS can route toward a destination it has never met if an intermediary has
- Well-studied algorithm; parameters are interpretable and debuggable (P values are meaningful probabilities)
- Combined PRoPHET + Spray-and-Wait handles both steady-state (PRoPHET) and cold-start (Spray-and-Wait) correctly

### Negative

- **Requires contact history state:** PRoPHET must maintain P(a,b) for all known destinations. With 10,000 nodes (large national deployment), P table requires 40 KB — still manageable, but this scales linearly with network size.
- **More complex than Spray-and-Wait or epidemic:** Requires correct implementation of three update rules (encounter, aging, transitivity) and a forwarding decision algorithm. More surface area for bugs.
- **Parameters require tuning:** P_init, γ, β are not universally optimal. Default values from literature may not be optimal for Indian disaster scenarios — see RESEARCH_GAPS.md GAP-001. Incorrect parameters can significantly reduce delivery ratio.
- **Cold start gap:** A node with no contact history gets Spray-and-Wait routing (not PRoPHET). In a first-disaster scenario (no pre-disaster contact history built up), the entire network may be in cold-start mode.

### Neutral

- PRoPHET is deterministic given the same contact history — behavior is reproducible in simulation, which aids testing and debugging

## Implementation Notes

- Module: `crates/iris-core/src/routing/prophet.rs`
- Contact history persisted in SQLite (`contact_events` table)
- P values recomputed on each contact event and after aging interval (every 10 minutes)
- Transitivity exchange: when nodes A and B meet, they exchange their P vectors (a brief anti-entropy sync). Exchange encoded as CBOR array of (dest_node_id, P_value) pairs. To limit bandwidth, only exchange entries where P > 0.1 (prune low-value entries).
- IRIS_PROPHET_P_INIT, IRIS_PROPHET_GAMMA, IRIS_PROPHET_BETA are configurable via `config/defaults.toml`; overridable by gateway operator or enterprise admin
