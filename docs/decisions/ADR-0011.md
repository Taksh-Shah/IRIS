# ADR-0011: Flat Envelope Protocol Structure for IRIS v1

**Status:** Approved
**Date:** 2026-08-11
**Deciders:** Protocol Agent, Principal Architect
**Supersedes:** N/A
**Superseded by:** N/A

## Context

IRIS requires a wire protocol envelope format. Three alternatives were evaluated:
- **A: Flat Envelope** (current design) — single CBOR map with integer keys
- **B: BPv7 Block-Based** — adopt BPv7's block array structure natively
- **C: Hybrid** — flat for P0-P2, block-based for P3-P7

The choice affects every layer of the system: message parsing, relay behavior, security model, fragmentation, and interoperability.

## Research Conducted

1. RFC 9171 (BPv7) — full specification analysis
2. RFC 4838 (DTN Architecture) — architectural principles
3. Bluetooth Mesh Protocol 1.1 — mesh networking approaches
4. LoRa/LoRaWAN IN865 regional parameters — payload size constraints
5. WPC India spectrum regulations — 865-867 MHz band

See: `docs/protocol/PROTOCOL_ALTERNATIVES.md`

## Decision

**Alternative A (Flat Envelope)** is approved as the IRIS v1 wire protocol structure.

The envelope is a single CBOR map with integer keys (1-18+). P0 messages use an abbreviated format with truncated fields. Extension fields are appended at the end of the map and ignored by nodes that don't understand them.

## Rationale

1. **P0 LoRa fit is CRITICAL**: Flat envelope with abbreviated P0 format leaves 69 bytes for payload within the 255-byte LoRa limit. This is sufficient for GPS coordinates + short emergency text.

2. **Implementation simplicity**: Single CBOR map decode is faster, uses less memory, and has fewer failure modes than block-based parsing. This matters on battery-constrained smartphones in disaster conditions.

3. **Adequate extensibility for v1**: The append-only extension mechanism (new fields at end of map, unknown-field tolerance) provides sufficient forward compatibility for the v1 lifecycle. BPv7's block-based extensibility is more powerful but overkill for smartphone-to-smartphone mesh.

4. **BPv7 interop is not a v1 requirement**: BPv7 interoperability can be provided by a future gateway adapter that translates between IRIS flat envelopes and BPv7 bundles. This is architecturally cleaner than native block adoption.

5. **Deterministic parsing**: Fixed integer key positions mean O(1) field access. Block-based requires O(n) block search.

6. **Smaller attack surface**: Fewer parsing code paths means fewer potential vulnerabilities in the protocol parser — a security boundary that handles untrusted input.

## Extension Mechanism

To address the extensibility concern without adopting block-based structure:

1. **New fields are appended**: Fields 19, 20, 21... added at end of map
2. **Unknown fields ignored**: Nodes skip map entries with keys they don't recognize
3. **Critical fields in low keys**: Fields 1-15 are mandatory/well-known; new optional fields use keys 16+
4. **Version negotiation**: Field 1 (version) indicates which fields are supported
5. **No breaking changes**: Old nodes can still parse envelopes containing new fields (they just ignore the new ones)

## Fragmentation Approach

For messages exceeding transport MTU:
- Fragment at the convergence layer (transport adapter)
- Each fragment is a complete envelope with `payload_type = FRAGMENT`
- Fragment payload contains: `{message_id, fragment_seq, total_fragments, data}`
- Original envelope's `payload_ref` links fragments
- Reassembly at destination before delivery to application

This is simpler than BPv7's block-based fragmentation but adequate for IRIS's needs.

## Consequences

### Positive
- Minimal wire overhead (critical for LoRa P0)
- Simple, fast parsing on constrained devices
- Clear security model (signature covers known fields)
- P0 abbreviated format maximizes emergency payload
- Smaller attack surface in parser

### Negative
- No native BPv7 interoperability (requires gateway)
- No per-field integrity (signature covers whole envelope)
- Adding new mandatory fields requires version bump
- Less extensible than block-based approach for future transports

### Neutral
- Fragmentation handled at convergence layer, not protocol layer
- BPv7 gateway adapter tracked as future node (GATEWAY_BPV7)
- Translation to/from BPv7 possible but not native

## Open Issues

1. **Hop count modification by relays**: Current design has a documented inconsistency — relays need to increment hop_count but can't re-sign. Resolution: hop_count is excluded from signature scope (relays may update it). This is noted in ADR-0011 and will be formalized in the protocol spec.

2. **Encryption header per-message vs per-session**: Current design shows per-message ephemeral key in encryption_hdr. ADR-0006 mentioned "per session." **RESOLVED 2026-08-14 (CRYPTO-001 RESEARCH, RES-0015 D1 / DEC-P0001): per-message ephemeral X25519** matching encryption_hdr; ADR-0006 wording corrected.

3. **P0 truncated sender_id**: 16-byte truncated BLAKE3 provides 128-bit security against collision. This is adequate but should be validated against actual collision probability in large-scale disaster scenarios.
