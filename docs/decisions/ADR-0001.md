# ADR-0001: Use CBOR over Protocol Buffers for Wire Format

**Status:** Approved  
**Date:** 2026-01-15  
**Deciders:** Core protocol team  
**Supersedes:** N/A  

---

## Context

IRIS needs a binary serialization format for the DTN bundle protocol wire format. The format must:
1. Be compact (LoRa maximum payload is 222 bytes at SF10 BW125; the bundle header must fit within this)
2. Be parseable on constrained devices (Android arm64, RPi 4, future ESP32 targets)
3. Have reliable, well-maintained library support in Rust, Kotlin, and Python
4. Require no out-of-band schema distribution (nodes must be able to parse messages from unknown-version senders)
5. Align with relevant DTN standards (RFC 9171 uses CBOR)

The format is used for: bundle primary block, bundle extension blocks (future), inter-node protocol messages (contact announcements, routing exchanges), and administration messages.

---

## Options Considered

### Option A: Protocol Buffers (protobuf)

**Description:** Google's binary serialization format using `.proto` schema files compiled to language-specific code.

**Pros:**
- Excellent performance; widely used; large ecosystem
- Strong Rust support (`prost` crate)
- Version evolution (field numbers allow adding fields without breaking)
- Small encoded size (varint encoding)

**Cons:**
- **Schema dependency:** Receiver must have the same (or compatible) `.proto` schema compiled in. Unknown fields in a message from a newer sender are silently ignored — no way to detect or react to unknown extension blocks.
- **Schema distribution problem:** In a DTN where nodes may be running different IRIS versions, schema out-of-band distribution is complex. A disaster survivor's phone running IRIS 1.0 must be able to receive a bundle from an NDRF phone running IRIS 1.3.
- **Not a DTN standard:** RFC 9171 (BPv7) uses CBOR, not protobuf. Any future interoperability with other BPv7 implementations requires translation.
- **Schema compilation step:** Adds build complexity; `.proto` files must be committed and versioned carefully.

### Option B: CBOR (RFC 8949)

**Description:** Concise Binary Object Representation. A self-describing binary format based on a type system similar to JSON but binary. IETF standard.

**Pros:**
- **Self-describing:** No schema required. Any CBOR decoder can inspect the structure of any CBOR message. Unknown fields are preserved as CBOR items and can be passed through without understanding.
- **RFC standard:** RFC 8949; used by RFC 9171 (BPv7), COSE (RFC 9052), LAKE (RFC 9528), and many IETF IoT standards.
- **DTN ecosystem compatibility:** DTNME, µD3TN, and other open-source DTN implementations use CBOR for BPv7 bundles. Future interoperability is feasible without translation.
- **Constrained device support:** CBOR was specifically designed for IoT/constrained environments (RFC 7049 motivation); reference implementations exist for 8-bit microcontrollers.
- **Rust support:** `ciborium` crate (maintained); `cbor4ii` (faster, less mature). Both are production-quality.

**Cons:**
- **No schema enforcement:** Any valid CBOR can be encoded in any field position. Type errors must be caught manually in parsing code (cannot rely on schema-generated validators).
- **Slightly larger than protobuf for simple structs:** CBOR includes type tags per value (~1 byte overhead per field) that protobuf omits for known-schema fields.
- **Less common in application layer:** Most developers are more familiar with protobuf or JSON; CBOR requires learning a new format.

### Option C: MessagePack

**Description:** A binary JSON-equivalent format without an IETF standard.

**Pros:** Very compact; good library support.

**Cons:** Not an IETF standard; no DTN ecosystem use; offers no advantage over CBOR for IRIS's use case.

### Option D: FlatBuffers

**Description:** Google's zero-copy binary serialization format.

**Pros:** Zero-copy deserialization; very fast.

**Cons:** Not an IETF standard; schema required; complex schema evolution; overkill for IRIS's message sizes (FlatBuffers is most beneficial for multi-megabyte messages, not 200-byte bundles).

### Option E: Custom Binary Format

**Description:** Hand-crafted binary encoding specific to IRIS.

**Pros:** Maximum compactness; complete control.

**Cons:** Maintenance burden; no libraries; security risks from custom parser implementation; no interoperability with DTN ecosystem; would need to be validated from scratch.

---

## Decision

**CBOR (RFC 8949)** with compact array encoding (not map encoding).

IRIS uses CBOR arrays (not maps) for fixed-position structures (primary block, security block) to minimize per-field overhead. Extension blocks use CBOR maps (keyed by field number) for self-describing forward compatibility.

---

## Rationale

1. **Self-describing is essential for DTN:** A store-carry-forward network where nodes run different software versions cannot require synchronized schema files. CBOR's self-describing property is a correctness requirement, not a preference.

2. **RFC 9171 alignment:** CBOR is the BPv7 wire format. Using CBOR now positions IRIS for future BPv7 interoperability without a format translation layer.

3. **Constrained device support:** CBOR was designed for the IoT/constrained device use case that IRIS targets.

4. **Size is acceptable:** IRIS compact array encoding reduces CBOR overhead to ~1-2 bytes per field over raw binary. For a 60-byte primary block, the overhead is ~5 bytes vs protobuf — acceptable given the self-describing benefit.

5. **Schema discipline is a team practice, not a compiler feature:** The absence of protobuf schema validation is addressed by: (a) a dedicated `BundleParser` module with explicit field validation, (b) property-based tests (proptest in Rust) that fuzz parse arbitrary CBOR inputs, and (c) a defined IRIS bundle schema specification document.

---

## Consequences

### Positive

- CBOR libraries in Rust (`ciborium`), Kotlin (`cbor-java`), Python (`cbor2`) are all production-quality
- Future BPv7 interoperability path is straightforward
- Unknown extension blocks can be forwarded by relay nodes without understanding them (DTN extensibility)
- No build-time schema compilation step

### Negative

- Manual field validation required in parser code (no generated validators)
- Slightly larger on-wire size than protobuf for known-schema messages (acceptable — 5 bytes per bundle)
- Developer unfamiliarity with CBOR requires documentation and examples
- Fuzzing the CBOR parser is mandatory (no schema to constrain inputs); this adds test suite complexity

### Neutral

- CBOR is not well-known outside IoT and IETF contexts; team education required

---

## Implementation Notes

- Primary crate: `ciborium` (Rust) — mature, `no_std` compatible for future ESP32 port
- Validation: `iris-core/src/bundle/parser.rs` contains all field validation logic; each field has documented expected CBOR type and range
- Fuzzing: `fuzz/fuzz_targets/bundle_parse.rs` (libFuzzer target) must maintain 100% coverage of parser branches
- Schema: `docs/protocol/BUNDLE_FORMAT.md` is the normative schema (maintained separately from the ADR)
