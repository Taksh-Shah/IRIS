# ADR-0006: ChaCha20-Poly1305 for Symmetric Encryption

**Status:** Approved  
**Date:** 2026-02-15  
**Deciders:** Core protocol team, Security  

---

## Context

IRIS encrypts bundle payloads end-to-end using a symmetric AEAD (Authenticated Encryption with Associated Data) cipher. The cipher is chosen after key agreement (X25519 Diffie-Hellman); the resulting shared secret is used as the AEAD key.

Requirements:
- **AEAD:** Provides both confidentiality and integrity in one operation. Relay nodes verify bundle integrity without decrypting payload. This requirement means integrity (MAC) must be computable over both the bundle header (plaintext, for routing) and the payload (ciphertext).
- **Performance on ARM without hardware acceleration:** Target devices include cheap Android phones (Redmi 12, MediaTek Helio G85; no AES-NI hardware instruction). Cipher must be fast in software.
- **Constant-time implementation:** Timing side-channels on shared-resource devices (where Android can run multiple apps) are a realistic threat model.
- **Small nonce management overhead:** Nonce management adds per-message overhead. Prefer ciphers with a large nonce space (reducing nonce collision probability) or deterministic nonces.
- **IETF standard:** Prefer ciphers with IETF RFC status for auditability and future FIPS compliance roadmap.

---

## Options Considered

### Option A: AES-256-GCM

**Description:** AES (Advanced Encryption Standard) with 256-bit key in Galois/Counter Mode. NIST standard, FIPS 140-2/3 approved. The most widely used AEAD cipher.

**Key size:** 256 bits  
**Nonce size:** 96 bits (12 bytes) — NIST recommended  
**Authentication tag:** 128 bits (16 bytes)  
**IETF standard:** RFC 5116 (AEAD interface), RFC 5288 (AES-GCM in TLS)

**Performance (ARM Cortex-A55, no AES-NI):**
- AES-256-GCM (software): ~50–80 MB/s (Bouncy Castle Android benchmark)
- AES-256-GCM (hardware, AES-NI): ~500 MB/s+ (not relevant for our target devices)

**Security concern — GCM nonce reuse:**
- GCM's security requires unique nonces for every encryption with the same key
- Nonce reuse in GCM is catastrophic: both the keystream and the authentication key are fully exposed
- The 96-bit nonce with random generation has a nonce collision probability of ~50% after 2^48 messages (birthday bound) — not a realistic concern for IRIS message volumes
- However: if a device clock resets (common in power failure during disaster) and IRIS uses time-based nonces, nonce reuse is possible

**Hardware support absence on target devices:**
- MediaTek Helio G85 (Redmi 12): no hardware AES instruction
- Qualcomm Snapdragon 680 (Realme C33): has ARMv8 cryptographic extensions (AES-NI equivalent)
- The inconsistency means IRIS cannot rely on hardware acceleration being present

### Option B: ChaCha20-Poly1305

**Description:** Stream cipher (ChaCha20) combined with universal hash-based MAC (Poly1305). Designed by Daniel J. Bernstein. IETF RFC 8439 (formerly RFC 7539).

**Key size:** 256 bits  
**Nonce size:** 96 bits (12 bytes) — IETF standard; 192 bits for XChaCha20-Poly1305 variant  
**Authentication tag:** 128 bits (16 bytes)  
**IETF standard:** RFC 8439

**Performance (ARM Cortex-A55, software only):**
- ChaCha20-Poly1305 (software): ~200–400 MB/s (ring crate benchmark on ARMv8)
- ChaCha20 uses only 32-bit additions, XOR, and rotations — operations that are equally fast on all modern CPUs including budget ARM SoCs

**Why faster than AES-GCM on software-only ARM:**
- AES-GCM requires the AES block cipher operation, which in software requires 8–14 table lookups per round × 14 rounds for AES-256. Table lookups are cache-timing side-channel sources and are slow without hardware support.
- ChaCha20 uses ARX (Add-Rotate-XOR) operations. No table lookups. No hardware instruction required. Constant-time by construction.
- The performance gap is 3–5× in favor of ChaCha20-Poly1305 on ARM without AES-NI.

**Nonce reuse consideration:**
- Same catastrophic failure mode as GCM if nonces are reused with the same key
- IRIS mitigates by using a new ephemeral X25519 key per session (not per message) — nonces increment monotonically within a session from a counter, not random. Counter nonces do not have a collision probability problem.
- XChaCha20-Poly1305 (192-bit nonce) eliminates random nonce collisions entirely — an alternative for future consideration.

**FIPS status:**
- ChaCha20-Poly1305 is NOT FIPS 140-2/3 approved (as of 2026). FIPS approval is expected in future updates as the algorithm has been widely adopted (TLS 1.3, QUIC, SSH, WireGuard).
- This is a known consequence — see ADR-0002 consequences for the FIPS discussion.

### Option C: XSalsa20-Poly1305

**Description:** An earlier Bernstein design (used by libsodium, Briar). 192-bit nonce.

**Pros:** Wider nonce (192 bits) eliminates nonce collision probability with random nonces; well-analyzed.

**Cons:** Not an IETF RFC standard (libsodium's NaCl standard, not IETF); ChaCha20-Poly1305 (the IETF version) has superseded it; less library support in the Rust ecosystem for production use.

### Option D: AES-128-GCM

**Description:** AES with 128-bit key in GCM mode.

**Pros:** Same performance as AES-256-GCM with a smaller key (128-bit vs 256-bit key has negligible performance difference); FIPS approved.

**Cons:** 128-bit security level — marginally below IRIS's 128-bit target (AES-128 provides 128-bit security for brute force; however, GCM mode has authentication-strength caveats). NIST recommends AES-256 for long-term data protection. Same software performance problem as AES-256-GCM.

---

## Decision

**ChaCha20-Poly1305 (RFC 8439)** as the sole symmetric AEAD cipher for bundle payload encryption in IRIS v1.

AEAD construction:
- Key: 256 bits, derived from X25519 shared secret via HKDF-BLAKE3
- Nonce: 96 bits, monotonically incrementing counter per session (not random per message)
- Associated data: bundle header (source EID, destination EID, bundle ID, timestamp — the fields that must be integrity-protected but not encrypted)
- Tag: 128 bits (appended to ciphertext)

---

## Rationale

1. **Software performance on ARM without AES-NI is 3–5× faster than AES-GCM:** IRIS targets cheap Android devices (Redmi 12, Realme C33) where AES-NI may not be present. ChaCha20-Poly1305's consistent software performance is preferable to AES-GCM's hardware-dependent performance variance.

2. **Constant-time by construction:** ChaCha20's ARX construction has no data-dependent branches or table lookups. It is constant-time on all platforms by design — not by implementation discipline.

3. **IETF RFC standard:** RFC 8439 is a well-specified IETF standard. ChaCha20-Poly1305 is used in TLS 1.3 (RFC 8446), QUIC (RFC 9001), WireGuard, and the Signal Protocol. The algorithm is extensively analyzed.

4. **Nonce management via counter is safe:** Using a monotonically incrementing counter for nonces within a session (with a new X25519 ephemeral key per session) eliminates nonce collision risk without requiring random nonce generation.

5. **ring crate provides production-quality implementation:** Google's `ring` crate (used in Chromium, AWS SDK, Cloudflare Quiche) implements ChaCha20-Poly1305 with constant-time guarantees and extensive testing.

## Consequences

### Positive

- 3–5× faster than AES-GCM on budget Android devices without AES-NI
- Constant-time by construction (no software-only AES timing side-channel risk)
- IETF RFC standard — auditable, well-analyzed, widely reviewed
- Excellent Rust support via `ring` and `chacha20poly1305` (RustCrypto)

### Negative

- **Not AES:** Some enterprise and government security policies require AES-based ciphers. If a specific government procurement mandates AES, IRIS would need to add an AES-256-GCM code path. This is documented as a known gap.
- **Not FIPS 140-2/3 certified (as of 2026):** FIPS compliance issues are shared with the Ed25519 decision (ADR-0002). The same mitigation applies: document the deviation; seek waiver for government deployments; monitor FIPS 140-3 updates (ChaCha20-Poly1305 inclusion is expected).
- **Less familiar to security auditors:** Security auditors (CERT-In empanelled firms, STQC assessors) may be less familiar with ChaCha20-Poly1305 than AES-GCM. IRIS must provide clear documentation and references for auditors.

### ⚠️ Open Architecture Issues Requiring Resolution Before Implementation

**Issue 1: Per-session vs per-message ephemeral key inconsistency.**
This ADR states "new ephemeral X25519 key per session." `MESSAGE_ENVELOPE.md` shows a per-message ephemeral public key in the encryption header. These are materially different designs with different security properties. **This contradiction must be resolved by the cryptographic architecture review before any E2EE implementation begins.** Per-message ephemeral keys provide better forward secrecy for the sender but increase overhead; per-session keys reduce overhead but require session state management.

**Issue 2: "HKDF-BLAKE3" is a non-standard construction.**
HKDF (RFC 5869) is defined over HMAC, which in turn is defined over a hash function. HMAC-BLAKE3 is not a standardized construction. Options: (a) use HKDF-SHA256 (standard, well-analyzed), (b) use BLAKE3's native key derivation API (which is a proper KDF but not HKDF), or (c) use BLAKE3-HKDF carefully documented. **Requires cryptographic architecture decision before implementation.**

**Issue 3: Forward secrecy properties.**
The current construction — ephemeral sender X25519 + static recipient X25519 — is an ECIES-like scheme. This provides: sender authentication (via Ed25519 signature), confidentiality against passive eavesdroppers, but does NOT provide forward secrecy against recipient key compromise. If the recipient's long-term X25519 private key is later compromised, and an attacker has recorded the ciphertexts and ephemeral public keys (which are in the cleartext envelope header), the attacker can recover all past plaintext messages. The documentation must not claim forward secrecy properties that this construction does not provide. True forward secrecy for the recipient requires ephemeral recipient keys (e.g., Signal-style prekeys or a Noise Protocol Framework handshake). This is a known limitation, not a bug — but it must be accurately documented and the security model must reflect it.

### Neutral

- Both AES-GCM and ChaCha20-Poly1305 provide 256-bit key / 128-bit authentication tag security. The security level is identical.
- Future migration to XChaCha20-Poly1305 (192-bit nonce) is straightforward if random nonces are desired.

## Implementation Notes

- Crate: `ring` (aead::ChaCha20Poly1305) for production; `chacha20poly1305` (RustCrypto) for `no_std` embedded targets
- HKDF: `ring::hkdf` with BLAKE3 as the hash (HKDF-BLAKE3); info parameter includes session ID and direction (sender→receiver vs receiver→sender) to derive separate keys for each direction
- Nonce: `u96` counter stored in session state; starts at 0 for each new session; monotonically increments; never reset
- Associated data: serialized bundle header fields (fixed-length fields for efficient AEAD computation)
- Module: `crates/iris-core/src/crypto/aead.rs`
