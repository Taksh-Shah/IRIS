# RED-0001 — Transport Layer Adversarial Review

- **Record ID**: RED-0001
- **Title**: Transport Layer Adversarial Review (internet.rs, manager.rs, ble.rs, simulated.rs, mod.rs, message.rs, error.rs)
- **Date**: 2026-08-13
- **Agent**: redteam
- **Scope**: Rust transport layer just implemented in `crates/iris-core/src/transport/`
- **Method**: Adversarial source review — 8 targeted probes, adversarial threat categories (blackhole, tamper, replay, sybil, eavesdropping, battery exhaustion, broadcast storm)
- **Status**: PARTIAL — CRITICALs + primary HIGHs mitigated 2026-08-13 (see Remediation below); MEDIUM/LOW + reconnect loop remain OPEN

---

## Executive Summary

The transport layer is a solid scaffold — framing is bounded, backoff is
jittered and capped, the manager score function is pure — but the review found
**2 CRITICAL, 6 HIGH, 5 MEDIUM, 2 LOW** issues. The two critical findings share
a root cause: **the transport treats "the relay" as a single implicit peer and
never binds a TCP connection to the logical `PeerId` it was opened for**. In a
cattle-network where relays are hostile or misconfigured, this produces
cross-peer misrouting, ack-without-delivery blackholes, and fully
unauthenticated message injection.

The emergency-path finding (RED-0001-03) is the most damaging to the product's
core promise: a P0/P1 emergency message can be silently dropped with **zero**
transports selected.

## Detailed Findings

### RED-0001-01 — CRITICAL — Cross-peer relay hijack / misrouting

- **File**: `crates/iris-core/src/transport/internet.rs:215-244`, `334-360`
- **Scenario**: Two logical peers P1 and P2 are reachable via two different
  relays R1 and R2. Application calls `connect(P1)` (relay R1) then
  `connect(P2)` (relay R2).
- **Preconditions**: More than one relay candidate exists, or topology has
  multiple peers on different relays. Both `connect()` calls park their
  connection into the **same** `ConnectionPool`.
- **Attack**:
  1. `send(&P1, msg)` builds `PeerInfo { addresses: Vec::new(), .. }`
     (`internet.rs:342-347`) — the caller's addresses are **never** passed
     through on the send path.
  2. `get_connection()` therefore resolves the target address as
     `peer.addresses.first()` (None) → `relay_addr` (last
     `connect()`, which is **R2**) → `relay_candidates.first()`.
  3. Even if the address resolved correctly, `pool.acquire()` (`internet.rs:113-116`)
     returns the **first non-expired pooled connection regardless of its
     destination address**. A connection opened to R1 can be handed to a send
     destined for R2.
- **Impact**: Message meant for P1 is transmitted to R2 (an arbitrary third
  party = confidentiality breach), or to a relay that has no route to P1
  (blackhole + receipt reported as success). In a cattle network where relays
  are untrusted, an attacker who operates R2 silently receives every message
  the app *thinks* it sent to P1. This is the single most severe flaw: the
  pool and send path validate **nothing**.
- **Likelihood**: HIGH (normal multi-relay usage triggers it, no adversarial
  action required)
- **Severity**: CRITICAL
- **Mitigation**:
  - Key the pool by `SocketAddr`; `acquire(addr)` only returns connections
    opened to that exact address. Reject/evict mismatched entries.
  - Store a `peer_id → SocketAddr` mapping at `connect()` and look it up in
    `send()`; never fall back to "any relay".
  - Return `TransportError::PeerNotFound` when the target peer has no
    established relay mapping instead of silently reusing another relay.
- **Status**: RESOLVED (2026-08-13) — per-peer `peer_relays` map + pool keyed by `SocketAddr`

### RED-0001-02 — CRITICAL — Silent blackhole + zombie `Connected`, no reader timeout

- **File**: `crates/iris-core/src/transport/internet.rs:226-244`, `250-268`, `339-359`
- **Scenario**: A malicious relay accepts our TCP connection, then resets it
  or stalls. The app keeps "sending" successfully.
- **Preconditions**: Relay lifetime > connection lifetime; TCP half-dead
  states (remote FIN/RST arrives, or remote stops reading).
- **Attack**:
  1. Relay RST/close after we parked the connection in the pool.
  2. `send()` → `get_connection()` → `pool.acquire()` returns the stale write
     half (**no liveness check** — `acquire` only checks idle time, not socket
     state).
  3. `write_all()` on a dead TCP socket frequently succeeds locally (kernel
     buffer accepts data before RST is observed); `flush()` may also succeed.
     `send()` returns `Ok(SendReceipt)` — the message is vaporized.
  4. State remains `Connected` **forever**: nothing in
     `spawn_reader`/`get_connection`/`send` transitions state on read failure.
     A dead relay becomes a permanent "best transport" (40 pts base score) that
     blackholes every message.
  5. Variant — slowloris pin: `spawn_reader` (`internet.rs:256`) allocates
     `vec![0u8; len]` (up to 1 MiB) **before** reading the payload. A relay
     that sends a valid 4-byte header declaring 1 MiB and then stalls holds
     1 MiB + a reader task indefinitely. There is **no read timeout anywhere**
     on the reader path. N concurrent stalled relay connections → N MiB pinned,
     reader tasks never die.
- **Impact**: Total silent loss of unicast traffic to a "connected" relay —
  the canonical blackhole attack, made trivially effective by the absence of
  liveness detection and read timeouts. Memory DoS scales with connection
  count. For a disaster-relief fabric this defeats the core promise.
- **Likelihood**: HIGH (trivial for a hostile relay; also occurs naturally on
  flaky Indian cellular links)
- **Severity**: CRITICAL
- **Mitigation**:
  - Add a read deadline around `read_exact` (e.g. 15-30 s keepalive/per-frame);
    on timeout or EOF, evict the connection from the pool **and** transition
    state to `Degraded`/`Unavailable`, then surface a state event.
  - `send()` should detect write failure and (a) evict the stale pooled
    connection, (b) return `Io`/`ConnectionFailed` rather than `Ok`.
  - Cap concurrent connections with the same peer (pool already caps at 3 but a
    stalled reader never releases its slot); consider a semaphore over in-flight
    byte budget.
- **Status**: PARTIAL (2026-08-13) — read timeouts, state→Available on link loss, send→Degraded on write failure landed; capped reconnect loop still pending

### RED-0001-03 — HIGH — Emergency (P0/P1) messages silently get ZERO transports

- **File**: `crates/iris-core/src/transport/manager.rs:151-157`, `194-196`
- **Scenario**: A large emergency payload (>10 KB, e.g. mass-casualty photo)
  is sent while the only connected transport reports
  `bandwidth_available_bps = 0` (Degraded link, model bug, or transport
  reporting 0).
- **Preconditions**: `req.message_size > 10_000` and a candidate transport's
  `cost.bandwidth_available_bps == 0`.
- **Attack**:
  1. `score_transport` computes `(0.0f32).log2() * 5.0 = -inf`
     (`manager.rs:195`). Any finite base score plus `-inf` is `-inf`.
  2. Emergency multipath path: `candidates.retain(|c| c.score > 0.0)`
     (`manager.rs:154`) — the `-inf` transport is filtered out.
  3. If all viable transports score `-inf`, the selection is **empty**. The
     routing layer receives an empty list; depending on caller behavior this
     means the P0/P1 message is dropped with no error surfaced. The one class
     of message the product guarantees ("ALL transports, multipath, never
     dropped") is the one that can silently starve.
  4. Non-emergency path is also wrong: `truncate(1)` keeps the `-inf`
     candidate as "best" and routes a large message onto a zero-bandwidth
     transport → guaranteed loss.
- **Impact**: Emergency messaging failure — the highest-impact availability
  failure mode in the product charter. Secondary: permanent mis-selection of
  zero-bandwidth transports for large bulk sends.
- **Likelihood**: MEDIUM (requires a transport reporting 0 bps; plausible in
  `Degraded` state or with a broken cost model)
- **Severity**: HIGH
- **Mitigation**:
  - Clamp the bandwidth bonus: `score += (bandwidth.max(1) as f32).log2() * 5.0`
    or use `if bandwidth > 0` guard.
  - Never let selection silently yield empty for emergencies: if the filtered
    set is empty but candidates existed, keep the best candidate or return an
    explicit error (`TransportError::Busy`/new `NoTransport`) so the routing
    layer retries/reduces size instead of dropping.
  - Add a unit test: P0, msg 20 KB, one Connected transport with bw=0 → must
    select something or error, never empty.
- **Status**: RESOLVED (2026-08-13) — `bandwidth.max(1)` clamp in score; log2 never −inf

### RED-0001-04 — HIGH — `sort_by` panics on NaN score

- **File**: `crates/iris-core/src/transport/manager.rs:151`
- **Scenario**: Any score evaluates to `NaN` (e.g. `monetary_cost_per_kb` fed
  as NaN from a relay pricing feed, `congestion_level = NaN`, or overflow
  `inf - inf` in the score arithmetic).
- **Preconditions**: NaN enters `TransportCost` fields; nothing validates
  inputs to `score_transport`.
- **Attack**:
  1. A cost snapshot with NaN flows into `score_transport`.
  2. `f32::partial_cmp` returns `None` for NaN operands.
  3. `.unwrap()` on `None` → **panic** inside `select_transports`.
- **Impact**: The panic aborts the selection future; every caller (routing
  engine send path, including P0/P1) is wedged until the task is restarted;
  in a single-threaded runtime the whole node can crash. An attacker able to
  influence cost inputs (relay pricing, congestion telemetry) can remotely
  crash transport selection.
- **Likelihood**: LOW-MEDIUM (requires non-finite inputs)
- **Severity**: HIGH (crash with attacker-influenceable precondition)
- **Mitigation**:
  - Use `total_cmp` (stable, total order, never `None`) instead of
    `partial_cmp().unwrap()`.
  - Sanitize `TransportCost` inputs at the boundary (`is_finite()` checks).
  - Fall back to `transport_id` as tiebreak for determinism.
- **Status**: RESOLVED (2026-08-13) — `total_cmp` replaces `partial_cmp().unwrap()`

### RED-0001-05 — HIGH — Single crafted frame kills the relay link; no read timeout

- **File**: `crates/iris-core/src/transport/internet.rs:152-163`, `250-268`
- **Scenario**: Malicious relay sends a 4-byte header with
  `payload_len > MAX_FRAME_BYTES` (e.g. `0xFFFFFFFF`) or truncates a frame.
- **Preconditions**: Attacker controls the relay endpoint (cattle assumption).
- **Attack**:
  1. `frame_payload_len` returns `None` for an oversized header
     (`internet.rs:159-161`); `spawn_reader` treats it as fatal and `break`s
     (`internet.rs:255`) — dropping the entire connection.
  2. The pool still holds the (now dead) write half; the next `send()` writes
     into the void and reports success → blackhole (RED-0001-02 loop).
  3. Truncated payload (header fine, then fewer bytes than declared then EOF):
     `read_exact` on payload fails, connection dropped. Same consequence.
  4. Repeatedly re-opening: our only recovery is `send()` → pooled dead write →
     error on next write → **no reconnect path exists in `send()`** — there is
     no retry/backoff logic invoked on the send path at all. Backoff exists
     (`backoff_ms`) but nothing in the code calls it.
- **Impact**: A one-shot crafted frame permanently disables a relay path until
  an explicit `connect()` is reissued; combined with the zombie state, the
  transport keeps reporting `Connected` and keeps being selected. Protocol DoS
  with attacker effort of 4 bytes.
- **Likelihood**: HIGH (trivial for a hostile relay)
- **Severity**: HIGH
- **Mitigation**:
  - On framing error, distinguish "oversized" (protocol violation → emit
    `TransportError::Protocol`, evict from pool, transition state) from
    "truncated/EOF" (connection lost → evict + state change), and notify the
    manager via state event.
  - Add reader read-timeout and a capped reconnect loop using `backoff_ms`
    in `send()`.
- **Status**: PARTIAL (2026-08-13) — 10 s per-read timeout + state transition on reader exit landed; reconnect loop pending

### RED-0001-06 — HIGH — BLE poller task leak; `shutdown()` doesn't cancel; battery violation

- **File**: `crates/iris-core/src/transport/ble.rs:304-322`, `372-376`
- **Scenario**: Repeated `connect()` calls (peer churn in a mesh) and
  `shutdown()` then re-register (hot-plug).
- **Preconditions**: `BleTransport` in use with any adapter.
- **Attack**:
  1. Every `connect()` spawns a **new** infinite `tokio::spawn` polling loop
     (`ble.rs:304-322`). No `JoinHandle` is stored; nothing ever cancels it.
  2. `connect(P1)` then `connect(P2)` → **two** loops both drain the same
     adapter queue via `incoming_gatt_writes()`. Events are consumed by the
     first loop; the second gets nothing; whichever drains first "steals" the
     message — delivery becomes nondeterministic, and events can be silently
     lost.
  3. `shutdown()` (`ble.rs:372-376`) only calls `disconnect_gatt`; the poller
     loop keeps running — polling an adapter that may now be detached, forever
     waking 20×/s (50 ms sleep). The transport is `Unavailable` but still burns
     CPU/wakelocks.
  4. Battery: a 50 ms busy-poll loop (20 wakeups/sec × task wake + mutex +
     drain) far exceeds the modeled `estimated_battery_ma: 3.0`
     (`ble.rs:361`, `mod.rs:203 BLE_COST.connected_idle_ma`) and violates the
     project's ≤5%/h power budget for a connected mesh node.
- **Impact**: Task/thread growth per connect; lost inbound BLE messages;
  shutdown that does not shut down; battery exhaustion on the exact transport
  class (BLE) intended for low-power always-on mesh participation.
- **Likelihood**: HIGH on any multi-connect usage
- **Severity**: HIGH
- **Mitigation**:
  - Store `JoinHandle`; on `connect()` abort the previous poller before
    spawning a new one; on `shutdown()` abort it.
  - Replace polling with a callback/notify channel (real Android/iOS adapters
    provide notify); keep a single poller per transport, not per connect.
  - Verify the polling interval against the battery budget; 50 ms is not
    viable for an always-on path.
- **Status**: RESOLVED (2026-08-13) — poller AbortHandle stored; `connect()` aborts prior poller; `shutdown()` aborts it

### RED-0001-07 — HIGH — BLE `send()` uses hardcoded `GattHandle(1)`

- **File**: `crates/iris-core/src/transport/ble.rs:339-343`
- **Scenario**: Two peers A and B connected (the codebase allows concurrent
  GATT connections; `connect()` returns a handle that is discarded).
- **Preconditions**: More than one connected peer.
- **Attack**:
  1. `connect(A)` → `connect_gatt(A)` returns `GattHandle(1)`, handle
     discarded (`ble.rs:296`).
  2. `connect(B)` → new handle (also likely `1` in the simulated adapter
     `ble.rs:152-154`, always returns `GattHandle(1)`!).
  3. `send(&A, msg)` hardcodes `GattHandle(1)` + control UUID
     (`ble.rs:339-340`) — writes to whichever connection the adapter mapped to
     handle 1. With the simulated adapter, sends to A and B are
     indistinguishable; with a real adapter, message for A can be written to
     B's GATT link → cross-peer leakage.
- **Impact**: Confidentiality violation between peers; routing layer believes
  P2P unicast semantics while the transport delivers to the wrong peer.
- **Likelihood**: HIGH once multi-peer BLE is enabled (scaffold currently
  masks it because the simulated adapter returns a constant handle)
- **Severity**: HIGH
- **Mitigation**: Maintain `peer_id → GattHandle` map populated by
  `connect()`; `send()` looks up the handle for `peer`. Return
  `PeerNotFound`/`NotConnected` when no mapping exists.
- **Status**: RESOLVED (2026-08-13) — `gatt_handle` stored at connect, used by `send()`, cleared at shutdown

### RED-0001-08 — HIGH — `IncomingMessage.peer_id` hardcoded to zeros

- **File**: `crates/iris-core/src/transport/internet.rs:260-265`, `ble.rs:314-319`
- **Scenario**: Malicious relay sends arbitrary framed payloads; or normal
  operation on any relay.
- **Preconditions**: Consumer layers (routing, dedup, ACL) read
  `IncomingMessage.peer_id`.
- **Attack**:
  1. The reader emits every received frame with
     `peer_id: PeerId([0u8; 32])` — a *valid* PeerId value that means "null".
  2. Routing/dedup layers keying on `peer_id` cannot distinguish "message from
     P1" vs "message from P2" vs "forged frame from the relay" — all collapse
     to the null peer. Responses/acks for null peer are misdelivered or
     dropped; per-peer ACLs (if any trust this field) are bypassed
     trivially.
  3. Because the framing carries **no peer identity and no authentication**,
     any node that can open a TCP connection to us (i.e. the relay, per
     INTERNET-001) can inject frames that the protocol layer will attribute
     however it handles the null peer — full message injection with zero
     effort.
- **Impact**: Spoofing/misattribution at the protocol layer; poisoning of
  dedup state (attacker reuses `message_id` with different payloads); broken
  unicast routing semantics (every inbound message looks like it came from the
  same peer). This is the transport-level precondition for most routing-layer
  attacks.
- **Likelihood**: HIGH (occurs in every inbound message today)
- **Severity**: HIGH
- **Mitigation**:
  - Bind the reader task to the `PeerId` of the connection's target *at
    `connect()` time* (closure capture) so relay-delivered messages are
    attributed to the connected peer, not zeros.
  - Protocol layer must authenticate senders (signature/MAC over the payload)
    before trusting `peer_id`; add a header field carrying explicit source
    PeerId + signature rather than relying on transport attribution.
- **Status**: PARTIAL (2026-08-13) — reader attributes inbound frames to the connected peer; protocol-layer authentication pending CRYPTO-001

### RED-0001-09 — MEDIUM — `broadcast_stream` silently drops state events on Lagged

- **File**: `crates/iris-core/src/transport/mod.rs:271-283`
- **Scenario**: Routing engine subscriber is slow (busy routing table
  rebuild), transport transitions `Connected → Unavailable` during the stall.
- **Preconditions**: Subscriber not polled for > 64 state events (state_tx
  capacity) — realistic under bursty state flapping on flaky links.
- **Attack**: `Err(Lagged(_))` → `continue` (`mod.rs:278`) — the state change
  is silently swallowed. The routing engine keeps its last-known
  `Connected` state and keeps selecting this transport for P0/P1 sends → every
  emergency message routed into a dead link (blackhole, ack-without-delivery).
- **Impact**: Diverged state between transport and routing; emergency-path
  failure driven purely by subscriber slowness.
- **Likelihood**: MEDIUM
- **Severity**: MEDIUM
- **Mitigation**:
  - On `Lagged`, emit a synthetic "state resync" event carrying the current
    `state()` snapshot (or use a `watch` channel for state, which preserves
    latest value by design).
  - Increase `state_tx` capacity and/or guarantee ordering of terminal states.
- **Status**: OPEN

### RED-0001-10 — MEDIUM — Forwarder task leak on duplicate registration

- **File**: `crates/iris-core/src/transport/manager.rs:87-101`
- **Scenario**: Hot-plug re-registration: register → deregister → register
  same id.
- **Preconditions**: `register()` called twice with the same id while the
  first transport is still alive (Arc held elsewhere, e.g. via `get()`).
- **Attack**: The state-forwarder `tokio::spawn` happens **before** the
  duplicate check (`manager.rs:87-94` vs `96-99`). On `DuplicateId` the task
  is leaked: it holds an `Arc<dyn Transport>` and streams forever because the
  broadcast sender never closes (transport still alive). Repeated attempts
  accumulate tasks.
- **Impact**: Task + memory leak per failed register; registry growth over
  hot-plug cycles.
- **Likelihood**: LOW-MEDIUM
- **Severity**: MEDIUM
- **Mitigation**: Check for duplicate **before** spawning; or store the
  `JoinHandle` and abort it on the error path.
- **Status**: OPEN

### RED-0001-11 — MEDIUM — `encode_frame` panic on oversized payload

- **File**: `crates/iris-core/src/transport/internet.rs:142-149`
- **Scenario**: Any caller passes a `SerializedMessage` with
  `payload.len() > 1 MiB` (bypassing manager size filter, e.g. routing layer
  assembling its own frame, or a bug).
- **Preconditions**: Payload > `MAX_FRAME_BYTES`.
- **Attack**: `assert!(len <= MAX_FRAME_BYTES)` fires → panic inside the
  `send()` future. Tokio catches it as a task panic, but the caller's future
  never completes and any state cleanup (pool release) is skipped — the pooled
  connection is leaked (write half dropped mid-flight).
- **Impact**: Panic-in-input-path; unrecoverable for the calling task.
- **Likelihood**: LOW-MEDIUM
- **Severity**: MEDIUM
- **Mitigation**: Return `Err(TransportError::Protocol("frame exceeds max"))`
  (or a `MessageTooLarge` variant) instead of asserting; keep `debug_assert!`
  for tests only.
- **Status**: OPEN

### RED-0001-12 — MEDIUM — Pool mutex held across network connect → lock convoy

- **File**: `crates/iris-core/src/transport/internet.rs:226-238`
- **Scenario**: Multiple relays down (natural in disaster scenario); app sends
  to several peers.
- **Preconditions**: More than one concurrent `send()` needing a fresh
  connection.
- **Attack**: `get_connection` holds `pool` lock while awaiting
  `TcpStream::connect` with a 3 s timeout. All other senders/connect/shutdown
  calls block on `pool.lock().await` until the connect completes or times out
  — serialized head-of-line blocking. With a few dead relays, every send
  stalls seconds; throughput collapses exactly when the network is worst.
- **Impact**: Availability degradation; attacker pointing peers at dead relays
  amplifies the convoy.
- **Likelihood**: MEDIUM
- **Severity**: MEDIUM
- **Mitigation**: Split the lock: reserve a slot under a short lock, perform
  the connect outside it (e.g. per-entry `Mutex<Option<OwnedWriteHalf>>` or
  `async` slot), then insert on completion.
- **Status**: OPEN

### RED-0001-13 — MEDIUM — Failed `connect()` leaves state stuck in `Connecting`

- **File**: `crates/iris-core/src/transport/internet.rs:315-332` (+ manager.rs:140 filter)
- **Scenario**: `connect()` to a dead relay fails (`get_connection` → error).
- **Preconditions**: Relay unreachable.
- **Attack**: `set_state(Connecting)` at `internet.rs:316`; on any error return
  the state is never restored to `Available`. The transport stays `Connecting`
  (discriminant 2) indefinitely — and `Connecting >= Available`, so
  `select_transports` still considers it a candidate (`manager.rs:140`),
  scoring it `-1000` via the `_ =>` arm (`manager.rs:179`). Single-path
  selection keeps returning it as the "best" only if it is the sole candidate,
  and after a successful connect elsewhere the stale state lingers until the
  next connect/shutdown.
- **Impact**: Selection sees zombie-Connecting transport; repeated failed
  connects never recover state automatically.
- **Likelihood**: MEDIUM (any failed connect)
- **Severity**: MEDIUM
- **Mitigation**: On connect failure, restore prior state (or `Available`)
  before returning the error; add a state transition guard so `Connecting` is
  never observable on the error path.
- **Status**: RESOLVED (2026-08-13) — `connect()` restores `Available` on all error paths

### RED-0001-14 — LOW — `priority_hint` is write-only dead code

- **File**: `crates/iris-core/src/transport/internet.rs:175`, `380-382`
- **Scenario**: Routing engine calls `set_send_priority_hint(P0)` expecting
  QoS/urgency behavior.
- **Preconditions**: Any caller of the trait method.
- **Attack/Impact**: The `AtomicU8` is written (`Ordering::Release`) and
  **never read anywhere** (verified by grep — no consumer in the crate). The
  P0 "never dropped / urgent" guarantee is not enforced by the internet
  transport at all; the method silently misleads callers into believing
  priority affects the send path.
- **Likelihood**: HIGH (always true)
- **Severity**: LOW
- **Mitigation**: Either wire the hint into send-path behavior (e.g. skip
  pool-wait, no backoff on retry, direct connection priority) or remove the
  method/field and document that priority does not affect this transport yet.
- **Status**: OPEN

### RED-0001-15 — LOW — Simulated transport unbounded task spawn

- **File**: `crates/iris-core/src/transport/simulated.rs:190-198`
- **Scenario**: A flood of `send()` calls (broadcast storm simulation, or a
  test feeding N messages).
- **Preconditions**: `send()` called faster than latency.
- **Attack/Impact**: Each non-lost send spawns a task holding a full clone of
  the payload. N sends → N tasks + N×payload memory momentarily. In
  simulation/lab only, but it can OOM a test harness or a sim-mode node during
  a storm test, which is exactly when sims are used.
- **Likelihood**: HIGH in sim mode by design
- **Severity**: LOW
- **Mitigation**: Bound in-flight sends (semaphore) or use a single delayed
  delivery loop with a bounded queue.
- **Status**: OPEN

   transport ranking.
6. **RED-0001-06 + RED-0001-07 (HIGH)** — BLE: single cancellable poller,

## Explicitly Reviewed and NOT Flagged

- **Lock ordering (probe 2c)**: `relay_addr` and `pool` are never acquired
  nested — all paths acquire sequentially; no deadlock found. (Convoy issue
  flagged separately as RED-0001-12.)
- **`latency + 1` (probe 3a)**: `100.0 / (typical_latency_ms as f32 + 1.0)` is
  safe — denominator minimum 1.0.
- **Broadcast channel memory (probe 4b)**: `tokio::sync::broadcast` is bounded;
  a slow subscriber does not grow memory — it lags, which is the actual bug
  (RED-0001-09). Per-subscriber payload cloning is noted as amplification but
  not a standalone finding.
- **Backoff (probe 2 related)**: `backoff_ms` is capped (30 s) and jittered
  (±25%); bounds verified against its own tests. Not a vuln — but note the
  backoff function is **never called on any live path** (only unit-tested);
  reconnection logic is absent from `send()` (folded into RED-0001-02/05).
