# RES-0032 — Tier-5 relay protocol and TLS implementation

**Date:** 2026-09-07  
**Node:** INTERNET-001  
**Maturity:** L1 — implementation-backing research; protocol/server and hardware evidence remain open

## Evidence

- Rustls 0.23 requires explicit certificate verification configuration and
  documents safe builder defaults: https://docs.rs/rustls/latest/rustls/struct.ConfigBuilder.html
- tokio-rustls provides `TlsConnector::connect(ServerName, stream)` for async
  TLS over Tokio I/O: https://docs.rs/tokio-rustls/latest/tokio_rustls/client/struct.TlsConnector.html
- RFC 8446 defines TLS 1.3 as the authenticated confidentiality/integrity layer
  while leaving application routing semantics to the application:
  https://www.rfc-editor.org/rfc/rfc8446.html

## Decision

Keep the IRIS envelope end-to-end encrypted and add a bounded outer relay
envelope carrying protocol version, message kind, source/target `PeerId`, and
opaque payload. Validate fixed fields and lengths before allocation. Add TLS as
a verified socket layer; test-only self-signed certificates must never be the
production default. Implement and test the pure codec before networking, then
integrate relay sockets and Android NSD. Do not claim Tier-5 acceptance until
the real LAN and relay paths are exercised.

## Rejected

- Routing by decrypting the IRIS envelope: the relay must not need message keys.
- Disabling certificate verification: it would make socket tests meaningless.
- A second Kotlin transport implementation: Rust remains owner of framing and
  retry policy per `INTERNET_ANDROID_DESIGN.md`.
