## 1. Q1 — API floors + deprecation status through API 36 / Android 16 (and 17)

- `android.net.wifi.aware` **added API level 26 (Android 8.0)**; the package-summary reference was still current as of 2026-03-26 with full class surface (`WifiAwareManager`, `WifiAwareSession`, `PublishConfig/SubscribeConfig`, `WifiAwareNetworkSpecifier`, `WifiAwareNetworkInfo`, `WifiAwareChannelInfo`, `AwareDataPathRequest`, `AwarePairingConfig`, `WifiAwareDataPathSecurityConfig`, `Characteristics`, `AwareResources`). **No deprecation** of NAN. [Level 1, https://developer.android.com/reference/android/net/wifi/aware/package-summary]
- Wi-Fi Aware = Neighbor Awareness Networking (NAN); forms clusters, managed by the Wi-Fi Aware system service; apps don't control clustering. Discovery = publish/subscribe; data path = NDP (bi-directional, no AP). [Level 1, https://developer.android.com/develop/connectivity/wifi/wifi-aware]
- **Android 16 / 17 support**: AOSP Wi-Fi Aware HAL surface present in `hardware/interfaces/wifi/1.2` referenced from `android16-release`; `source.android.com` Wi-Fi Aware doc (updated 2026-07-22) references `android17-release` for the legacy `wifi_nan.h`; a dedicated **"Wi-Fi Aware Architecture" external doc exists for Android 17+** mitigating firmware-centric limitations in Android 16 and lower. NAN is a strategic Android feature, not a legacy one. [Level 1, https://source.android.com/docs/core/connect/wifi-aware; https://android.googlesource.com/platform/hardware/interfaces/+/android16-release/wifi/1.2/README-NAN.md; https://source.android.com/docs/core/connect/wifi-aware-architecture.pdf]
- **Permissions** (initial setup): `ACCESS_WIFI_STATE`, `CHANGE_WIFI_STATE`, `CHANGE_NETWORK_STATE`, `INTERNET`, `NEARBY_WIFI_DEVICES` (with `neverForLocation` flag), and `ACCESS_FINE_LOCATION` with `maxSdkVersion="32"` (pre-33 requires fine location for discovery). Runtime feature check: `PackageManager.FEATURE_WIFI_AWARE`/`hasSystemFeature`; runtime availability check: `WifiAwareManager.isAvailable()` + `ACTION_WIFI_AWARE_STATE_CHANGED` broadcast — availability can change at any time (Wi-Fi or Location disabled; some devices also lack support when Wi-Fi Direct / SoftAP / tethering is in use). [Level 1, https://developer.android.com/develop/connectivity/wifi/wifi-aware]
- **Options/limitations**: `Characteristics` exposes `getMaxServiceSpecificInfoLength()` (discovery service info) and mounted counts (`getNumberOfSupportedDataPaths/DataInterfaces/PublishSessions/SubscribeSessions`), NAN resource counts (`getAvailableAwareResources()`), and capability flags. Enforce these at runtime via `AttachCallback.onAttached(Characteristics)`. [Level 1, developer.android.com Characteristics/WifiAwareManager]
- **Manufacturer/firmware gating is real**: API 26+ is the platform floor, but the OEM must enable NAN at firmware/HAL level (`WIFI_HIDL_FEATURE_AWARE` + `android.hardware.wifi.aware.xml`), so `FEATURE_WIFI_AWARE` runtime check is mandatory — a device running Android can still lack NAN. [Level 1, source.android.com wifi-aware Implementation; Level 5, https://github.com/getditto/wifi-aware-checker]

## 2. Q2 — NDP security types + transfer control

- **Data-path security config**: `WifiAwareNetworkSpecifier.Builder.setPskPassphrase(String)` (PSK) or `setDataPathSecurityConfig(WifiAwareDataPathSecurityConfig)`; `WifiAwareDataPathSecurityConfig.Builder` carries the peer-passphrase / certificate material. [Level 1, developer.android.com wifi-aware overview; MS Learn net-android-35]
- **NCS cipher suites** (`Characteristics.getSupportedCipherSuites()`): `WIFI_AWARE_CIPHER_SUITE_NCS_SK_128` (API 30), `NCS_SK_256` (API 30), `NCS_PK_128` (API 33), `NCS_PK_256` (API 33), `NCS_PK_PASN_128/256` (API 34), `NCS_NONE` = open (API 33). "The device automatically picks the strongest cipher suite when initiating a data-path setup." **Open (`NONE`) is an explicit opt-in**, not implicit. [Level 1, developer.android.com Characteristics]
- **Aware Pairing (API 34+)**: `isAwarePairingSupported()` if WFA Wi-Fi Aware spec 4.0 features are present — NAN Pairing with NIK caching, NDP unicast frame encryption (§7.3.1), group-addressed frame encryption (§7.3.3), management-frame protection (§7.3.2), beacon integrity protection (§7.3.4). `getPairedDevices()` lists paired peers. [Level 1, developer.android.com WifiAwareManager + Characteristics + AwarePairingConfig]
- Vendor corroboration: Realtek Wi-Fi NAN supports "WPA2 encryption … for data path security", "protection of multicast data frames and management frames using GTK / IGTK", "beacon protection using BIGTK". [Level 3, https://aiot.realmcu.com/en/latest/rtos/nan/index.html]
- **Transfer control / connection setup**: after discovery the *publisher* runs a `ServerSocket`, requests a NAN network via `ConnectivityManager.requestNetwork` with `NetworkCapabilities.TRANSPORT_WIFI_AWARE` + `WifiAwareNetworkSpecifier` (discovery session + `PeerHandle` + optional port); subscriber requests the same (no port) and learns the publisher's `WifiAwareNetworkInfo.peerIpv6Addr` + `port` from `onCapabilitiesChanged(NetworkCapabilities)`, then opens a socket. Android 12+ simplifies datapath bringup: the responder can accept any peer (no initiator MAC upfront), speeding NDP setup and enabling multiple point-to-point links with one network request. [Level 1, https://developer.android.com/develop/connectivity/wifi/wifi-aware]
- **Design decision**: IRIS already signs+encrypts the app-layer envelope (CRYPTO-001/IDENT-001/SEC-001). NDP-level crypto (PSK or PASN) would add a device-pairing step that complicates large-field onboarding with no identity benefit; keep NDP **open at L2** and treat the platform's randomized-NMI/NDP MAC + OS patches as the L2 perimeter — the security boundary stays in the envelope (consistent with R5/R8 posture). [Level 4, internal SEC-001/IDENT-001/CRYPTO-001 evidence]

## 3. Q3 — 6 GHz / Wi-Fi 6E NAN + U-NII channel plan

- No authoritative, NAN-specific 6 GHz channel-plan primary source surfaced — recorded **Gap G-WA-3** (treat 6 GHz NAN as hardware/firmware/region dependent; design on 2.4/5 GHz).
- Parallel Wi-Fi 6E (802.11ax over 6 GHz) results show the 6 GHz pipe is genuinely faster and uncontended: Excentis live test (160 MHz, 2-stream client, 2.5 Gbps test endpoint) — 6E coverage slightly below 5 GHz but clean spectrum; highspeedinternet benchmarks (Pixel 6 / Wi-Fi 6E, 160 MHz): ~1963 Mbps @10 ft, ~1719 Mbps @30 ft, ~617 Mbps @120 ft; same hardware on 5 GHz lower. [Level 3, https://www.excentis.com/blog/blog-6/we-tested-wi-fi-6-versus-wi-fi-6e-here-are-the-results-75; https://www.highspeedinternet.com/resources/wi-fi-7-tested-benchmarks]
- Implication for the abstraction matrix: "~300 Mbps peak" is a conservative *usable* planning figure; the *capable* data path is Wi-Fi-speed (up to ~1.8 Gbps over 6 GHz close range on capable NICs). Keep the matrix's conservative practical numbers for routing/resource planning; do not gate design on 6 GHz. 6 GHz regulatory availability (e.g., India) must be checked at runtime via capability/feature, not assumed. [Level 1/3 synthesis]

## 4. Q4 — NDP MTU/throughput + max_message_size for TransportCapabilities

- **NDP is a routable network interface** over which IRIS opens standard IPv6 `Socket`/`ServerSocket`; MTU is kernel-managed and no authoritative public value was found (**Gap G-WA-1**). Application layer sees a socket; therefore `TransportCapabilities.max_message_size` should reflect the *framing* cap rather than any discovered NDP MTU — reuse INTERNET-001's 1 MiB cap; the engine's fragmentation layer already handles large ADUs below the cap and across-transport. [Level 1 socket path, developer.android.com wifi-aware overview; Level 4 INTERNET-001]
- Discovery channel sizing is separate: native Aware `sendMessage` payload and `setMatchFilter`/`setServiceSpecificInfo` are bounded by `Characteristics.getMaxServiceSpecificInfoLength()`. For IRIS, discovery carries only a compact signed beacon (service name + PeerId short-id + capability flags) and a *bind* trigger — never envelope payload. [Level 1, Characteristics; Level 4 WIFI_AWARE.md/WIFI_AWARE_COST]
- Throughput: existing TRANSPORT_ABSTRACTION row (10–300 m / ~300 Mbps peak / 20–100 Mbps practical / 1–10 ms / P2P) is **retained**; 6 GHz headroom noted in Q3 does not change the conservative planning numbers. [Level 4 internal matrix]

## 5. Q5 — Background discovery persistence guarantees (no-FGS, Doze) + Suspend/Resume

- **Attach model**: `WifiAwareManager.attach(AttachCallback, ...)` returns a `WifiAwareSession`; a cluster is a shared resource (re-attach returns immediately); app **must** call `WifiAwareSession.close()` when done. This is an explicit app-driven life-cycle; there is no implicit "always-on NAN app process". [Level 1, developer.android.com WifiAwareManager]
- **Doze**: NAN discovery is executed by the Wi-Fi Aware system service + chip firmware (the Aware service manages duty cycling and the discovery windows); the radio activity itself is not an Android "network" socket so it is not throttled the same way app sockets are in Doze. **However**, callbacks (`onServiceDiscovered`, `onDataPathRequest`, etc.) are delivered to the app process — if the app process is cached/killed (Android 8+ background-execution limits), delivery is unreliable. Modern Android (12+/14+/15/16) aggressively enforces background limits, so **an active foreground service is the reliable production pattern** for continuous discovery. [Level 1 WifiAwareManager; Level 3/L5 ProAndroidDev "Beyond Doze" Android 15/16 background reality — process death, FGS buckets, OEM killers]
- Correction: `WIFI_AWARE.md` "background chart (API 8-9 FGS, API 10+ discovery survives without FGS)" is **dated** and contradicts Android 12+ background-execution enforcement; the DESIGN stage must require a FGS (`connectedDevice` type API 34+, else a runtime-appropriate type) for production discovery and document it (like BLE-001 AC-10). [Level 1/3 synthesis]
- **Suspend/Resume (API 34+ HAL/firmware gated)**: privileged apps can suspend active discovery sessions (incl. NDPs) for power and resume fast; out-of-band (e.g., BLE) can synchronize suspend/resume across devices. IRIS can adopt suspend as a battery optimization on capable devices. [Level 1, source.android.com wifi-aware]
- **Availability is dynamic**: on `ACTION_WIFI_AWARE_STATE_CHANGED`, discard active sessions and re-check `isAvailable()`; never assume persistence across toggles. This is the runtime capability-refresh requirement already recorded in the WIFIAWARE-001 known_limitations. [Level 1, developer.android.com wifi-aware]

## 6. Q6 — Ranging (WifiRttManager) + geofenced discovery

- **Direct ranging of a Wi-Fi Aware peer**: `WifiRttManager.startRanging(RangingRequest, Executor, RangingResultCallback)`; `RangingRequest.Builder.addWifiAwarePeer(PeerHandle)` or `addWifiAwarePeer(MacAddress)`; results in `onRangingResults(List<RangingResult>)`, per-result failures handled individually. Ranging requires the device to support **both** Wi-Fi Aware and Wi-Fi RTT (802.11mc FTM base; 802.11az NTB initiator from API 35). [Level 1, developer.android.com wifi-rtt; source.android.com wifi-rtt]
- **Permissions**: a ranging request with only Wi-Fi Aware peers needs `NEARBY_WIFI_DEVICES` (with `neverForLocation`) **or** `ACCESS_FINE_LOCATION`; any request including APs needs `ACCESS_FINE_LOCATION` (plus `CHANGE_WIFI_STATE`, `ACCESS_WIFI_STATE`). Ranging requires location services enabled + Wi-Fi scanning on. [Level 1, developer.android.com WifiRttManager]
- **Geofenced discovery (API 31+)**: `SubscribeConfig.Builder.setMinDistanceMm(...)/setMaxDistanceMm(...)`; the publisher must call `setRangingEnabled(true)`. When a peer service is discovered within the geofence, `onServiceDiscoveredWithinRange` fires with measured distance, which can then be refined with direct RTT. This enriches IRIS discovery metadata (proximity banding for routing weights) without opening a data path. [Level 1, developer.android.com wifi-aware + wifi-rtt]
- **Ranging calibration**: AOSP specifies RTT KPI accuracy targets and CTS verifies them. [Level 1, source.android.com wifi-rtt]

## 7. Q7 — Coexistence / RadioConflictGroup (single radio)

- Android 12+ **Wi-Fi and cellular coex channel avoidance** applies to STA, SoftAp, Wi-Fi Direct (P2P), and **Wi-Fi Aware (NAN)**: unsafe-channel avoidance is best-effort via a vendor lookup table + power cap; mandatory per-carrier channel restrictions are possible. Notably, for NAN **"the framework is not involved in channel selection"** — channel selection is firmware/vendor-driven. [Level 1, source.android.com/docs/core/connect/wifi-coex-channel-avoidance]
- Official guidance states **Wi-Fi Aware may be unavailable when Wi-Fi Direct, SoftAP, or tethering is in use** on given hardware — a single-radio contention reality (the `RadioConflictGroup` concept lives at the HAL/`IWifiNanIface` concurrency layer). Combined with `isAvailable()` dynamism, coexistence is a **runtime-availability constraint, not a build failure**. [Level 1, developer.android.com wifi-aware `isAvailable()`; source.android.com wifi-aware multi-interface concurrency note]
- **Design implication** (mirror BLE-001): maintain a runtime capabilities table; on `ACTION_WIFI_AWARE_STATE_CHANGED` or transport open failure due to conflict, mark Wi-Fi Aware unavailable and degrade to BLE / Wi-Fi Direct; when Aware becomes usable, promote back. Do not treat Wi-Fi Direct or BLE as mutually exclusive at the *routing* layer — operations are serialized by the platform radio scheduler; IRIS simply re-orders transport preference at runtime. [Level 1/4 synthesis]

## 8. Q8 — NAN/NDP CVEs + MAC-rotation privacy + app-layer-security posture inheritance

- **No NAN-specific Android *app-layer* CVE wave** was surfaced in this pass (**Gap G-WA-2**). The 2024-25 Android *BLE-stack* remote-RCE class (GATT/SDP/ACL, e.g. CVE-2025-48539) does **not** map to Wi-Fi Aware: the NAN backend is kernel/firmware and its API surface is a high-level service; the app defensive surface is config/parse of *your own* discovery payload — which IRIS signs/verifies in the envelope. The relevant posture is an **OS patch-floor + never-trust-platform-peer-data-for-identity**, matching the BLE-001 R5 decision. [Level 4 synthesis; Level 1 policy]
- One kernel driver item surfaced: **CVE-2024-49857** (iwlwifi — "set the cipher for secured NDP ranging") — a Linux wireless-driver bug around secured-NDP ranging, OS-patch-gated, not app-remediable. [Level 1, NVD https://nvd.nist.gov/vuln/detail/CVE-2024-49857]
- **MAC randomization privacy is platform-built-in**: the NMI (discovery) and NDP (data) MACs **must be randomized and never equal the factory MAC**; re-randomized at a regular interval (`NanConfigRequest.macAddressRandomizationIntervalSec`, default 30 min); randomization may be *suspended* while an NDP is configured (less-frequent re-randomization, but the factory MAC is never used). RTT transaction MACs are randomized too. `WifiAwareManager.attach(..., IdentityChangedListener, ...)` reports the (rotating) Aware interface MAC on attach and on updates — apps should key peers by their own identity, not the rotating MAC. [Level 1, source.android.com wifi-aware + wifi-rtt]
- **App-layer posture inheritance (SEC-001/IDENT-001)**: discovery service name = IRIS service; subscribe/publish carries only the signed compact beacon; data-path accept **must** verify the app-layer envelope/signature chain before forwarding or surfacing content; **no unauthenticated triggers** — a discovered peer or inbound NDP never changes routing/identity/authority state without envelope verification. [Level 4, SEC-001 AC-11 / IDENT-001 / CRYPTO-001 evidence]

## 9. Cross-cutting note: Apple now ships Wi-Fi Aware (CONFLICT-1)

- **`WiFiAware` framework** is first-party Apple: iOS 26.0+, iPadOS 26.0+, Mac Catalyst 26.0+; supported devices: iPhone 12+, iPad (10th gen)+, iPad Air (4th gen)+, iPad Pro 11" (3rd gen)+, iPad Pro 12.9" (5th gen)+, iPad mini (6th gen)+. Overview: "securely pair and connect to external devices over peer-to-peer Wi-Fi … authenticated and encrypted at the Wi-Fi layer … simultaneous use with a Wi-Fi infrastructure network". Appents: `com.apple.developer.wifi-aware` entitlement + declared Wi-Fi Aware services. Pairing via AccessorySetupKit / DeviceDiscoveryUI. [Level 1, https://developer.apple.com/documentation/WiFiAware]
- Interop reality check (community, L5): an Android↔Apple NDP attempt (Apple publisher, Android subscriber) reached authenticated pairing on both sides but the **NDP request from Android was not answered** (Apple forum Aug 2025; a "Qualcomm's NDI and NMI are different" reason offered). Cross-vendor NDP interop is therefore **not yet dependable** — do not rely on it for v1. [Level 5, https://developer.apple.com/forums/thread/797186]
- **Action for DESIGN (iter 93)**: correct `WIFI_AWARE.md` + `TRANSPORT_ABSTRACTION.md` "iOS NO" rows (Apple `WiFiAware`, iOS 26+); record a future iOS-Wi-Fi-Aware transport/roadmap note; keep BLE-002 as the implemented iOS transport path for v1. Register as CONFLICT-1 in the design's doc-reconciliation matrix (like SEC-001 DISC-0013 C-pattern). [Level 4/1 synthesis]

## Verdict

**PROCEED to DESIGN (iter 93).** v1 = publish/subscribe NAN discovery + NDP IPv6 socket data path reusing INTERNET-001 TCP framing; FGS-required background model (AC mirror of BLE-001 AC-10); app-layer envelope = trusted boundary with NDP open at L2; runtime capability/availability refresh on `ACTION_WIFI_AWARE_STATE_CHANGED`; ranging/geofence as optional discovery metadata; coexistence handled by degrade-to-BLE; and CONFLICT-1 (Apple Wi-Fi Aware) recorded for doc reconciliation. Design must define AC-1..n (C2 gap) + DEC-WA-0001..n.
