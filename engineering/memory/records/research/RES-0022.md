## 0. Executive summary (decisions at a glance)

- **Q1 ADOPT — foreign traits are the mechanism.** UniFFI (0.31.x, 0.32 on docs.rs) now prefers **foreign traits** (`#[uniffi::export(foreign)]` proc-macro or `[Trait, WithForeign]` UDL) over the older "callback interface" concept, which is **soft-deprecated** for new work. The three adapter traits translate almost 1:1: `BleAdapter` ⇒ sync foreign-trait methods returning `Result` (precedent: keychain example); `WifiAwareAdapter` + `WifiDirectAdapter` ⇒ **async trait methods** exported over FFI (UniFFI generates `suspend` methods in Kotlin; Rust side receives them back through the **foreign future / oneshot callback** mechanism — "Async callback/trait interface methods are the way that Rust makes async calls across the FFI"). **Known trap (issue #2576, open 2026): `#[uniffi::export(async_runtime="tokio")]` on a struct implementing an exported trait's async methods is INEFFECTIVE** — bridging for trait-method calls does not route through `async-compat`; Transport impls must pass their own tokio handle / use `tokio::spawn` rather than relying on the attribute. Constraints: foreign-trait methods **must return `Result` with a compatible error type** (else panic) and **references aren't supported** (issue #2263) → by-value params (the existing adapter traits already pass by-value — compatible).
- **Q2 ADOPT — UniFFI + cargo-ndk, no hand-written JNI.** cargo-ndk **v4.1.2** (MSRV Rust 1.86; targets `aarch64-linux-android`/`armv7-linux-androideabi`/`x86_64-linux-android`/`i686-linux-android`; NDK autodetect via Android Studio path or `ANDROID_NDK_HOME`; hosts Linux/macOS/Windows). Gradle integration: `org.mozilla.rust-android-gradle.rust-android` **0.9.6** (2025-01-13) for Gradle 8.x; **Mullvad fork `net.mullvad.rust-android` 0.10.1 (2026-04-20) targets Gradle 9+** — pin per the chosen Gradle version (design AC). NDK r26+ floor stands; current SDK ships NDK 28.x — **pin via `ANDROID_NDK_HOME` and record the exact NDK at scaffold time** (G-AND-4/G-AND-5). Reference project `ianthetechie/uniffi-starter` demonstrates a production Android library build + generated-Kotlin commit convention. JNI by hand only for the `System.loadLibrary` seam + rare escape hatches; all typed surface via UniFFI.
- **Q3 ADOPT — Kotlin 2.2.x + Compose (stable), Hilt.** Kotlin 2.2.0 stable (context parameters, guard conditions, smarter Compose builds; 2.1 strong-skipping compiler now default). Compose = default UI toolkit (Google apps on Compose); MVVM+Clean Architecture per KOTLIN_LAYER.md; **Hilt** (official, compile-time) for Android-only DI; `collectAsStateWithLifecycle()` over `collectAsState()`; stable keys/`@Stable` for recomposition. Target stays **API 34 / min 26** per ANDROID.md (Ubikon/Pillai 2026 both confirm API 26 ≈ 95%+ device coverage floor) — but see Q5 carry-forward on `ACCESS_LOCAL_NETWORK` before any future targetSdk bump to 37. FGS `connectedDevice` (API 34+ `FOREGROUND_SERVICE_CONNECTED_DEVICE`) confirmed still the mandatory BLE transport foreground contract; background scan via `PendingIntent` (Oreo+) + `SCAN_MODE_LOW_POWER`/`OPPORTUNISTIC`; WorkManager for periodic store-and-forward cadence; OEM battery-kill matrix (Samsung One UI Adaptive Battery, Xiaomi aggressive killers, Doze/app-standby buckets) must be documented + capacity-exempt FGS in DESIGN.
- **Q4 ADOPT — single curve line: Keystore Ed25519, NO ECDSA conversion.** Android Keystore natively supports **Ed25519+X25519 hardware-backed since Android 13 (KeyMint v2 HAL adds Curve25519 signing + key agreement; keystore2 daemon itself rewritten in Rust, Android 12)**. StrongBox (API 28+ KeyMint SE) supports **only** RSA/AES/ECDSA P-256/ECDH P-256/HMAC-SHA256/3DES — **Ed25519 is NOT in the StrongBox subset** (and StrongBox Ed25519 attestation has an ecosystem CTS failure 2026: issue 399856239). Conclusion per IDENT-001 RES-0016 D2 + RED-0005: provision the Ed25519 identity + X25519 static in **TEE-backed Keystore** (API 23+ KeyGenParameterSpec, `setIsStrongBoxBacked(false)` default); keep the Rust Ed25519/X25519 session/onion keys in-engine (ephemeral session keys need no hardware anchor — precedent: hw-sign hardware-key priority literally places ED25519 first, P-256 second). StrongBox reserved only for an optional AES DEK / P-256 hardened rescue path if the threat model ever demands it (not v1).
- **Q5 ADOPT with TWO carry-forward platform changes.** (a) **BLE**: unchanged core (BluetoothLeScanner + BluetoothGatt); Android 17 changes BLE only for targetSdk 37+: `BluetoothSocket.read()` (RFCOMM) now returns **-1** on close/drop → Kotlin `BleAdapter` read loops must check for -1 explicitly (already accurate for LE CoC). Background scanning limits unchanged (30-s no-filter limit, 5-starts/30-s throttle, PendingIntent pattern, FGS connectedDevice mandatory). (b) **Wi-Fi Aware**: alive + current through API 37 (docs updated 2026-08-14), NAN-USD mode exists, datapath 1:1 (already IRIS design), iOS 26+ `WiFiAware` framework (CONFLICT-1 already reconciled). (c) **Wi-Fi Direct + the LOCAL NETWORK PERMISSION — CRITICAL NEW**: Android 17 introduces `ACCESS_LOCAL_NETWORK`, a runtime permission (in the `NEARBY_DEVICES` group, no re-prompt if a group sibling is granted) **mandatory for apps targeting API 37+**. It gates **outgoing TCP, incoming TCP, UDP unicast/multicast/broadcast → i.e. the entire IRIS data plane** (TCP-over-GO, NDP IPv6 sockets, NAN UDP) plus mDNS/DNS-SD. **For targetSdk ≤ 36, `INTERNET` implicitly grants local-network (temporary bridge — must be revisited at any SDK bump).** Carry to DESIGN: (i) keep targetSdk 34 for v1 ⇒ no LNP needed, **but document the SDK-37 cliff inline** (declare + runtime-request `ACCESS_LOCAL_NETWORK` before any bump); (ii) general guideline for the SDK-37 path: `android.net.nsd` system-mediated DiscoveryRequest picker + `NsdManager` IPs don't need the permission; raw in-process sockets DO.

**Key doc corrections/carry-forward to DESIGN**: ANDROID.md stays valid (Kotlin 1.9+/Compose BOM 2024.01.00, FGS connectedDevice API 34+, cargo-ndk, UniFFI, generated-Kotlin committed) but should be amended with: UniFFI version pin 0.31.x + foreign-trait proc-macro preference (callback interfaces soft-deprecated → use `#[uniffi::export(foreign)]`); cargo-ndk 4.1.2 + rust-android-gradle 0.9.6 (Gradle 8.x) or Mullvad 0.10.1 (Gradle 9+); Android 13 (API 33) Keystore Ed25519/X25519 hardware-backed; `ACCESS_LOCAL_NETWORK` SDK-37 analysis; Android 17 `BluetoothSocket.read()` -1 semantics; NDK r28 pinned-at-scaffold note.

## 1. Evidence passes

### Q1 — UniFFI bridging mechanism for Kotlin-implemented transports (callbacks vs foreign traits vs async)
**VERDICT: ADOPT foreign traits** (`#[uniffi::export(foreign)]`) + **async trait methods** via UniFFI foreign-future/oneshot callbacks. Callback interfaces remain for UDL legacy but are soft-deprecated in the 0.31 guide ("foreign traits should be preferred").
- Foreign traits guide — Rust trait implemented in Kotlin/Swift/Python; proc-macro `#[uniffi::export(rust, foreign)]` or `#[uniffi::export(foreign)]`; UDL `[Trait, WithForeign]`; params by value (references unsupported, issue #2263); methods must return `Result` w/ compatible error type; cycle warning (Rust obj ↔ foreign obj) — https://mozilla.github.io/uniffi-rs/latest/foreign_traits.html (L1)
- Callback interfaces — "Callback interfaces are a special implementation of Rust traits implemented by foreign languages… They are (soft) deprecated, remain now for backwards compatibility, but foreign traits should be preferred" + VTable `/` handle mechanics + Kotlin `class AndroidKeychain: Keychain` example — https://mozilla.github.io/uniffi-rs/0.31/types/callback_interfaces.html (L1); module doc https://docs.rs/uniffi/latest/uniffi/ffi/callbackinterface/ (L3/L4)
- **Async overview** — "Foreign async callback methods: Async callback/trait interface methods are the way that Rust makes async calls across the FFI"; oneshot-channel + leaked `Sender` + `extern "C"` completion fn; foreign side runs the `suspend`/async fn normally and calls back; Rust never needs its own event-loop thread (piggybacks foreign runtime) — https://mozilla.github.io/uniffi-rs/latest/internals/async-overview.html (L1)
- Async/Future support — Rust async fn ↔ foreign `suspend fun`; **async trait methods exported with `#[uniffi::export]` outside `#[async_trait::async_trait]`** or UDL `[Async]` — https://mozilla.github.io/uniffi-rs/0.27/futures.html (L1); verified compatible with the `async-trait` crate already used by wifiaware.rs/wifi_direct.rs
- **OPEN TRAP**, issue #2576 (2025-2026): `#[uniffi::export(async_runtime="tokio")]` INEFFECTIVE on structs implementing exported traits' async methods — trait-method bridging doesn't route through `async-compat`; maintainer confirms; workaround = explicit `tokio::spawn`/runtime handle — https://github.com/mozilla/uniffi-rs/issues/2576 (L3/L5, real production report). _Design must not rely on the attribute for the polled async adapter methods._
- Version reality: uniffi 0.31.x current (crates.io 2026-06-30; uniffi_core 0.31.1), **uniffi_bindgen 0.32.0 on docs.rs**; "ready for production use, long way from 1.0" — https://crates.io/crates/uniffi, https://docs.rs/crate/uniffi/latest (L3/L4); AOSP itself vendors uniffi (`platform/external/rust/crates/uniffi`) (L4)
- Community confirmation: "Mozilla already did this. It's called UniFFI" (Kotlin Discussions June 2026 on auto-generating JNI bindings) — https://discuss.kotlinlang.org/t/31098 (L5 corroboration)

### Q4 — Keystore hardware-backed Ed25519 vs ECDSA P-256 vs Rust session keys
**VERDICT: ADOPT Keystore Ed25519 (TEE), reject ECDSA conversion, session keys stay Rust.**
- **Android 13 = Ed25519/X25519 hardware-backed**: KeyMint v2 HAL "adds support for Curve25519 for both signing and key agreement"; keystore2 daemon rewritten in Rust (Android 12) — https://source.android.com/docs/security/features/keystore (L1). Issue confirmation: "AndroidKeyStore provider started supporting Curve25519 for signatures (Ed25519) and key agreement (X25519) in Android 13. Implementation is hardware-backed when the device has a TEE" — https://issuetracker.google.com/issues/356158095 (L1)
- Ed25519 in Keystore also surfaceable API 31+ officially but OEM-dependent (older 4.x claim); sample `KeyPairGenerator.getInstance("Ed25519","AndroidKeyStore")` + `DIGEST_NONE` — https://blog.yashgoyal.dev/secure-eddsa-key-management-on-ios-android (L5)
- **StrongBox algorithm subset EXCLUDES Ed25519**: RSA 2048, AES 128/256, **ECDSA/ECDH P-256**, HMAC-SHA256, 3DES → Keystore system docs — https://developer.android.com/training/articles/keystore (L1); same in http://source.android.com/docs/security/features/keystore + https://developer.android.com/privacy-and-security/keystore (L1). StrongBox caution (slower, fewer concurrent ops) — L1.
- **StrongBox Ed25519 CTS pain is real in 2026**: "ed25519 signature algorithm not supported for android 15 ctst testCurve25519Attestation failure (StrongBox: false)" — https://issuetracker.google.com/issues/399856239 (L1/L5)
- Guardsquare 2026 Keystore guide: software vs hardware-backed tradeoffs, TEE vs SE (StrongBox) perf/side-channel, `setIsStrongBoxBacked(true)` per-key decision, StrongBox "only for extremely sensitive keys" — https://www.guardsquare.com/blog/android-keystore (L3)
- **Hardware-key precedent orders ED25519 FIRST then P-256 then RSA-PSS** (device-bound credential experiments across Browser/Apple/Android/Windows) — https://github.com/reitowo/hw-sign (L4). Strongly corroborates keeping Ed25519 as the hardware-anchored identity curve instead of converting to P-256.
- IDENT-001 alignment: RES-0016 D2 provisioned Keystore TEE/StrongBox with StrongBox keygen ≈9.2 s / 1 MiB ≈3 s (KeyDroid 2507.07927) — GPU for DESIGN: master/identity in TEE Ed25519; StrongBox only if a P-256/AES rescue path is ever added.
