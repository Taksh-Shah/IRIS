## Question

For the MSG-001 Message Engine implementation pass (`crates/iris-core/src/message_engine/`), what do the **newest 2025–2026 primary sources** say about the six open implementation questions — (1) lifecycle/custody/status reporting, (2) priority scheduling + starvation prevention, (3) deduplication data structures, (4) retransmission/ACK timing tables, (5) TTL + clock skew handling, (6) fragmentation — and exactly which concrete changes must be made to `docs/implementation/MSG_DESIGN.md` before code is written?

Primary-source verification performed 2026-08-13: RFC Editor (RFC 9171, 9713, 9758, 6298, 5326, 9174 full texts fetched), IETF Datatracker (IETF 124 DTN WG minutes + slides for CTAB/CREB and QoS/UQEB), IEEE/ACM/arXiv literature (Audsley OPA, DRR, Kirsch-Mitzenmacher, cuckoo filters, binary fuse filters, custody-transfer analysis), and Android platform configuration source for clock-synchronization reality.

## Findings

### A. Lifecycle / Custody / Status Reporting

**F1. RFC 9713 (2025-01) updates the BPv7 Administrative Record Types registry; custody transfer signaling is BPv6-only.**
- **Claim**: RFC 9713, "Bundle Protocol Version 7 Administrative Record Types" (Jan 2025), registers administrative record types for BPv7 (status reports, and the RFC 9171 §6.1 records). The BPv7 processing-control flags carry **no custody bit** — custody transfer (BPv6 "Custody signal", RFC 5050 §5.10) is not expressible in the BPv7 primary block.
- **Evidence**: RFC 9713 (rfc-editor.org/rfc/rfc9713); RFC 9171 §9.3 flag table; RFC 5050 §5.10. *(SPEC_RFC, HIGH)*
- **Implication**: IRIS `C-ACK` ("custody ACK", ACKNOWLEDGEMENTS.md) is a *custom* responsibility handoff — it must not be presented as a standard BPv7 custody signal. Wire format stays IRIS-proprietary; semantics must match the emerging CTAB extension (F5) if interop is ever desired.
- **Decision**: keep C-ACK as IRIS-level custody *responsibility* (per RES-0008 C2 resolution); document "not BPv7 custody signal" in ACKNOWLEDGEMENTS.md.

**F2. RFC 9758 (2025-05) updates the `ipn` URI scheme; EID syntax is now more flexible.**
- **Claim**: RFC 9758, "Updates to the ipn URI Scheme" (May 2025), adds a **Service Number** field to `ipn:<node number>.<service number>` and defines new dot-decimal compaction rules, superseding RFC 7116's fixed node-number/service-number split.
- **Evidence**: RFC 9758 (rfc-editor.org/rfc/rfc9758). *(SPEC_RFC, HIGH)*
- **Implication**: IRIS uses its own 16-byte UUIDv7 NodeId (RES-0008 C1), not ipn EIDs — so RFC 9758 is *informational* for MSG-001. If a future interop shim maps IRIS NodeId → ipn, the Service Number field is the correct place for IRIS's message-type/port concept (mirrors PROTO-001 envelope fields).
- **Decision**: no wire change; log in interop backlog. Reference RFC 9758 when the relay-gateway interop layer is designed.

**F3. RFC 9171 DTN time, creation timestamp, and lifetime semantics.**
- **Claim**: RFC 9171 §4.2.6: DTN time is milliseconds since **2000-01-01T00:00:00Z**; value 0 = "time unknown". §4.2.7: creation timestamp = DTN time of creation; bundle identity = (source EID, creation timestamp[, fragment offset, payload length]). §4.3.1: lifetime is **relative, in milliseconds past creation time**; value 0 = no explicit lifetime; a BPA "MAY impose an overriding lifetime" on reception.
- **Evidence**: RFC 9171 §4.2.6, §4.2.7, §4.3.1 (rfc-editor.org/rfc/rfc9171). *(SPEC_RFC, HIGH)*
- **Implication**: IRIS's absolute `expires_at_unix` (TTL.md) is a valid *projection* of (creation time + lifetime). The 0 = unknown DTN time is the standards hook for IRIS's `ClockSkewSuspect` state: a node that cannot trust its clock should treat its own timestamp as unknown and rely on relay-observed skew. Bundle identity = (source, creation timestamp) is exactly why IRIS `msg_id` must be derived from originator + created_at (+ nonce) — DEDUPLICATION.md's construction is correct.
- **Decision**: keep `expires_at_unix` absolute; map `created_at_unix_millis` to DTN-time semantics (ms resolution); treat `created_at == 0` as "unknown" → mark `ClockSkewSuspect` instead of trusting it.

**F4. RFC 9171 §5.5 expiration is mandatory and fire-at-any-processing-point; status reports are DoS-sensitive.**
- **Claim**: §5.5 "Bundle expiration MAY occur at any point in the processing of a bundle. When a bundle expires, the BPA MUST delete the bundle" (reason "Lifetime expired" or "Traffic pared" when an overriding lifetime was imposed). §6.1/§8.8: status-report generation is **disabled by default** because "it is possible for status reports to be used to amplify denial-of-service attacks"; they must be explicitly requested per bundle. §8.9: **fragments themselves are a DoS vector** — a remote node can send endless partial fragments to exhaust reassembly buffers.
- **Evidence**: RFC 9171 §5.5, §6.1, §8.8, §8.9 (rfc-editor.org/rfc/rfc9171). *(SPEC_RFC, HIGH)*
- **Implication**: (a) Expiry → delete + free storage must be a first-class MSG-001 transition (matches RES-0008 F3). (b) ACK/status generation must be opt-in per delivery policy, never blanket — ACKNOWLEDGEMENTS.md already scopes ACKs to CONFIRMED/PRIORITY policies; keep it that way and **rate-limit ACK generation** as an anti-amplification control. (c) The fragment reassembler needs a per-source in-flight-fragment budget + timeout (matches F12).
- **Decision**: implement `EXPIRED → delete + evict`; gate ACK emission by policy + per-peer rate limit; cap fragment buffers per source.

**F5. IETF 124 (2025-11) CTAB/CREB: custody transfer ≠ reliable delivery; CCSDS Orange Book expected early 2026.**
- **Claim**: "BPV7 Custody Transfer (CTAB) + Compressed Bundle Reporting (CBR)" (Wobbe et al., IETF 124, 2025-11-06): custody is being re-standardized as an **extension block**; "Any node can request custody; decision to take or refuse is mission or network specific"; custody is a *responsibility*, not a delivery guarantee; bundles carrying CTAB/CBR "should not be fragmented"; CCSDS "QoS Extension" Orange Book expected **early 2026**; custody removed from BPv7 partly because "estimating the right values for timer variables is difficult in some scenarios" (arXiv 2507.17403).
- **Evidence**: datatracker.ietf.org/meeting/124/materials/slides-124-dtn-wobbe-bpv7-custody-transfer-00; ietfminutes.org/minutes/ietf124/dtn.html; arxiv.org/abs/2507.17403. *(IETF-DRAFT/ACADEMIC, MEDIUM-HIGH)*
- **Implication**: IRIS relay custody (C-ACK) should be **policy-controlled refusal** (relay refuses when queue > 80%, per RES-0008 R6) and treated as responsibility transfer, never delivery proof. ACK/custody payloads must **never be fragmented** — hard rule for MSG-001's fragmenter. Monitor CCSDS Orange Book (early 2026) to align QoS semantics.
- **Decision**: implement custody accept/refuse policy hook; fragmenter hard-excludes ACK/custody payload types; track Orange Book release as a watch item.

### B. Priority Scheduling / Starvation

**F6. QoS UQEB proposal (IETF 124): within-class fairness is a stated requirement; storage classes are deleted bottom-up, TTL-first.**
- **Claim**: The BP QoS extension block (UQEB, Algarra Ulierte & Flentge, IETF 124) defines traffic classes EXPEDITED/NORMAL/BULK; slides state: **"A fair scheduling algorithm is required within each priority class to avoid data starvation"**; storage classes are CLASS 0..23 with the rule: "Bundle classes are deleted starting from the bottom. Within the same class, deletion is performed according to the TTL left, with the shortest TTL first."
- **Evidence**: datatracker.ietf.org/meeting/124/materials/slides-124-dtn-qos-algarra-00; RES-0008 F8–F10 (SpaceOps-2025 paper #252). *(IETF-DRAFT, MEDIUM-HIGH)*
- **Implication**: IRIS's 60-second starvation heuristic (MSG_DESIGN.md §Starvation Prevention) is weaker than the standard direction. The standard requires **fairness within a class** — meaning even within P4, a flood of P4 messages must not starve other P4 traffic. Storage eviction `(priority DESC, expires_at ASC)` (STORAGE.md, PRIORITY_MODEL.md) matches the UQEB storage-class rule exactly.
- **Decision**: replace the 60s heuristic with a **budget-based fair scheduler** (see R3): each priority (and each message within a priority) gets a guaranteed transmission-slot share per 60s window; P0 preemption is preserved but budgeted.

**F7. Audsley OPA and Deficit Round Robin are the validated tools for priority assignment + starvation-free scheduling.**
- **Claim**: Audsley's Optimal Priority Assignment (1991; journal version 2001) computes a priority ordering in polynomial time for any set of real-time tasks with an ordering-consistent schedulability test. Deficit Round Robin (Shreedhar & Varghese, SIGCOMM 1995) provides O(1) work-per-packet fairness — each queue gets a quantum (deficit) per round, guaranteeing bandwidth share without head-of-line starvation and without per-flow packet sorting.
- **Evidence**: Audsley, "Optimal priority assignment and feasibility of static priority tasks with arbitrary release times", Real-Time Systems J. 2001; Shreedhar & Varghese, "Efficient fair queuing using deficit round robin", SIGCOMM 1995 (dl.acm.org/doi/10.1145/217382.217453). *(ACADEMIC/IEEE, HIGH)*
- **Implication**: DRR maps 1:1 onto IRIS's 8 `VecDeque`s (one per priority): one round visits each non-empty priority queue and sends up to its quantum. Guarantees *some* airtime for P7 even under P0 flood — the exact property PRIORITY_MODEL.md's Known Limitations says the heuristic lacks. Audsley's result is the theory for choosing the priority ordering itself (P0…P7) and proving no better ordering exists.
- **Decision**: implement DRR with per-priority quanta as the queue scheduler (replaces pure strict priority + 60s hack); priority *order* P0..P7 stays (Audsley-consistent); quanta tuned per TTL/size (see R3).

### C. Deduplication

**F8. Kirsch–Mitzenmacher: two hash functions suffice — no FPR loss.**
- **Claim**: Kirsch & Mitzenmacher, "Less Hashing, Same Performance: Building a Better Bloom Filter" (2008): using only **two** hash functions h1, h2 and computing gi(x) = h1(x) + i·h2(x) gives an asymptotically identical false-positive rate to k independent hash functions, for all k ≥ 2.
- **Evidence**: Kirsch & Mitzenmacher, Random Structures & Algorithms 33(2) 2008 / arXiv:0708.4126. *(ACADEMIC, HIGH)*
- **Implication**: DEDUPLICATION.md's 10 hash functions can be **2** with zero FPR loss — simpler, faster, and 5× fewer hash computations per insert/lookup on the hot relay path. This is a pure implementation win with no behavior change to the 0.1% FPR budget.
- **Decision**: implement Bloom with the double-hash scheme (2 seed hashes → k derived indices); keep 0.1% FPR, 100k capacity, 144h window (DEDUPLICATION.md), and the 1.44 MB sizing (FPR budget unchanged).

**F9. Cuckoo and binary-fuse filters: space-optimal alternatives that support deletion/persistence (RES-0008 C4 resolution path).**
- **Claim**: Cuckoo filters (Fan et al., CoNEXT 2014) support **deletion** and beat Bloom filters when target FPR < 3%; binary fuse filters (Graf & Lemire, ACM J. Experimental Algorithmics 2022) reach within **~13% of the information-theoretic storage lower bound**, vs Bloom's ~44% overhead. Bloom filters cannot delete entries; cuckoo/fuse can — enabling a sliding 144h window without rebuild or overflow.
- **Evidence**: Fan et al., "Cuckoo Filter: Practically Better Than Bloom", CoNEXT 2014 (cs.cmu.edu/~dga/papers/cuckoo-conext2014.pdf); Graf & Lemire, "Binary Fuse Filters: Fast and Smaller Than Xor Filters", ACM JEA 2022 (arxiv.org/abs/2201.01174). *(ACADEMIC, HIGH)*
- **Implication**: RES-0008 C4 (Bloom reset-on-restart vs 144h window) has two viable resolutions: (a) persist the Bloom bitmap (1.44 MB I/O on startup) — simple, current design; or (b) switch to a **binary-fuse/cuckoo filter** that is smaller (~0.9–1.0 MB at same FPR) and can evict expired IDs, keeping the filter bounded without rebuild. Filter persistence is now a *research-answered* choice, not an open question.
- **Decision**: implement Bloom v1 (double-hash, F8) with bitmap persistence to SQLite; record binary-fuse filter as the documented upgrade path when the 144h window × volume requires deletion (EXP-MSG-001 candidate).

### D. Retransmission / ACK Timing

**F10. RFC 6298 RTO rules bound any exponential-backoff table; LTP and TCPCL show transport-level retransmission.**
- **Claim**: RFC 6298: initial RTO = 1s; **min RTO = 1s**; the maximum value "MAY be set to any value ≥ 60s"; RTO doubles on each retransmission (backoff factor 2). RFC 5326 (LTP): ARQ with **selective-acknowledgment reception reports** — retransmits only lost block ranges, not whole messages. RFC 9174 (TCPCLv4): a reliable transport for BPv7 bundles — when the transport is reliable, the bundle layer does not need to retransmit.
- **Evidence**: RFC 6298 (rfc-editor.org/rfc/rfc6298) §2.1–§2.5; RFC 5326 (rfc-editor.org/rfc/rfc5326) §2.5/§3.3; RFC 9174 (rfc-editor.org/rfc/rfc9174). *(SPEC_RFC, HIGH)*
- **Implication**: (a) Any IRIS retry table must respect the 1s floor / ≥60s cap / ×2 backoff shape — the task-proposed table (R2) complies; RETRIES.md's P0/P1 "no backoff" rows do *not* (they are constant-interval, which RFC 6298 does not prohibit, but they also get no jitter benefit — see R2). (b) For large P5–P7 payloads over reliable transports (TCPCLv4/Internet), whole-message retries are wasteful: LTP-style selective retransmission is the model for future fragment-level retry. (c) Retry is the *bundle* layer's job only when the transport is unreliable — IRIS must know per-transport reliability (Internet = reliable → 1 attempt; LoRa/BLE = unreliable → full schedule).
- **Decision**: adopt RFC 6298 bounds in the unified retry table (R2); add per-transport `reliability` hint so reliable transports skip bundle-level retransmission; log LTP-style selective retry as a P5–P7 future enhancement.

### E. TTL / Clock Skew

**F11. RFC 9171 Bundle Age block is the standard fallback for inaccurate clocks; Android reality shows large real-world skew windows.**
- **Claim**: RFC 9171 §4.4.2: the **Bundle Age extension block** (type 7) carries the time since bundle creation, measured by the local node, and is "recommended for use by nodes that do not have access to accurate clocks" — it lets intermediate nodes compute remaining lifetime without trusting the sender's clock. Android platform time sync: `config_ntpPollingInterval` = **64,800,000 ms (18 hours)** — a stock Android device re-syncs NTP roughly every 18h, so after a disaster begins clocks can be off by **minutes to hours** (exactly IRIS's TTL.md Known Limitations).
- **Evidence**: RFC 9171 §4.4.2 (rfc-editor.org/rfc/rfc9171); AOSP frameworks/base core/res/res/values/config.xml (`config_ntpPollingInterval`); RES-0008 F13–F14. *(SPEC_RFC + BEST-PRACTICE, HIGH)*
- **Implication**: IRIS's 300s skew budget + observed-skew-per-peer is the right design, and the **Bundle Age block is the missing fallback**: when a relay receives a message with `created_at` untrusted/unknown (F3), it can still enforce lifetime by tracking local arrival timestamps (age) rather than the sender's absolute clock. Android's 18h NTP interval confirms multi-minute/hours skew is realistic in the field — the 300s budget alone is insufficient without observed-skew tracking.
- **Decision**: add per-peer `observed_skew` (already in TTL.md) as the *primary* skew correction, and implement a **bundle-age fallback** (arrival-time-based lifetime check) for nodes flagged `ClockSkewSuspect`; keep 300s as the maximum applied budget (TTL.md).

### F. Fragmentation

**F12. RFC 9171 two-fragment model + reassembly rules + DoS guard; custody/ACK never fragmented.**
- **Claim**: RFC 9171 §5.8: fragmentation splits an ADU into **two fragments** when the full bundle would exceed a constraint; both fragments carry offset/length; §5.9: reassembly requires receiving both and buffering until all fragments arrive (or a local reassembly deadline). §8.9: fragments are a DoS vector (buffer exhaustion). §5.10: cancellation may be signaled. Combined with F5: custody/status payloads should not be fragmented.
- **Evidence**: RFC 9171 §5.8–§5.10, §8.9 (rfc-editor.org/rfc/rfc9171); RES-0008 F30 (CTAB no-fragmentation policy). *(SPEC_RFC, HIGH)*
- **Implication**: MSG_DESIGN.md's `fragment_timeout_secs: 30` reassembly timeout is a floor, not a ceiling: per-priority reassembly deadline should be up to the TTL remainder (RES-0008 R8). The two-fragment model means reassembly state per ADU is tiny (2 slots); the DoS guard (per-source fragment budget, F4) bounds total reassembly buffers.
- **Decision**: fragmenter emits ≤ 2 fragments per ADU (RFC 9171 model); reassembly deadline = min(30s floor, TTL remainder, priority cap); hard-exclude ACK/C-ACK/GW-ACK payloads (F5); per-source fragment budget (F4).

## Recommendations (R1–R8) — mapped to MSG_DESIGN.md

1. **R1 — Lifecycle + unknown-time handling (F3, F11).** Add `created_at_unix_millis` DTN-time semantics: `0 = unknown` → mark `ClockSkewSuspect`, never trust. Enforce `EXPIRED → delete + evict` as an explicit transition (F4). *Map: `Message Lifecycle`, `TTL Enforcer`.*
2. **R2 — Unify the retry/ACK tables (F10).** RETRIES.md, MSG_DESIGN.md, and ACKNOWLEDGEMENTS.md currently have **three different retry tables** (contradiction C-10-1 below). Adopt one RFC 6298-shaped table: P0 30s base ×2 (unlimited until TTL), P1 60s ×2 (max 10), P2 120s ×2 (max 5), P3 300s ×2 (max 3), P4–P7 600s ×2 (max 2); full jitter; reliable transports get 1 attempt. *Map: `Retry Strategy`, `ACK Tracker`.*
3. **R3 — Budgeted fair scheduling instead of the 60s heuristic (F6, F7).** Implement Deficit Round Robin over the 8 priority queues with per-priority quanta per 60s window (P0 quantum largest but bounded; every non-empty lower class receives ≥ 1 slot per round). Remove the "insert one P1-or-lower message" hack. *Map: `Priority Queue`, `Starvation Prevention`, acceptance #2/#7.*
4. **R4 — Storage eviction stays `(priority DESC, expires_at ASC)` (F6).** This exactly matches the UQEB storage-class rule (delete bottom-up, shortest TTL first). Document the mapping to CLASS 0–23 in STORAGE.md. *Map: `MessageStorage::evict_by_priority`, acceptance #9.*
5. **R5 — Dedup: 2-hash Bloom + persistence; fuse-filter upgrade path (F8, F9).** Switch to Kirsch–Mitzenmacher double hashing (k derived indices from 2 seeds); persist the 1.44 MB bitmap to SQLite on shutdown/startup to fix the restart-window gap; document binary-fuse filter (deletion-capable, ~13% from lower bound) as the upgrade when eviction is needed. *Map: `Dedup Engine`, acceptance #4.*
6. **R6 — ACK/custody: policy-controlled refusal; never fragmented (F5, F4).** Relays refuse custody when queue > 80%; custody = responsibility, not delivery proof; ACK generation rate-limited (anti-amplification); fragmenter hard-excludes ACK/custody payloads. *Map: `ACK Tracker`, `Fragment Reassembler`.*
7. **R7 — TTL: observed-skew primary + bundle-age fallback (F11, F3).** Per-peer `observed_skew` (cap 3600s, reject tamper-suspect) is the primary correction; nodes without trustworthy clocks use arrival-time (bundle-age) lifetime checks; 300s applied budget unchanged. *Map: `TTL Enforcer`, acceptance #3.*
8. **R8 — Fragmentation: two-fragment model + DoS guard (F12).** ≤ 2 fragments per ADU; reassembly deadline = min(30s, TTL remainder, priority cap); per-source fragment buffer budget; ACK/custody never fragmented. *Map: `Fragment Reassembler`, acceptance #6.*
