## 2. RQ-1 — Regulatory reconciliation (25 mW vs 1W, band, duty, ETA/import, LoRaWAN-vs-raw)

**ANSWER: ADOPT-WITH-CONDITION.** The governing instrument for IRIS LoRa in India is **WPC G.S.R. 853(E), 10-Dec-2021** — "Use of Low Power Equipment in the Frequency Band 865-868 MHz for Short Range Devices (Exemption from Licence) Rules, 2021", made under §4+§7 Indian Telegraph Act 1885 and §4+§10 Indian Wireless Telegraphy Act 1933, superseding the 2005 RFID 865-867 rules. **Table-I (Non-Specific SRD — telemetry, telecommand, alarms, data): 865-868 MHz, 25 mW e.r.p., duty-cycle limit 1%** (applied to the entire transmission), EN 300 220 (ETSI harmonized). The `LORA.md` "1W (30 dBm)" is the **LoRaWAN IN865 network-plan** uplink parameter (Semtech RP002 / TTN Regional Parameters: 865.0625–867.1375 MHz, 8 channels, 30 dBm EIRP, 1% duty) — a network-deployment planning figure for LoRaWAN networks, **not** a device-level license-exempt emission limit. IRIS uses **raw LoRa peer-to-peer** (no LoRaWAN stack), so IRIS devices fall under Table-I device limits: **≤25 mW e.r.p. (≈14 dBm) and ≤1% duty (36 s/device/hour)**. **FIELD_OPERATIONS 866.0 MHz ≤25 mW e.r.p. CONFIRMED stands.**

## 3. RQ-2 — Duty-cycle enforcement (window, budget, R7 coupling, 60/25/10/5, P0, no override)

**ANSWER: ADOPT.** A `DutyCycleTracker` with a **rolling 1-hour window** and a **36,000 ms airtime budget** (1% of the hour) enforces Table-I. `check_and_consume(msg_airtime)` returns the next permitted send window (`next_send_window`) per RES-0008 R7 — the router schedules around the window rather than failing the send; airtime (packet on-air duration at SF/BW/CR) is the accounting unit. When budget is contended, airtime is allocated **proportionally by priority** per REQ-ROUTE-C-002: P0 60%, P1 25%, P2 10%, P3-P7 share 5%. **P0 on exhaustion**: the P0 message switches to the next-best available transport (P0 is never held/dropped — consistent with the P0-envelope discipline), never overrides the duty budget. **No runtime override exists** — Meshtastic's `override_duty_cycle_limit` is deliberately NOT followed (discussion #3725 shows it as a debug backdoor that defeats the regulatory constraint; IRIS has no equivalent switch).

| 2 | REQ-ROUTE-C-002 fixes priority-proportional airtime: P0 60% / P1 25% / P2 10% / P3-P7 5%. DutyCycleTracker budget is partitioned on this basis under contention. | docs/routing/ROUTING_REQUIREMENTS.md | L1 (project) |

## 4. RQ-3 — Radio parameters (SF/BW/CR, SF12-P0, airtime, size cap, fragmentation)

**ANSWER: ADOPT.** Default link: **SF9 / BW125 kHz / CR4/5** — the headline Semtech sensitivity/airtime balance. **P0 uses SF12** → -136 dBm sensitivity (BW125) vs -129 dBm at SF9: ≈+7 dB additional link budget for emergency traffic at ~4× the airtime — acceptable under the duty budget because P0 is rare and P0-switch protects it. Sensitivity figures from Semtech AN1200.13/SX1276 datasheet; SX1262 matches/beats SX1276 at these settings. Message size: IRIS envelope cap **255 B (P0_MAX_ENVELOPE_BYTES)** ≤ raw-LoRa practical payload; larger messages reuse the existing **5×51 B fragmentation** (RES-0003: fragment >255 B into 51-B chunks — 255 B cap). **Raw-LoRa P2P v1 reaffirmed**; LoRaWAN/IN865 (RP002) is a documented future alternate uplink only (join keys, 30 dBm EIRP network planning — NOT device power).

## 5. RQ-4 — Bridge protocol (BLE GATT primary, USB-SLIP alt, telemetry, hardware)

**ANSWER: ADOPT-WITH-CONDITION.** The phone/RPi gateway talks to the external LoRa module over **BLE GATT as the primary bridge** — three characteristics: **LORA_TX** (write, 255-B ATT value ≤512-B negotiated MTU), **LORA_RX** (notify), and **LORA_STATUS** (read/notify: RSSI/SNR/duty/battery). **USB-SLIP is the alternative** for RPi/desktop gateways: CDC-ACM serial + `frame.encode_slip()` (SLIP framing, RFC 1055-style) — deterministic latency, no BLE renegotiation. Status telemetry rides LORA_STATUS so the app can surface link RSSI/SNR + remaining duty + module battery. Hardware candidates: **Waveshare SX1262 LoRa HAT** (868M variant, programmed to 866.0 MHz — FIELD_OPERATIONS note) and **EBYTE E22-900M30S** (UART/AT). **Condition**: a `LoRaLinkAdapter` trait abstracts **AT-serial vs SPI-native** firmware surfaces (the BleAdapter-seam lesson: adapter implementation must be swappable; the E22 is AT/UART, the SX1262 HAT is SPI-native on RPi — both expose the same logical `tx/rx/status` contract).

## 6. RQ-5 — TRANSPORT-001 integration (adapter, Caps, lifecycle, reuse, crypto)

**ANSWER: ADOPT.** `LoRaTransport` implements the `Transport` trait via the existing **`TransportAdapter`** pattern (register/transmit/poll/…): `estimated_bandwidth_bps ≈ 14` (36 s/h × 255 B ≈ ~1 B/s average at 1% duty; peak-rate framing ≈14 B/s), `max_message_size_bytes = 255`, `duty_cycle_remaining` added to the trait surface (R7 seam). **`Caps`** gains the **SubGHz** row (long-range, low-rate, duty-bounded, P0-P2). Lifecycle: register/deregister on dongle plug/unplug (hot-plug via platform notifications — RPi udev/BLE discovery). Reuse: **multipath dedup** (a message delivered over BLE and LoRa is deduplicated at the envelope layer), **fragmentation** (5×51 B), **relay-cadence** seam (CONGESTION_CONTROL.md §355 — LoRa relay cadence scales with the same ≤40-flat/>40-linear rule; LoRa is the *lowest* cadence tier), **OBS-001** `iris.transport.lora.*` metrics (airtime consumed, duty remaining, packets TX/RX, RSSI/SNR). **No crypto changes**: the envelope-layer X25519+ChaCha20-Poly1305 (CRYPTO-001) is transport-agnostic; P0-encryption rules (P0 never encrypted over LoRa per FIELD_OPERATIONS) already live above the transport.

## 7. RQ-6 — Simulation fidelity (sim params, link budget, EXP-LORA-001 calibration, honesty)

**ANSWER: ADOPT-WITH-CONDITION.** `SimulatedLoRaTransport` gains explicit config: `sf`, `bandwidth`, `range_km`, `packet_loss_rate`, `duty_cycle_enforced`, `propagation_delay_ms`. Link-budget model: receive sensitivity from AN1200.13 (-129/-136 dBm) + **Okumura-Hata urban** path-loss model (suburban Mumbai multiplier) to derive range→SNR→PDR — so simulation reproduces distance-vs-reliability curves instead of a flat loss rate. ## 10. Gaps

- **G-1**: **TEC ER Annexure-G5 lag** — TEC ER (Dec-2024) lists LoRa equipment under 865-867 MHz while G.S.R. 853(E) 2021 governs 865-868 (same instrument supersedes) — certification authorities must reconcile at ETA time; tracked as a LEGAL-001/type-approval carry, not a software gate.
- **G-2**: **Sensitivity/airtime datasheet precision** — AN1200.13/SX1276 numbers are datasheet-grade; SX1262 HAT figures need a board-level noise-figure measurement at EXP-LORA-001 before the DESIGN airtime table is treated as hardware-ground-truth (sim stays SIMULATION_VALIDATED).
- **G-3**: **Okumura-Hata applicability** at 866 MHz urban Mumbai — Hata is 150-1500 MHz, but its city-size/suburban corrections are empirical; EXP-LORA-001 PDR data is the authoritative calibration (synthetic model only until then).
- **G-4**: **Module-A FCC/EU/IN band-scan overlap** — Waveshare 868M/915M variants and E22-region SKUs may expose bands outside India; procurement must verify the India-enabled variant + antenna (866 MHz) per SKU (LEGAL-001 carry).
- **G-5**: **Bandwidth estimate** (≈14 B/s framing / ≈1 B/s average at 1% duty) is derived from the envelope math + duty cap, not measured; refine from EXP-LORA-001 packet traces + airtime table at DESIGN/DEPLOY.
