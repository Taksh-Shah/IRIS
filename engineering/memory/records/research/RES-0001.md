# RES-0001: BPv7 Bundle Structure vs Flat Envelope

**Type**: Research
**Date**: 2026-08-11
**Node**: PROTO-001
**Author**: Protocol Agent
**Status**: ACTIVE

## Question

Should IRIS adopt BPv7's block-based bundle structure or keep its current flat envelope design?

## Source

RFC 9171 (BPv7), Section 4.1 Bundle Structure
https://www.rfc-editor.org/rfc/rfc9171.txt

## Finding

BPv7 uses a block-based structure where each bundle is a CBOR indefinite-length array of blocks:
- Block 0: Primary Bundle Block (mandatory, immutable)
- Block 1: Payload Block (mandatory)
- Blocks 2+: Extension blocks (optional, any order)

Each block has: block number, block type, block data, block processing control flags, CRC type, CRC.

IRIS currently uses a single flat CBOR map with integer keys 1-18 containing all envelope fields.

## Key Differences

| Dimension | BPv7 Block-Based | IRIS Flat Envelope |
|-----------|-----------------|-------------------|
| Extensibility | New block types added without breaking compatibility | New fields require schema version bump |
| Block ordering | Any order (blocks identified by number) | Fixed field order implied by key numbers |
| Security targeting | BIBs can target specific blocks | Signature covers entire envelope |
| CRC per block | Yes, each block has its own CRC type | No CRC mechanism |
| Parsing complexity | Higher (must parse array of blocks) | Lower (single map) |
| Wire size overhead | Higher (array headers, block headers) | Lower (single map header) |
| Block replication | Block must be replicated in every fragment flag | Not applicable |
| Forward compatibility | Strong (unknown block types ignored) | Moderate (unknown fields ignored) |
| Implementation complexity | Higher | Lower |
| BPv7 interoperability | Native | Requires translation |

## Implications for IRIS

### Arguments for adopting BPv7 blocks:
1. Future extensibility without breaking changes
2. Native interoperability with BPv7 implementations
3. Per-block CRC for integrity verification
4. Security can target specific blocks
5. Standardized approach, well-documented
6. Block replication control for fragmentation

### Arguments for keeping flat envelope:
1. Smaller wire overhead (critical for LoRa P0 255-byte budget)
2. Simpler parsing and implementation
3. Faster serialization/deserialization
4. Lower memory footprint on constrained devices
5. IRIS has different design constraints than BPv7 (smartphone-first vs deep-space)
6. Block headers add ~3-5 bytes per block × multiple blocks = significant overhead
