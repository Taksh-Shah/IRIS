## Question

## 1. Verdict: **PROCEED — ADOPT with 4 conditions and 1 defer**

The Android proof (RES-0022) transfers: **RQ-1 ADOPT-WITH-CONDITION** (foreign traits + async-over-FFI work on Swift; conditions = Swift-5 language mode or #2929 patch, and the 0.31.x `async_runtime`-on-trait-exports trap is only fixed in 0.32.0). **RQ-2 ADOPT-WITH-CONDITION** (CryptoKit Ed25519 persisted as a Keychain generic password with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` and **no** biometric flag; Secure Enclave ECDSA P-256 is NOT the identity path — confirmed P-256-only through current iOS; SE rescue path DEFERRED, mirrors RES-0022 StrongBox decision). **RQ-3 ADOPT-WITH-CONDITION** (iOS build is macOS-runner-gated; `macos-15` runner + Xcode 16.4 default is the floor; Linux iOS cross-build exists only via licensed-SDK workarounds — not worth it; UniFFI generation must use the 0.31 `generate --library` metadata flow, the IOS.md UDL command is stale). **RQ-4 ADOPT-WITH-CONDITION** (a thin Swift `SessionRecovery` coordinator IS warranted — it distinguishes launch reasons and re-arms BLE + re-submits BGTask requests; the underlying mechanisms remain `willRestoreState` + BGTaskScheduler). **RQ-5 ADOPT-WITH-CONDITION** (Live Activities shipped in **iOS 16.1**, not 16.2; still current through iOS 26/27 with no BLE-specific relaxation; the iOS-26 screen-on scan continuation is the only background-ish path and stops at screen sleep — carry RES-0024 framing).

## 2. RQ-1 — UniFFI Swift foreign traits + async-over-FFI: does the Kotlin proof transfer?

**ANSWER: Yes — foreign traits and async trait methods are first-class in the Swift bindings, with three Swift-specific conditions.** The `BleAdapter` trait (sync 10-op + `gatt_read`) maps to a generated Swift `protocol`; an `IosBleAdapter` Swift class conforms and is registered as a foreign trait; async adapter methods (the `WifiAwareAdapter`/`WifiDirectAdapter` pattern, and any future async `BleAdapter` ops) bridge via UniFFI foreign-future/oneshot callbacks exactly as on Kotlin — Rust never runs its own event-loop thread.

## 3. RQ-2 — iOS identity key: Secure Enclave (P-256 only) vs CryptoKit Ed25519 in Keychain

**ANSWER: ADOPT CryptoKit Ed25519 (app-layer key, persisted as a Keychain generic password) with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` and no biometric access-control flag; Secure Enclave ECDSA P-256 is confirmed P-256-only through current iOS and is NOT the identity path — defer an SE-backed rescue key.** This preserves the single-curve Ed25519 identity line (DEC-0002, CRYPTO-001 envelope core, IDENT-001 RES-0016 D2/DEC-P0006) and mirrors the Android Keystore-TEE decision's *spirit* (hardware-anchored where the platform allows; software-backed app-layer key where it does not — RES-0022 Q4 StrongBox carve-out analogy).

| # | Finding | Source (evidence) | Maturity |
|---|---------|-------------------|----------|
| 1 | **Secure Enclave supports only ECDSA P-256** (secp256r1) for signing and key agreement — no Ed25519, no EdDSA in SE, current through iOS 17/18/26. CryptoKit's `SecureEnclave.P256` is the only SE curve; Apple engineer: "SE-protected keys are always P256"; SE PKA supports RSA + ECC (secp256r1). | Apple CryptoKit `SecureEnclave` + `SecureEnclave.P256` docs; Apple Platform Security Guide (PDF); Apple Developer Forums 749596 (eskimo) + 680554 | L1 / L4 |
| 2 | **CryptoKit Curve25519.Signing.PrivateKey (Ed25519) is an app-layer key** — no Secure Enclave involvement; "Curve25519… have no direct keychain corollary. To store these kinds of keys, you package them as generic passwords" (`kSecClassGenericPassword`). Ed25519 is fully supported for signing in CryptoKit (RFC 8032). | Apple "Storing CryptoKit Keys in the Keychain" + "Importing Cryptographic Keys" (forum, eskimo: Curve25519 = "Apple CryptoKit only") | L1 / L4 |
| 3 | **Keychain accessibility for a background relay app**: `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` is the documented class for background-accessible items — "Apps that use background refresh services can use kSecAttrAccessibleAfterFirstUnlock" (Apple Security: Keychain data protection); the `ThisDeviceOnly` suffix = device-bound (UID-protected, excluded from backups/iCloud restore). This is also CryptoKit's default `accessControl` for SE keys — the same class is the correct choice for the IRIS identity item. | Apple support.apple.com "Keychain data protection"; CryptoKit `SecureEnclave.P256.Signing.PrivateKey.init(compactRepresentable:accessControl:authenticationContext:)` default | L1 |
| 4 | **FaceID/biometry must NOT gate the background identity key**: a biometric `SecAccessControl` flag (`.userPresence`/`.biometryAny`/`.biometryCurrentSet`) requires interactive auth and fails in background with `errSecInteractionNotAllowed` (-25308) — Apple engineer-confirmed; practitioner rule: background-accessible items = `AfterFirstUnlockThisDeviceOnly` **without** user-presence flags; pair biometric flags only on a separate foreground-only item. | Apple Developer Forums 759777 (eskimo) + 114159; Apple "Accessing Keychain Items with Face ID or Touch ID" (shows `.userPresence` = foreground semantics) | L4 / L1 |
| 5 | **CRYPTO-001 interop**: envelope core is Ed25519-based (DEC-0002/RES-0016); iOS must produce the same Ed25519 identity key material (per-device Ed25519 identity, sender_id = first 16 B of SHA-256(pubkey)). CryptoKit Ed25519 ↔ Rust `ed25519-dalek` are both RFC 8032 — byte-compatible raw representations (32-B seed / 32-B public key). SE ECDSA would require a second P-256 key + a conversion layer that breaks the single-curve line (RES-0022 Q4 rejected the same ECDSA conversion on Android). | RES-0016 D2/DEC-P0006, RES-0022 Q4, RFC 8032 (ed25519-dalek KAT line, CRYPTO-001) | L1 (synthesis) |
| 6 | **Known-limitation tradeoff to document**: iOS Ed25519 identity is device-protected by the Keychain class key + UID (not by SE hardware signature ops) — weaker anchor than Android TEE Keystore Ed25519. Acceptable for v1 (identity key is a long-lived signing key; per-message envelopes carry AEAD + X25519 ephemeral security — CRYPTO-001 posture). Optional SE ECDSA P-256 "rescue" path = DEFER, only if a hardware-anchored signing requirement appears (mirrors RES-0022 StrongBox deferral). | Synthesis of Apple docs + RES-0016/RES-0022 | L1/L5 |

**Design implication (IOS-001)**: Provision `identity.v1` on iOS = CryptoKit `Curve25519.Signing.PrivateKey`, persist `rawRepresentation` as `kSecClassGenericPassword` with `kSecAttrAccessible: kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, tag `com.iris.identity.v1`, **no** `kSecAccessControl` biometric flags (background-relay requirement); load lazily with `isProtectedDataAvailable` guard (iOS 15+ pre-warm can start the process before first unlock); never store the SE-style "P-256" key as identity. Update `IDENT_DESIGN.md` §keychain "iOS (later, IOS-001)" note accordingly at DOCUMENT stage.

## 5. RQ-4 — State restoration + background churn: is a dedicated SessionRecovery component warranted?

**ANSWER: Yes — a thin Swift `SessionRecovery` coordinator is warranted, layered ON TOP of `willRestoreState` + BGTaskScheduler (not instead of them).** The two relaunch mechanisms are distinct and must be distinguished at launch; neither auto-resumes BLE state; user force-quit disables both until manual relaunch.

| # | Finding | Source (evidence) | Maturity |
|---|---------|-------------------|----------|
| 1 | CoreBluetooth relaunch matrix (current through iOS 18/26): system relaunches the app for **pending BLE events only** (scanning, connecting, subscribed-notification characteristic) when the app was system-terminated or crashed; **NO relaunch after user force-quit**; Bluetooth-power toggle blocks relaunch; Airplane mode without BT toggle OK; device restart → relaunch deferred until first unlock (passcode devices). App is responsible for re-`startScan`/re-`startAdvertising` in `willRestoreState` — the system does not auto-resume (RES-0024 DI-6 cross-ref). | Apple QA1962 (archive); TN3115 "Bluetooth State Restoration App Relaunch Rules"; `peripheralManager(_:willRestoreState:)` doc; Apple Developer Forums 739307/760330 (eskimo) | L1/L4 |
| 2 | BGTaskScheduler is **heuristic, not periodic**: BGAppRefreshTaskRequest/BGProcessingTaskRequest get "a small amount of background execution time" at system-chosen times; Apple engineer: "if you expect app refresh to grant you time every 15 minutes, you'll be disappointed — common scenarios where it won't grant any at all." BGProcessingTask = "a few minutes" window chosen to minimize user interaction. Force-quit sets a flag blocking **all** background launch (incl. BGTask) until the user manually launches the app; silent pushes also blocked. | Apple Developer Forums 685525 (eskimo, authoritative summary), 808188, 721584, 809661; BGTaskScheduler/BackgroundTasks docs | L4/L1 |
| 3 | Relationship: CoreBluetooth has its own relaunch architecture (event-driven, independent of BGTaskScheduler); the system generally avoids terminating apps engaged in active BT communication; BGTask relaunch exists for scheduled maintenance work (routing maintenance, message expiry, metric flush — IOS.md BGProcessingTask design). Both relaunch paths wake the same process → **launch-reason discrimination is required**. | Apple Developer Forums 809661 (eskimo), 685525 | L4 |
| 4 | Lifecycle contract (BLE_002_DESIGN.md §5): stable restoration identifiers "IrisCentralManager"/"IrisPeripheralManager"; `willRestoreState` MUST re-call `startScan`/`startAdvertising`; never initialize BLE state outside a valid launch path; debounce/timeout restoration to avoid relaunch-crash loops (RES-0024 DI-6 hardening). | BLE_002_DESIGN.md §5; RES-0024 §7 DI-6 | L1 (project) |
| 5 | **SessionRecovery design** (thin coordinator, not a custom daemon — iOS forbids that): (a) at `application(_:didFinishLaunchingWithOptions:)` classify launch reason (BLE-restoration launch vs BGTask launch vs user launch) and gate BLE init on protected-data availability (`isProtectedDataAvailable`); (b) forward `willRestoreState` dictionaries to the CB managers and re-arm scan/advertise with backoff; (c) re-submit BGAppRefresh/BGProcessing requests at EVERY launch (scheduled requests do not survive force-quit/termination — forum-confirmed); (d) set task expiration handlers and `setTaskCompleted` on both task types. | Synthesis: QA1962 + forums 685525/809661 + BLE_002_DESIGN.md §5 | L1/L4 |

**Design implication (IOS-001)**: DESIGN a `SessionRecovery` component (Swift, ~1 coordinator + 2 task-handler closures) with ACs: launch-reason classification, re-arm-on-restore, BGTask re-submission-on-every-launch, force-quit-safe no-op, restoration debounce. This is a design-layer component, not a new background API. Carry RES-0024 DI-6 wording into IOS_DESIGN.md.

## 6. RQ-5 — ActivityKit / Live Activity: availability, iOS 18/26 status, screen-on BLE scan, limits

**ANSWER: ADOPT-WITH-CONDITION (framing only).** Live Activities shipped in **iOS 16.1** (not 16.2 — prompt claim corrected); still fully supported through iOS 26 (and iOS 27 per WWDC26), with hard limits: 8 h active + 4 h stale = 12 h max on Lock Screen, sandboxed (no network/location), per-app + device-wide concurrency caps, foreground-only start (except scheduled/LiveActivityIntent/push). No general-purpose lock-screen BLE continuation exists; the only "background-ish" scan path is the iOS-26 Live-Activity screen-on scan continuation (RES-0024 RQ-2) which **stops at screen sleep**.
