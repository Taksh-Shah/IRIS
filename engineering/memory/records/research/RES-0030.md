# RES-0030 — Mobly `/addkey`/`/to` hypothesis failure research

- **Date:** 2026-09-06
- **Node:** WIFIDIRECT-001
- **Maturity:** L2 — primary documentation plus direct device evidence
- **Question:** Did the Mobly failure occur because the harness bypassed the
  app's `/addkey` and `/to` command flow?

## Findings

The Kotlin command implementation shows `/addkey` validates and registers the
peer's X25519 key, while `/to` only sets the UI recipient. The Mobly snippet's
`addFriend(peerId, x25519)` is the durable equivalent of `/addkey`, and
`sendText(peerId, ...)` already supplies the same recipient that `/to` would
select before `/send`.

The corrected harness used `addFriend` before every `startMesh()` cold cycle.
The physical run still failed cycle 1/10 with P1 `Connected`, P2 `Degraded`,
`peers_seen=0`, and fallback send attempts rejected as BLE not connected.

Official Android documentation confirms that `discoverPeers()`/`connect()`
require the relevant nearby-device permission on Android 13+, and that P2P
connection progress is asynchronous; Mobly documentation likewise requires
bounded waits for asynchronous snippet events. Neither source supports treating
`/addkey` or `/to` as a substitute for framework peer discovery.

## Decision

The hypothesis is **rejected as the complete root cause**. Keep the
`addFriend`/direct-recipient harness correction. Do not retry or modify
production transport until a new design pass isolates the Vivo instrumentation
discovery/context failure.

Sources: Android `WifiP2pManager` API and Wi-Fi P2P overview; Mobly callback
handler documentation. Direct evidence is in
`docs/bug-hunting/hardware_verification/evidence/run-20260906-addkey/`.
