# RES-0029 — Mobly Wi-Fi Direct readiness and message-observation failure

**Date:** 2026-09-06  
**Node:** WIFIDIRECT-001 / hardware verification  
**Evidence maturity:** RESEARCHED  
**Result:** ADOPT-WITH-CONDITION

## Question

Why did the Mobly Tier-2 harness report delivery failure while both phones
reported `wifi-direct-0: Connected` and the shipping-app gate remained green?

## Evidence

- Android's Wi-Fi Direct guide states that `connect()` only reports initiation
  success/failure; applications must observe connection-state changes through
  `requestConnectionInfo()` and `onConnectionInfoAvailable()` before starting
  group-owner/client work. https://developer.android.com/develop/connectivity/wifi/wifi-direct
- The Android guide describes separate group-owner server and client socket
  work after `groupFormed` becomes true; framework group state is not itself
  proof that IRIS's application TCP socket handshake is live.
  https://developer.android.com/develop/connectivity/wifi/wifi-direct
- Mobly Snippet Lib documents asynchronous callbacks and blocking event waits.
  https://android.googlesource.com/platform/external/mobly-snippet-lib/+/refs/heads/aml_hef_341811030/examples/ex3_async_event
- Mobly's callback handler provides bounded `waitAndGet` / `waitForEvent`
  semantics for asynchronous RPC results.
  https://mobly.readthedocs.io/en/latest/mobly.controllers.android_device_lib.callback_handler.html
- Fresh bench evidence from
  `evidence/run-20260906-1001/FAIL-test_wifi_direct_cold_start_election/`:
  both snapshots reported `wifi-direct-0: Connected`, while P1 logged
  `p2pSend ... no live socket (link=false, accepts=true)` and
  `transport: busy`; P2 later logged `security.replay_detected` for the first
  message ID. The same run later delivered a different message in each
  direction.

## Mechanism

The harness stops and restarts both engines, then immediately sends. IRIS's
transport state reaches `Connected` before the application-level framed socket
is attached. `sendText()` returns a message ID while the message engine queues
or retries the send. The harness waits only 6 seconds, treats the result as a
failed attempt, and creates a new message on the next loop iteration. The
original message may later reach the peer, so subsequent retries can be
rejected as replay/high-water traffic or produce misleading attribution.

## Decision

Change only the Mobly test observation path: create one message ID per
direction after cold start, then poll `awaitDelivered()` on that same ID until
the existing 60-second cycle budget expires. This preserves the hardware gate,
does not weaken the pass criteria, and makes the harness wait for the actual
delivery outcome rather than coupling success to socket-attachment timing.

Rejected alternatives: changing production retry or replay logic based on one
harness-observation failure, and sending new message IDs on every poll.
