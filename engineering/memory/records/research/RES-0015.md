**Lessons for IRIS (all Level 1, RFC 7748 §6.1 + the advisory set)**:
1. **X25519 all-zero shared-secret check is mandatory** (RFC 7748 §6.1) — hpke-rs was patched for exactly this class (RUSTSEC-2026-0072). IRIS `diffie_hellman` must reject an all-zero output.
2. **Validate ephemeral public key bytes** (32 bytes, clamped) before DH — libcrux-ecdh RUSTSEC-2026-0023.
3. **Ed25519 `verify_strict()`** (weak-key guard) is the only verification path — dalek docs + Ed25519 paper §7.1 / Scuttlebutt exploit (eprint 2019/526).
4. The libcrux advisory family (RUSTSEC-2026-0023/0024/0025/0026/0075/0124) is about **Cryspen's libcrux bindings**, a formally-verified alternative family; they are NOT the RustCrypto/dalek crates IRIS selects. Watch the naming confusion in reviews.

### 1.3 Constrained-node performance (Android, no AES-NI)

- ChaCha20-Poly1305: software ~200–400 MB/s on ARM Cortex-A55 (ring benchmark cited in ADR-0006) vs AES-256-GCM ~50–80 MB/s software (Bouncy Castle Android benchmark, ADR-0006 §Option A). ARX-only, no table lookups, constant-time by construction. IRIS workloads (P0 255 B … P7 50 MB) are trivially served; even 2 MB IMAGE at 200 MB/s ≈ 10 ms software AEAD. Level 3 estimate.
- Budget Android (Redmi 12 Helio G85, Realme C33 Snapdragon 680): Snapdragon 680 has ARMv8 crypto extensions, Helio G85 does not — the IRIS no-AES-NI assumption holds for the cheaper tier; ChaCha20 removes the dependency. Level 1 (ADR-0006) + Level 3 (numbers).
- Android Keystore: hardware-backed on API 28+ effectively guaranteed (source.android.com keystore doc); StrongBox SE since Android 9 for very sensitive keys (slower — use only for master/storage keys, not per-message ops); software-backed keystore unsupported below API 24 for hardware guarantee. Level 1.

## 2. Question 1 — DEC-P0001: per-session vs per-message ephemeral X25519 key

### Findings

- **DTN/IRIS media are asynchronous by design**: messages are individually routed, stored, and forwarded (store-and-forward; NASA DTN overview: "only the next hop needs to be available"; RFC 9171 semantics already in IRIS). A "session" — the classic interactive connection state machine — does not exist between an offline recipient and a sender operating during an outage. Recipient may reboot between messages; messages may be delivered out of order days apart.
- **Per-message ephemeral keys** (MESSAGE_ENVELOPE.md encryption_hdr: `ephemeral_pubkey` per message, random 12-byte nonce):
  - Stateless: no session bookkeeping, no counter persistence across reboot, no receiver-side session association problem.
  - Nonce uniqueness is per-message: fresh ephemeral key + random nonce per message → AEAD nonce collision risk is bounded per message (no multi-message counter to lose).
  - Sender-side forward secrecy: compromise of sender long-term key cannot decrypt past messages (each message used a fresh ephemeral).
  - No recipient-side FS (see Q4).
  - Cost: one X25519 DH + keygen per message (µs-scale on ARM — Level 3 estimate), no interactive requirement to decrypt.
- **Per-session keys** (ADR-0006 language): require a session handshake/context that both ends must reliably associate and persist; incompatible with asynchronous store-and-forward where the recipient is offline and a relay may hold the bundle for hours/days before contact. Counter nonce management across reboot risks nonce reuse (disaster: clock/power reset context — the exact GCM-class failure ADR-0006 §Option A warned about).
- **X3DH (Signal, Level 1 spec)**: designed precisely for async (Bob offline, published prekeys; one-time prekeys give Bob-side FS for initial messages). BUT requires a prekey distribution facility; Signal uses a central server with rate-limit protections (Prekey Pogo, USENIX WOOT 2025, Level 2 — depletion of one-time prekeys degrades PFS). IRIS has no trusted central directory in the disaster mesh; DISCO-001 capability exchange is 256 B (too small for a family of prekey bundles without new message types). X3DH is a v2 candidate, not v1.
- **Noise Protocol Framework (RFC unavailable; noise spec, Level 1)**: Noise_XX gives mutual FS + transcript DH with two round trips — requires interactivity; in DTN redshift, two or more round trips across opportunistic contacts mean the interlocutor must be reachable. Not v1 material for unidirectional bundle delivery; appropriate for a future relay-edge control channel (ORCH/daemon).

### Resolution (DEC-P0001)

**V1: per-message ephemeral X25519 (ECIES-like), matching MESSAGE_ENVELOPE.md.**
- ADR-0006 Issue 1 resolves in favor of the per-message design: the ADR's "per session" wording is corrected (the ADR's own line 137 demands the review settle this; the review does).
- Accepted trade-offs: no recipient-side forward secrecy (documented, Q4), one DH per message (µs-scale).
- Future (v2, BLK-0002): X3DH-style signed prekeys + one-time prekeys over DISCO-001 capability extensions + Double Ratchet for multi-message conversations when a session-like relationship emerges; re-evaluate when IDENT-001 trust + group key (type 15) land.

## 3. Question 2 — DEC-P0002: HKDF construction

### Findings

- **RFC 5869 HKDF is the Level-1 standard** (Informational; Krawczyk/Eronen). Used in TLS 1.3 (RFC 8446), HPKE (RFC 9180), IKEv2 (RFC 7296), Signal X3DH/Double Ratchet (Signal spec), WireGuard. Two-phase extract-then-expand; NB: unlike SP 800-108 PRF-KDFs, HKDF accepts non-uniform IKM (ECDH shared secret) — exactly the IRIS use case. Level 1.
- **HKDF-SHA256 security**: 2025 formal proofs of HKDF pseudorandomness (Hoang, ScienceDirect 2025, Level 2). TLS 1.3-grade analysis; RFC 5869 Appendix A has official test vectors (7 cases) for KAT.
- **HKDF-BLAKE3 is non-standard** (DISC-0002; FAIL-0003): HMAC-BLAKE3 is not an IETF construction; ADR-0006's "HKDF-BLAKE3" (line 98/155) must be corrected.
- **BLAKE3 native KDF**: `BLAKE3 derive_key(context, ikm)` is a *proper, spec'd KDF* (BLAKE3 spec) — not HKDF, no HMAC, built-in domain separation; fine for custom protocols but non-standard for auditability/interop; IRIS values RFC-standard lines (ADR-0006 §Context rationale: "IETF RFC status for auditability").
- **Crate**: `hkdf` (RustCrypto) implements RFC 5869 with PLAIN checkable vectors; `ring::hkdf` also implements HKDF-SHA256 as C code. RustCrypto HKDF-SHA256 is pure Rust, matches no-C dependency stance of iris-core.

### Resolution (DEC-P0002)

**V1: HKDF-SHA256 exactly per RFC 5869** via RustCrypto `hkdf` + `sha2` crates.
- Extract: `HKDF::new(Some(salt), shared_secret)` with a fixed domain-separation salt (constant, e.g. `b"iris-message-key-v1"`); Expand: info = message context (per-message: message_id + direction, or session context if per-session mode later) and 32-byte output.
- KAT: RFC 5869 Appendix A test case 1 (and 2-7 in unit tests where lengths vary).
- BLAKE3 remains for **non-crypto** hashing only (message_id derivation in PROTO-001, payload_hash envelope field 12, dedup Bloom) — keys never pass through BLAKE3. Documented deviation from ADR-0006 line 98/155 ("HKDF-BLAKE3" → HKDF-SHA256), noted as FAIL-0003 correction.

## 4. Question 3 — at-rest row encryption for STORE-001

### Findings

- **Threat**: PostgreSQL DB-level compromise (DB dump, backup theft, SQLi on admin path) exposes envelope rows: E2EE ciphertext + **plaintext metadata** (sender_id, recipient_id, timestamps, routing hints, priority). At-rest encryption protects metadata + ciphertext from DB/dump attackers, not from in-app compromise.
- **Android Keystore** (Level 1, source.android.com + developer.android.com): keys never leave TEE/StrongBox; hardware-backed effectively guaranteed API 28+; use for the node **master key** (non-exportable); StrongBox SE for the most sensitive key (slower — only master/storage key, not per-message); software-backed only as fallback on API < 24 (none of the target cheap Android fleet).
- **Patterns** (Level 1 docs, guardsquare 2026 level 3 corroboration): wrap/derive app keys from a Keystore-held master key; AES-GCM (Keystore-native) or ChaCha20-Poly1305 for the actual row AEAD; per-row random nonce/IV stored with ciphertext; never static derived IVs.
- **IRIS constraint**: STORE-001 is PostgreSQL (`iris-storage`, PgStorage), navigates DEC-0002 line 55 ("storage key derived from node master key — deferred to CRYPTO-001 gate").

### Resolution (Q3)

**V1 (land with CRYPTO-001)**: at-rest row encryption in `iris-storage` via an AEAD seal over the **envelope CBOR + signed sender_id/recipient_id/timestamp** columns.
- Storage key = `HKDF-SHA256(master_key, "iris-at-rest-v1")` (RFC 5869), where `master_key` is provisioned by IDENT-001: on Android, Android Keystore-held (TEE/StrongBox, non-exportable); on desktop, OS keychain or a local protected key file (DESKTOP-001 known_limitation path).
- AEAD: ChaCha20-Poly1305 (consistent with transport; constant-time on ARM) with **per-row random 12-byte nonce** stored alongside ciphertext. (AES-256-GCM via Keystore is the Android-native alternative — recorded as an implementation option; ChaCha20 keeps one AEAD across the stack.)
- Scope: encrypt `envelope_cbor` + `sender_id`/`recipient_id`/`timestamp` (metadata that leaks contact graph); routing/reap queries must operate on plaintext index columns ONLY (message_id, priority, ttl_seconds, expiry) — design constraint: **index columns stay plaintext; content/metadata columns sealed**.
- KAT: same RFC 8439 vectors; storage wrapper gets round-trip + tamper tests.
- Note: MESSAGE_ENVELOPE payload is already E2EE end-to-end (Q1); at-rest protects metadata graph + ciphertext-at-dump.

## 5. Question 4 — forward-secrecy honesty (DISC-0003)

### Findings

- **Truth**: per-message ephemeral sender key + **static recipient key** (ECIES-like) provides sender-side FS and passive confidentiality, but **NO forward secrecy against recipient long-term key compromise**: attacker who records ciphertext + cleartext `ephemeral_pubkey` (envelope header field 16) recovers all past plaintext after compromising the recipient's static X25519 key — ADR-0006 Issue 3, DISC-0003, Level 1 reasoning (Signal X3DH spec §4 security considerations: without one-time prekeys, compromise of IK_B + SPK_B exposes SK).
- **What provides recipient FS in async DTN**: X3DH one-time prekeys (Signal spec Level 1; Prekey Pogo WOOT 2025 Level 2 — depletion degrades PFS, needs rate-limited distribution we lack); Noise_XX round-trip ephemeral DH (needs interactivity); puncturable/forward-secure encryption research for DTN (Rüsch 2017 "Forward Secure Delay-Tolerant Networking", IBR-DTN + libforwardsec, Level 2 — message-key puncturing; complexity high, no battle-tested Rust crate).
- **IRIS honesty requirement**: ADR-0006 Issue 3 explicitly: "The documentation must not claim forward secrecy properties that this construction does not provide."

### Resolution (Q4)

**V1: document the ECIES limitation; do NOT claim forward secrecy against recipient compromise.**
- Security-model statement in CRYPTO_DESIGN.md + ARCHITECTURE docs: "v1 provides sender-authentication (Ed25519) + confidentiality against passive eavesdroppers + sender-side FS; it does NOT provide forward secrecy against recipient key compromise."
- v1 deliberately does NOT ship Noise_XX or X3DH (interactivity/mesh prekey-distribution not available; BLK-0002 v2 line).
- Mitigations in v1: recipient static key stored in Android Keystore (non-exportable; raises bar on compromise), keys rotate via envelope type 16 (KEY_ROTATION), optional key_id in encryption_hdr for future prekey/session keys.
- Redteam checkpoint (SECURITY_REVIEW stage) MUST verify no doc or code claims recipient-FS.

## 6. Synthesis — decisions feeding CRYPTO_DESIGN.md

1. **D1 (DEC-P0001)**: per-message ephemeral X25519, ECIES-like, per MESSAGE_ENVELOPE.md; ADR-0006 "per session" wording corrected.
2. **D2 (DEC-P0002)**: RFC 5869 HKDF-SHA256 (RustCrypto `hkdf`+`sha2`); HKDF-BLAKE3 rejected (non-standard); BLAKE3 stays non-crypto-only.
3. **D3**: at-rest row encryption in iris-storage; storage key HKDF(master_key,"iris-at-rest-v1"); ChaCha20-Poly1305 per-row random nonce; index columns plaintext, content/metadata sealed; master key in Android Keystore (TEE/StrongBox) / OS keychain on desktop (IDENT-001).
4. **D4**: FS honesty — no recipient-FS claims; recipient-FS is v2 (X3DH-style prekeys over DISCO-001 capability exchange / Double Ratchet; needs BLK-0002).
5. **D5 crates**: x25519-dalek 2.0.1 (+ curve25519-dalek ≥4.1.3), ed25519-dalek 2.x (verify_strict only), chacha20poly1305 0.10.1, hkdf 0.12 + sha2. ring 0.17.9+ documented alternative (single-impl, C-based). Mandatory hygiene: RFC 7748 §6.1 all-zero shared-secret reject; validate 32-byte X25519 inputs; ed25519-dalek verify_strict only.
6. KAT line-up for node acceptance: RFC 7748 §5.2/6.1, RFC 8439 §2.8.2, RFC 8032 §7.1, RFC 5869 Appendix A.
