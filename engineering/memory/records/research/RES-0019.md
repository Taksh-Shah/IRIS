## 1. Q1 — BLE mesh vs connectionless discovery for Android (2024-2026)

### 1.1 Connectionless primitives actually available
- **Advertising/Extended Advertising** (BLE 5.0+, Android 8+): the only universally-available connectionless channel on phones. Android exposes `AdvertisingSet`/`AdvertisingSetCallback`/`AdvertisingSetParameters`/`PeriodicAdvertisingParameters`; extended payloads up to 1650 B advertised (251 B legacy) via `startAdvertisingSet()`; runtime capability checks: `isLe2MPhySupported()`, `isLeCodedPhySupported()`, `isLeExtendedAdvertisingSupported()`, `isLePeriodicAdvertisingSupported()`. [Level 1, https://source.android.com/docs/core/connect/bluetooth/ble_advertising; https://developer.android.com/reference/android/bluetooth/le/PeriodicAdvertisingParameters]
- This directly supports IRIS's "advertise-parse" discovery model: a small signed discovery beacon (identity/PeerId short-id, service UUID, capability) over Extended Advertising; payload exchange over GATT once discovered. RES-0007's "production-ready-for-v1" verdict for this model is reconfirmed by the 2026 API surface (no API regression; Android 15 adds only AoA/AoD previews + payload length improvements). [Level 1, https://argenox.com/blog/whats-new-in-bluetooth-for-android-15]

### 1.2 PAwR (BLE 5.4) — the "connectionless bidirectional" option
- PAwR = Periodic Advertising with Responses, introduced Core Spec 5.4 (Jan 2023). One advertiser (Access Point/gateway) runs a periodic advertising train divided into **subevents** (≤128 per interval) with **response slots** (≤247 per subevent); synchronized observers wake on their assigned subevent, receive downlink, optionally respond, sleep. Scales theoretically 31,000+ nodes per AP; real deployments "hundreds to a few thousand". Period interval 7.5 ms-81.9 s; designed for coin-cell years. [Level 1 (Core 5.4), https://www.bluetooth.com/bluetooth-resources/periodic-advertising-with-responses-pawr-bidirectional-bluetooth-advertising-is-now-possible-2; Level 3 vendor guide, https://devzone.nordicsemi.com/guides/nrf-connect-sdk-guides/b/software/posts/periodic-advertising-with-responses-pawr-a-practical-guide; Level 4, https://novelbits.io/periodic-advertising-with-responses-pawr]
- **Limitations that disqualify PAwR for IRIS v1 peer-mesh**: (a) star topology — "all nodes must be in the range of the advertiser", spec does not define multi-advertiser networks; (b) **no multi-hop/relay** — "PAwR does not operate in a way where nodes can relay messages"; (c) "throughput is limited"; (d) role asymmetry: AP = broadcaster+central (mains-powered), tags = observer+peripheral. [Level 3-4, Nordic guide; novelbits]
- **Android phone role**: Android 14+ exposes *sync/receive* of periodic advertising trains (`PeriodicAdvertisingManager`/`PeriodicAdvertisingCallback`: `onSyncEstablished`, `onPeriodicAdvertisingReport`, `onSyncLost`), usable for a phone to monitor an ESL-style AP; but **no public API for transmitting in a PAwR response slot** — a phone cannot be a PAwR responder. Nordic's own DevZone answer on "PAwR with Android smartphones": "I am afraid this functionality is not built to be used with smartphones and is designed only for ESL use case". Hardware gating: needs `isLePeriodicAdvertisingSupported()` + PAST-capable controller (Snapdragon 8 Gen1+/Dimensity 9000+; API availability ≠ hardware capability — field reports of Pixel 6a sync failures on Android 14). [Level 5 vendor Q&A corroborated by Infineon AN (peer-only roles) + Zephyr `periodic_sync_rsp` sample (peer-echo via GATT-assigned slots, embedded only), https://devzone.nordicsemi.com/f/nordic-q-a/108981/ble-pawr-...; https://manuals.plus/m/2c73e5b37c... (Infineon CYW20829 AN); https://docs.zephyrproject.org/latest/samples/bluetooth/periodic_sync_rsp/README.html; Medium 2026 guide L5]
- Verdict for IRIS: PAwR is a **gateway/AP technology**, not a phone-peer mesh. Revisit as a future *gateway-to-sensor cluster* link (e.g., LORA/SAT gateway nodes with embedded radios), not for BLE-001 Android. Confirmed by Silicon Labs' 1500-node PAwR test network, built on embedded hardware, not phones. [Level 3, https://www.silabs.com/blog/bluetooth-pawr-in-large-scale-test-networks; https://www.bluetooth.com/blog/bluetooth-pawr-in-a-large-scale-test-network/]

### 1.3 Connectionless isochronous (BIS) as an alternative
- BLE 5.2 isochronous channels: CIS (connected unicast) + BIS (broadcast/connectionless). BIS = one-way synchronized broadcast to many receivers (LE Audio / Auracast); **no uplink** — "in connectionless communication, only the master will send a packet in each subevent"; retransmissions broadcast without receiver feedback; ISO interval 5 ms-4 s; broadcast security via LE Security Mode 3. [Level 1 (Core 5.2 via SIG), https://www.bluetooth.com/blog/10-frequently-asked-questions-on-le-isochronous-channels/; Level 3, https://novelbits.io/bluetooth-version-5-2-le-audio/, https://cloud2gnd.com/fundamentals-of-le-audio-connected-isochronous-streams]
- Android exposure is LE-Audio-oriented (`BluetoothLeAudio`, `BluetoothLeBroadcast`, `BluetoothLeBroadcastAssistant`; API 33+), stabilized/refined through Android 14/15; Auracast broadcast audio is the flagship use. Not a general-purpose bidirectional message bus. [Level 1, https://developer.android.com/develop/connectivity/bluetooth/ble-audio/overview; Level 3, Argenox Android 15 BLE; Level 5, Medium BLE LE Audio on Android]
- Verdict: BIS/RECORD on watchlist only; asymmetric, audio-centric, additional profile machinery — no IRIS v1 benefit over GATT+advertising.

### 1.4 Bluetooth SIG Mesh 1.1 — current status and Android support
- Mesh Profile 1.1 / Mesh Model 1.1 are adopted SIG specs: Remote Provisioning (RPR), Mesh Device Firmware Update (DFU) + BLOB Transfer, Enhanced Provisioning Authentication (EPA), Certificate-Based Provisioning (CBP), Private Beacons, subnet bridging, Directed Forwarding, Networked Lighting Control. Embedded stacks (Zephyr, nRF Connect SDK, ESP-BLE-MESH, Silicon Labs, ST) implement them. [Level 1, https://www.bluetooth.com/mesh-remote-provisioning/; https://www.bluetooth.com/specifications/specs/mesh-model-1-1/; Level 3, Nordic "Solving real-world challenges: new features of BLE Mesh 1.1"; Zephyr DFU docs; Espressif press release (first 1.1 supporter)]
- **Android (2026 status)**: There is **no native BLE Mesh API in AOSP** — the `android.bluetooth` package exposes GATT/LE advertising/scanner/BroadcastAssistant classes but no mesh module (official reference). Developer-grade mesh on Android = third-party stacks: Nordic nRF Mesh Android library (open source; the "most viable open-source starting point in 2026"), Silicon Labs `Bluetooth Mesh App`, STBLEMesh, Telink libs; the Bluetooth SIG reference stack exists "but is far less developer-friendly". A May/June 2026 community blog claims "Google finally baked proper BLE Mesh support into Android 14+ … `android.bluetooth.mesh` APIs" — **contradicted** by (a) official Android docs, (b) the same author's separate field report that mesh provisioning on Android "has always felt like an afterthought" and that native mesh APIs are "not coming anytime soon". This is an internal L5 contradiction — never rely on it; record as Gap G3. [Level 1 absence verified via developer.android.com; Level 4, https://github.com/nordicsemi/Android-BLE-Library & nRF Mesh; Level 5, Medium "BLE Mesh on Android in 2026" (claims native API) vs "BLE Mesh on Android: Why Your 2026 Tests Keep Failing" (denies it)]
- Verdict: v1 = no Mesh. It solves many-to-many flooding (vertical for IRIS's gossip), but it is a distinct protocol stack with its own security model (Network Keys, App Keys, provisioning) — not the IRIS `Transport` trait shape; INTERNET-001 pattern (framing on a point-to-point connection + app-layer envelope) does not map cleanly. DEFER to v2 as a possible alternate transport for fixed-node clusters; document Mesh 1.1 features (RPR/DFU/CBP) as the eventual provisioning story if adopted.

## 2. Q2 — DLEP (RFC 6841?) applicability to a BLE duty-cycled mesh

- **Spec correction**: the DLEP standard is **RFC 8175** ("Dynamic Link Exchange Protocol (DLEP)", Standards Track, June 2017), with extensions **RFC 8703** (Link Identifier) and **RFC 8757** (Latency Range). RFC 6841 — as cited in the research prompt — is **not** the DLEP specification (no IETF artifact with that title found in-session); recorded as a prompt-acronym correction, same pattern as RES-0018 G1 ("BBPATs"). [Level 1, https://datatracker.ietf.org/doc/rfc8175/, https://www.rfc-editor.org/rfc/rfc8703.html, https://www.rfc-editor.org/rfc/rfc8757.pdf]
- What DLEP actually is: a **control protocol between an IP router and an attached radio modem** — the modem tells the router link-quality metrics (data rate, latency, MTU, resource state) so Layer-3 routing can be radio-aware ("Radio Aware Routing"). It is explicitly router↔modem, **not** a mesh transport; operates over a single (possibly logical) hop; strongly associated with MANET routing (OLSRv2/MPR ecosystem); security guidance = secure the Layer-2 link (802.1AE/802.1X) + TLS/DTLS in networked deployments. [Level 1 RFC 8175 §6 metrics, §9; Level 3, Cisco Radio Aware Routing whitepaper, https://www.cisco.com/c/en/us/solutions/collateral/industries/radio-aware-routing-wp.html; Fraunhofer FKIE DLEP community-network paper, https://zenodo.org/records/7459]
- Applicability to IRIS: (a) On Android phones there is **no router/modem split** — the BLE controller is embedded; DLEP has no home. (b) BLE link metrics (RSSI, PHY, connection interval) are already visible to the app via existing APIs; a DLEP-style *metric transport* would be redundant. (c) For future gateway hardware (e.g., a LoRa radio attached to a Linux router on an IRIS relay), DLEP or RFC 5578 PPPoE is the standards-shaped way to feed L2 metrics into ROUTE-001/002 routing weights — DEFER as a routing-metric interface, not a transport. (d) DLEP's own caution: when the router-modem path is multi-hop/tunneled, RF stats can mislead routing — relevant if IRIS ever tunnels BLE over another transport. [Level 1 + Level 3 synthesis]

## 3. Q3 — Android BLE 5 coordinator/scanner/GATT/MTU/background constraints (2026 state)

### 3.1 Foreground service model (this defines "keep-alive" legality)
- FGS **types are mandatory** (Android 10+, enforced forward): BLE device management = **`connectedDevice`** type (API 34+); requires runtime `BLUETOOTH_CONNECT` + manifest `FOREGROUND_SERVICE_CONNECTED_DEVICE` (API 34+) + `FOREGROUND_SERVICE` + `POST_NOTIFICATIONS` (API 33+) + `BLUETOOTH_SCAN` (with `neverForLocation` where appropriate). [Level 1, https://developer.android.com/develop/background-work/services/fgs/changes; https://dev.to/ble_advertiser/... (L5 corroboration)]
- Android 16 (API 36): jobs spawned from an FGS must honor runtime quotas; user-initiated data-transfer jobs are the exempt path for user-visible data work; FGS enforcement/diagnostics tightened ("stricter categories", valid `foregroundServiceType`, notification throttling for excess). Android 17 (Q2 2026) reportedly hardens scan throttling + bonding + background-audio rules (L5 — treat as planning input, verify against official release notes at IMPLEMENT). [Level 1, https://developer.android.com/develop/background-work/services/fgs/changes; Level 5, Medium Android 16 FGS + Android 17 BLE breakdown]
- Implication for BLE-001 DESIGN: an IRIS Android node that must advertise/scan in background runs an FGS of type `connectedDevice`, with an explicit user-visible notification (emergency tool posture: user-initiated, long-running, shown). This is exactly the shape DESKTOP-001/BLK-0005 anticipated; DESIGN must declare the FGS contract as an AC (manifest + runtime + Android 16 quota notes).

### 3.2 Scanning constraints and batching
- Background scanning since Android 8 (API 26): background services short-lived; the sanctioned path is **filtered scans delivered via `PendingIntent`** (startScan with filters to a receiver — hardware-offloaded filtering keeps the radio active after process death intent only for matches). [Level 1, https://developer.android.com/reference/android/bluetooth/le/BluetoothLeScanner; https://developer.android.com/about/versions/oreo/background; Nordic Scanner Compat Library (L4)]
- Batch scanning: `ScanSettings.setReportDelayMillis() > 0` enables controller-side batching; results flushed via `flushPendingScanResults()` (API 21+); batched+abbreviated or ambient modes can require `BLUETOOTH_PRIVILEGED`; unfiltered scans stop on screen-off. [Level 1, BluetoothLeScanner/ScanCallback reference]
- Scan failures: `SCAN_FAILED_OUT_OF_HARDWARE_RESOURCES` (API 33+) and `SCAN_FAILED_SCANNING_TOO_FREQUENTLY` (API 33+); community-referenced ceiling ~5 start/stop cycles per 30 s before `SCAN_FAILED_APPLICATION_REGISTRATION_FAILED` (Android 17 enforcing more strictly). DESIGN must include **exponential-backoff scan-restart + explicit failure callbacks** (never blind restart loops — the #1 silent BLE failure). [Level 1, https://developer.android.com/reference/android/bluetooth/le/ScanCallback; Level 5, ProAndroidDev + Medium Android 17 scan-throttling]
- Discoverability duty cycle: default long-running scans degrade to opportunistic (~30 min); a loop scan/rest-scan duty cycle is the community-standard pattern for persistent discovery. [Level 5, ProAndroidDev; corroborated by Android docs' "long-running → opportunistic" behavior]

### 3.3 GATT/MTU
- MTU default is **23 bytes** and unchanged. Since **Android 14**: the stack requests **ATT MTU = 517** the first time any GATT client on an ACL calls `requestMtu`, and **disregards all subsequent MTU requests on that ACL** (Core Spec 5.2 adherence). Negotiated value = min(517, remote-supported). Legacy pre-4.2 peers that don't support Exchange MTU stay at 23; an early `requestMtu` error path ("Request Not Supported") was observed to wedge later GATT ops on some Android 14 devices (L5 field report). [Level 1, https://developer.android.com/reference/android/bluetooth/BluetoothGatt + https://developer.android.com/about/versions/14/behavior-changes-all; Level 5, Stack Overflow 77602246/77748472]
- Implication: IRIS should design payload segmentation for **≤512 B** ATT payloads (517-5 header), consistent with RES-0007/EMERG-001's 512-B ceiling; `onMtuChanged` must update the segmenter; treat MTU as negotiated-late (23 until the callback), never assume 512 up front. INTERNET-001's framing/backoff pattern transfers directly. [Level 1 + L4 internal]
- GATT client count: community reports of a ~32-client registration ceiling (stack state exhaustion after repeated start/stop without close) — no official documented number. Record as L5 constraint → DESIGN should **reuse a single GATT connection per peer** and `close()` promptly (official guidance) rather than churn connections. [Level 5, Stack Overflow 52142036; Level 1, Android gatt-server guide]

### 3.4 Periodic advertising sync (PAwR/PAST path — for future, not v1)
- Existing API: `PeriodicAdvertisingManager` + `PeriodicAdvertisingCallback` (`onSyncEstablished`, `onPeriodicAdvertisingReport`, `onSyncLost`); sync via PAST exists for LE-Audio broadcast assist. Hardware gating via `isLePeriodicAdvertisingSupported()`. [Level 1, AOSP PeriodAdvertisingManager + Android docs; Level 5 field confirmation Medium PAwR guide]

## 4. Q4 — 2024-2026 BLE/Android stack CVEs: regression checklist for BLE-001

- **CVE-2024-43770 (Critical, patched June 2024)**: out-of-bounds write in Android GATT server (`gatts_process_find_info` in `gatt_sr.cc`) → remote (adjacent) RCE with no user interaction. Directly in the ATT/GATT path BLE-001 uses. [Level 1, NVD + https://www.sentinelone.com/vulnerability-database/cve-2024-43770/ + https://www.cve.news/cve-2024-43770]
- **CVE-2025-0074 (March 2025 bulletin)**: Android SDP stack RCE, no user interaction (Android 15). [Level 1, SentinelOne cve-2025-0074]
- **CVE-2025-48539 (CVSS 8.0, exploited in the wild, Sept 2025)**: zero-click adjacent RCE via use-after-free in `acl_arbiter.cc SendPacketToPeer`; bypasses standard hardening; mitigation = kernel/Bluetooth module patches. [Level 1 NVD + Level 5 infosec writeup]
- **CVE-2025-22406 (8.4 HIGH, Android 15)**: use-after-free in BNEP (`bnepu_check_send_packet`) → local EoP/arbitrary code, no user interaction. [Level 1 advisory + securityvulnerability.io]
- **CVE-2025-44557 (vendor stacks)**: BLE pairing state-machine bypass via crafted `pairing_failed` (authentication bypass in BLE stack implementations). [Level 2/3, Ameeba security research summary]
- **CVE-2025-62235 (embedded, BLERP re-pairing)**: NimBLE re-pairing allows PK overwrite; Zephyr mitigates re-pairing downgrades. Relevant to any embedded BLE nodes IRIS later targets (LoRa gateways with BLE commissioning). [Level 2, NDSS 2026 BLERP paper PDF]
- **Takeaway for BLE-001**: The platform BLE stack is a *host-side* attack surface the app cannot patch (OS updates only). IRIS message security (envelope sign+encrypt, verify-before-forward, SEC-001 rate/ACL gates) must not depend on BLE link-layer or pairing security. ADOPT as DESIGN ACs: (a) verify every inbound frame's envelope before any state change; (b) cap advert payload size + parse defensively (adversarial tests on the advertise-parse path — the CVE pattern is parser/state bugs); (c) no auto-trigger actions from unauthenticated connectionless frames; (d) DOC: "BLE stack CVEs are OS-patch-gated — document required minimum Android security-patch level in deployment docs (mirrors BLK-0005 resource gating)". [Level 1 CVE evidence + L4 internal security stack]

## 5. Q5 — BLE relay attacks: do they matter for IRIS?

- **NCC Group (2022 advisory, sustained 2024-2026 relevance)**: link-layer relay of encrypted links, ≤8 ms added RTT, single connection event, defeats (a) GATT response-latency bounding and (b) link-layer encryption — the two standard mitigations for BLE *proximity authentication*. Bluetooth SIG response: relay is a "known risk"; mitigation direction = more accurate ranging (→ Channel Sounding). [Level 2/3, https://www.nccgroup.com/research/technical-advisory-ble-proximity-authentication-vulnerable-to-relay-attacks; ACM poster BLERelayGuard 2026 shows relay is still an active research topic, https://dl.acm.org/doi/10.1145/3812835.3814853]
- Relay threat model vs IRIS: IRIS does **not** do unlock-on-proximity or distance-based authorization; APP-layer envelope crypto protects message content regardless of link-layer relay. Residual risks: (1) a relay can declare two distant phones adjacent — affects *routing/topology* (peer appears in NeighborTable) but the messages themselves remain signed/encrypted and the IRIS routing stack already treats any peer as untrusted (SEC-001 reputation/routing-weight; ROUTE-002). (2) Relay can replay/carry discovery traffic — bounded by app-layer freshness/replay window (SEC-001 replay + dedup). Secure-position defenses (RTT/distance bounding) already REJECTED in RES-0018 for the no-GPS requirement; **Channel Sounding (Core 6.0+, 0.3-1 m, normalized attack detector, 6.2/6.3 security updates May 2026) is the standards-path future mitigation for distance claims — record as HARDWARE-gated future node, not v1** (phones with CS silicon only from ~2026-2027). [Level 1, Bluetooth CS test suite pdf https://files.bluetooth.com/wp-content/uploads/dlm_uploads/2025/05/CS.TS_.p2.pdf; u-blox CS intro; NewTec BT 6.0-6.3 security analysis; Home Assistant community (L5)]
- Just-Works pairing caveat: BLE security is independently weak under Just Works (MITM decrypt/relay demonstrated in 2025 MIT course report); IRIS should (a) not rely on pairing, (b) prefer OOB/QR pairing only for *commissioning convenience* (IDENT-001 verified tier), never as a security boundary. [Level 3, MIT 6.5610 report https://65610.csail.mit.edu/2025/reports/ble.pdf]

## 6. Q6 — iOS CoreBluetooth background (BLE-002 forward evidence)

- Background advertising on iOS: local name ignored; service UUIDs moved to a special **overflow area** discoverable only by iOS devices explicitly scanning; advertising frequency may decrease when all advertisers are background; scanning in background coalesces discoveries, ignores duplicates, may slow cadence; state preservation/restoration is the sanctioned resume path. **iOS 26+: apps with an active Live Activity continue background scanning with foreground privileges.** [Level 1, https://developer.apple.com/documentation/corebluetooth; https://docs.developer.apple.com/tutorials/data/documentation/corebluetooth.md]
- Implication: an IRIS iOS node cannot be a dependable background *advertiser*; BLE-002 must design iOS discovery around central-role + connection-first + Live Activity/state-restoration, and cross-platform discovery must tolerate iOS phones being invisible-in-background (Android-mdns-like asymmetry). [Level 1 + Level 5 StackOverflow corroboration]
- Note: iOS advertising also restricts manufacturers to local name + service UUIDs (no arbitrary custom manufacturer-data advertising from CoreBluetooth) — Android/iOS advert payloads are **not symmetric**; IRIS discovery payloads must fit the iOS-compatible subset for cross-platform discovery. [Level 5, irisclasson macOS/.NET field report 2026 — corroborates the cross-platform asymmetry]
