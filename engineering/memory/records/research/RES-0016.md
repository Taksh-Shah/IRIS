## 1. Question 1 — Device identity model + address derivation (DEC-P0005)

### Findings

- **IRIS has no BPv7 interop, but the BPv7 identity lesson applies**: BPv7 (RFC 9171) is a bundle *format* — it does NOT bind identity to keys. Whatever identity a bundle carries is asserted by the sender; authentication/authorization requires the separate BPSec security layer (RFC 9172). The IRIS flat envelope has the same property: `sender_id`/`auth_cert_chain` are asserted fields and are only trustworthy when the envelope signature (Ed25519, CRYPTO-001) verifies and the identity-to-key binding is enforced. Level 1.
- **Never derive identity from hardware/MAC — CVE-2025-53627**: Meshtastic's `NodeNum` was historically derived from the device MAC address. CVE-2025-53627 (published 2026-03, CVSS 8.2) documents that any attacker can forge/collide node identity (derive the NodeNum, spoof sender identity, abuse auto-reply confirmations). Maintainers are migrating node identity to *public-key-derived* IDs. This is a direct, current, real-world validation that IRIS must derive `PeerId`/`sender_id` from the public key, never from MAC/serial/hardware characteristics. Level 1 (primary CVE advisory).
- **libp2p PeerId = multihash of the protobuf-encoded public key** — the canonical key-derived self-authenticating identifier: identity-multihash form when the pubkey encoding ≤42 bytes (Ed25519 is exactly 32 bytes → in range). This is the pattern IRIS should mirror (with CBOR/IRIS wire bytes instead of protobuf). Level 1 (libp2p spec).
- **did:key** (W3C did:key method): self-describing DID = multicodec-prefixed pubkey (0xed = Ed25519) + base58btc. Elegant one-line derivation from an Ed25519 public key, no registry required. Relevant for RED-0008/SPKI-style semantics and any future DID interop; IRIS v1 does not need full DID resolution but should preserve derivation compatibility. Level 1 (W3C method spec).
- **Tor onion v3 address** = base32(sha3-256(pubkey)[..32] || checksum || version) — another precedent that a compact, key-derived identity is standard practice in anonymous/offline networking. Level 1.
- **Stable node UID vs key-derived PeerId**: BPv7 and libp2p practice separate the *persistent human/device label* from the *cryptographically-derived identifier*. A human-readable node name/UID is a convenience label (non-authoritative, may be duplicated); the PeerId/sender_id is the security-critical identifier. IRIS already uses `IRIS_NODE_ID` (per-process random, DESKTOP-001 known_limitation) — this becomes the *UID slot*, distinct from the key-derived PeerId.

### Resolution (DEC-P0005)

**V1: per-device Ed25519 identity keypair; PeerId/sender_id derived from the public key.**
- `sender_id` (16-byte field on the wire, MESSAGE_ENVELOPE) = first 16 bytes of SHA-256(Ed25519 public key) — deterministic, key-derived, self-authenticating. (Full 32-byte identity for the internal PeerId; wire sender_id remains 16 bytes per existing codec — RED-0010 codec revision already tracked.)
- 32-byte X25519 static key remains **separate and bound by signature** (DEC-P0009).
- Node UID (human label, e.g. `IRIS_NODE_ID`) is a distinct, non-authoritative convenience field; never used for authentication.
- No MAC/hardware-derived identity (CVE-2025-53627 lesson).
- DID-style derivation is preserved as a documented derived view (did:key-compatible multicodec 0xed), not a v1 requirement.

## 2. Question 2 — Key provisioning (Android Keystore / iOS Keychain / desktop / Pi) (DEC-P0006)

### Findings

- **Android Keystore / StrongBox**: hardware-backed keystore is effectively guaranteed API 28+ (source.android.com); StrongBox Secure Element since Android 9 for most sensitive keys. Operational numbers (KeyDroid, arXiv:2507.07927, 2025): StrongBox RSA-2048 keygen ≈ 9.2 s, 1 MiB AES-GCM ≈ 3 s → **StrongBox is for the master/KEK and identity keys only, never per-message crypto**; TEE (non-StrongBox) is viable up to ~5 MiB. Level 2 (paper) + Level 1 (docs).
- **AOSP keystore internal design validates DEC-P0004**: Android's keystore implementation itself derives AES-256-GCM super keys from master keys using **HKDF-SHA256** — the exact RFC 5869 pattern IRIS chose for `StorageKeySealer` (HKDF(master, "iris-at-rest-v1")). Level 1 (AOSP source primary) — strong independent corroboration of the CRYPTO-001 DEC-P0004 construction.
- **iOS Secure Enclave is NIST P-256-only**: Ed25519/X25519 keys CANNOT live in the Secure Enclave. Practice is to store them in the **Keychain** (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, hardware-backed via device passcode) and optionally wrap with a SE-attested P-256 key. Level 1 (Apple docs).
- **Raspberry Pi (relay/gateway class)**: no onboard TPM and **no measured boot**; external TPM modules (Infineon SLB9670/SLB9672) provide key sealing only, not attestation. Security without measured boot is limited to tamper-resistant storage. Level 1 (TPM vendor docs) + Level 3.
- **Stronghold (iota_stronghold v2.1.0, 2026)** — the Rust software vault used by IOTA/Wallet: XChaCha20-Poly1305 snapshot files + guarded in-memory key material; **ships with an explicit "not yet audited for security" warning** in its docs. Suitable as a *software exporter-free secret store*; NOT a hardware root of trust; treat as optional desktop convenience, not a security boundary. Level 1 (official docs) — post-2.1.0 external audit status unconfirmed (gap).
- **Desktop (RED-0001 target)**: OS keychain (Windows DPAPI / macOS Keychain / Linux secret-service) or a protected key file with restrictive ACLs. New Rust crates would be needed for OS-keychain integration (`keyring`) — RustSec audit in §6: no advisory at snapshot; kept as DESIGN-stage decision since RED-0001 needs desktop wiring.
- **Wrap pattern (all platforms)**: master key non-exportable where the platform supports it (StrongBox/TEE/Keychain); app keys (storage DEK) generated on device and wrapped with the master (AES-GCM KEK wrap, per Android best practice); per-row nonces already random (CRYPTO-001). Level 1/3 (developer docs + industry practice).

### Resolution (DEC-P0006)

**V1: per-platform provisioning; master key in the strongest available platform store; wrapped DEK pattern; sealed key directory.**
- Android: Ed25519 identity + master storage key in Android Keystore (TEE default, StrongBox-optional for master); ChaCha20-Poly1305 payload ops stay in-process (never StrongBox per-message).
- iOS: Ed25519/X25519 in Keychain (WhenUnlockedThisDeviceOnly), optional SE-wrapped P-256 wrapper.
- Desktop: OS keychain or protected key file (DESIGN decides crate: `keyring` vs Android-style file with ACL) — this is the RED-0001 wiring deliverable.
- Pi/relay: TPM available → seal; otherwise documented weaker posture (no measured boot); Stronghold optional software vault, never a root of trust.
- `StorageKeySealer::from_master_key(...)` (CRYPTO-001) is the provisioning target on every platform; at-rest sealing becomes default-on once IDENT-001 provisions the master key (currently OPT-IN `NoSealer`, CRYPTO-001 known_limitation).

## 3. Question 3 — Trust model (TOFU / pairing / QR / advertisement / chains) (DEC-P0007)

### Findings

- **TOFU is the decentralized-mesh baseline**: Meshtastic docs state trust-on-first-use is "a hard requirement" for a decentralized mesh — no PKI, no central directory; first-seen key cached, key change → user warning. IRIS is in the same class (no trusted central directory in a disaster mesh — also the DEC-P0001/X3DH constraint). Level 1/3 (project docs + code).
- **Briar BQP pairing (QR + X25519)**: out-of-band QR-commitment ("BQP" verifiable pairing) exchanges X25519 keys with an authenticated channel built by two-round QR scan; UI distinguishes **verified (3 bars) vs unverified (2 bars)** contacts. Tamarin formal analysis: the pairing protocols fail to provide key agreement against an active MITM *unless* a trusted PKI distributes signing keys — so QR verification is best-effort human-verified, still the strongest available primitive. Level 2 (USENIX/Briar spec/analysis) + Level 1 (spec).
- **SPKI/SDSI re-ratified as RFC 9804 (2025-06, Informational)** — authorization certificates where a *key* is the subject ("keyholder"), the address of record is a principal (SPKI "name"), and chains of authorization are key-signed. This is exactly the model for: RED-0005 (identity Ed25519 signs its X25519 static key advertisement → the keyholder certifies the key) + RED-0008 (`auth_cert_chain` field 18 = SPKI-style chain of authorization from a known keyholder). Level 1 (RFC 9804). Strong rule: *recent re-ratification, currently maintained spec line*.
- **ZI-CG / Vouchsafe (arXiv:2601.02254, 2026)**: zero-infrastructure capability-graph identity for offline networks (identity = capability publication, delegations by direct signing) — academic corroboration of the keyholder/capability model in offline settings. Level 2.
- **PRoPHET/DTN trust ≠ key identity**: the DTN/PRoPHET trust literature (RFC 6693, opportunistic-routing trust surveys) is about *routing reputation/blacklisting*, not key-identity trust. Do not conflate: routing reputation is a P3/route-selection concept; key-identity trust is the IDENT-001/auth_cert_chain concept. Level 1/2.
- **WebAuthn/FIDO**: passkeys use platform TEE/SE — same underlying keystore/TEE primitives as §2. Not directly applicable (no relying party in a mesh) but confirms platform key storage availability. Level 1.

### Resolution (DEC-P0007)

**V1: TOFU baseline + signed key advertisement (RED-0005) + optional QR/pairing for verified channels; UI must distinguish verified vs unverified.**
- First-seen key binds by TOFU; key change = warning (Meshtastic pattern).
- Higher assurance: QR/pairing-code exchange (Briar BQP style) marks a peer **verified**; the UI tier distinguishes verified/unverified (Briar 3-vs-2-bar lesson).
- RED-0005 signed key advertisement = SPKI-style (RFC 9804) cert: Ed25519 identity signs the X25519 static public key.
- RED-0008 `auth_cert_chain` validated as key-anchored chain of authorization (SPKI "keyholder" model), not a CA hierarchy.
- Routing reputation stays in ROUTE-002/SEC-001 scope — explicitly NOT an identity-trust input.

## 4. Question 4 — Rotation + revocation (DEC-P0008)

### Findings

- **BPSec RFC 9172 §6: key management explicitly out of scope**; RFC 9173 defines the wrapped-key security context (RFC 3394 AES key wrap) and **negative context IDs reserved for local use** — evidence that the IETF DTN ecosystem deliberately leaves rotation/revocation to the application. Level 1.
- **Offline rotation has a double-spend-like ordering problem**: Ceramic's canonical analysis (2022) — an offline network cannot authenticate *which* rotation event is newest; an attacker who compromises an old key can replay a convincing old rotation. Need versioned, monotonic, timestamp-independent ordering: **monotonic counters + valid-until windows + earliest-seen-wins** conflict rule. Level 2.
- **KERI (Key Event Receipt Infrastructure, IETF draft lineage)**: signed event logs with a **single root of trust = the inception event**; **null-rotation = revocation** (a signed "no key change" event with a new nonce); duplicate/equivocation detection via witness counters. The null-rotation concept is the clean primitive: revocation IS a signed rotation event that moves to an unusable key / increases a counter. Level 1/2.
- **ICN (Information-Centric Networking) revocation, 2026**: signed revocation announcements gossiped with sequence numbers; receivers discard keys from revoked senders even if content arrived earlier. Level 2.

### Resolution (DEC-P0008)

**V1: key rotation + revocation via signed rotation events with monotonic counters; KERI-style full event log = v2.**
- Reuse the existing envelope KEY_ROTATION path (type 16) with a **key-generation counter + valid-until timestamp + "earliest-seen-wins on conflict"**.
- Revocation = signed rotation event moving the identity to a placeholder "revoked" key (KERI null-rotation semantics), propagated like a normal signed advertisement (gossip/SCF path) so offline nodes converge.
- Long-term (v2): full KERI-style signed event log with equivocation detection (BLK-0002), fed by the same advertisement seam.
- CRYPTO-001's optional `key_id` in encryption_hdr (RES-0015 Q1/D1) becomes the routing key for multi-key state.

## 5. Question 5 — Identity ↔ X25519 key binding (RED-0005) (DEC-P0009)

### Findings

- **Ed25519-signs-X25519 is an established, deployed pattern**:
  - **Signal X3DH**: long-term identity keys sign prekey bundles; the original XEdDSA scheme (Curve25519-based signing) was used by Signal to sign X25519 keys with Ed25519-style signatures. Level 1 (Signal spec).
  - **Meshtastic 2.8.x**: packet signatures via XEdDSA (as of 2026 ~month 2-4) — the direct peer of IRIS, actively deploying Ed25519-on-Curve25519 key binding. (Merge/workflow status at this exact iteration is in flux — see Gap 2.) Level 4 (open source).
  - **IACR 2021/509** (Khan, "EdDSA for X25519" / curve to Ed25519 conversion paper): proves a secure conversion (curve25519-dalek's `EdwardsPoint::to_montgomery...` family) permitting Ed25519 keys to sign X25519 public keys directly. Level 2.
  - **LSEG (arXiv:2511.07548, 2025)**: Ed25519/X25519 same-key hardening analysis (HybridEd25519); confirms the same-key route is workable but requires "careful analysis" — the conservative recommendation remains **two distinct keypairs bound by signature**. Level 2.
- **Recommended binding**: Ed25519 identity keypair (signing, verify_strict-only per CRYPTO-001) signs the X25519 static public key in the key advertisement (SPKI-style, §3). No curve conversion, no XEdDSA complexity, crystal-clear key separation (identity vs encryption), verify_strict-only single code path.

### Resolution (DEC-P0009)

**V1: two distinct keypairs; Ed25519 identity signs the X25519 static public key (the RED-0005 advertisement).**
- No XEdDSA/curve-conversion in v1 (documented; XEdDSA is valid but carries the "careful analysis" caveat — LSEG 2025, IACR 2021/509).
- The signed advertisement IS the SPKI-style cert (RFC 9804 keyholder model) consumed by RED-0008 chain validation.
- Small-order rejection of remote X25519 keys (RED-0011) is defense-in-depth on top of this binding.

## 7. Synthesis — decisions feeding IDENT_DESIGN.md

1. **D1 (DEC-P0005)**: per-device Ed25519 identity; `sender_id` = first 16 bytes of SHA-256(pubkey); full hash = internal PeerId; UID is a separate non-authoritative label; no MAC/hardware derivation.
2. **D2 (DEC-P0006)**: provisioning per platform (Keystore/Keychain/OS-keychain-or-file/TPM); master in strongest store; wrapped-DEK; `StorageKeySealer` default-on; RED-0001 desktop wiring is the first consumer.
3. **D3 (DEC-P0007)**: TOFU + signed key advertisement (RED-0005) + optional QR/pairing for verified tier; UI verified/unverified distinction; RED-0008 = SPKI (RFC 9804) keyholder chains, NOT PKIX.
4. **D4 (DEC-P0008)**: rotation/revocation = signed rotation events, monotonic key-generation counter + valid-until + earliest-seen-wins; null-rotation semantics; KERI-style full log is v2.
5. **D5 (DEC-P0009)**: two distinct keypairs; Ed25519 signs X25519 static advertisement; no XEdDSA/curve conversion in v1; RED-0011 small-order rejection rides along.
6. **D6 crates/security posture**: no new crypto crates required by identity model; `keyring`/`android-keystore` are DESIGN-stage candidates (no advisories); AVOID PKIX/X.509 family (rustls-webpki RUSTSEC-2026-0104/0098/0099, pemfile RUSTSEC-2025-0134); monitor core2/thin-vec if they enter the tree.
