## 1. Q1 — DoS resistance on constrained DTN/mesh nodes (2024-2026 SOTA)

### 1.1 Standards/IETF position
- **RFC 9171 (BPv7) is the normative anchor for DTN congestion/rate control**: "the Bundle Protocol relies on the capabilities of protocols at the convergence layer to minimize congestion … convergence-layer protocols **MUST provide rate limiting or congestion control**." [RFC 9171 §6.9, Level 1, https://www.rfc-editor.org/rfc/rfc9171.html]. Direct textual support for placing per-node rate limiting at the mesh/convergence layer, which is exactly where IRIS's message engine sits.
- **RFC 9172 (BPSec)** defines security blocks (BIB/BCB) for integrity/confidentiality of bundles; its reuse of extension blocks means security processing happens *before* forwarding — the same "verify at relay" pattern IRIS already uses for emergency broadcasts. [RFC 9172, Level 1, https://datatracker.ietf.org/doc/rfc9172/]
- **draft-ietf-dtn-bp-sand-00 (Sipos & Deaton, Jan 2025)** — Secure Advertisement and Neighborhood Discovery: neighborhood discovery must be BPSec-secured, explicitly no insecure mode for discovery. Relevance: if IRIS adds neighbor/peer advertisements (reputation or liveness), they must be signed; unverifiable discovery messages must not be processed (mirrors IRIS verify-and-drop rule). [Level 3 (IETF draft), https://www.ietf.org/archive/id/draft-ietf-dtn-bp-sand-00.html]
- **RFC 9713** — "BPv7 Administrative Record Types Registry" (updated RFC 9171): BPv7 administrative records are now registry-catalogued. This is the closest resolvable artifact to the prompt's "BBPATs" (no IETF artifact named "BBPATs" exists; see Gap G1). [Level 1]
- **No IETF standard for DTN flooding/custody abuse** beyond the above: BPv7 moved custody-transfer procedures out of the core (RFC 9171 retains only the custody flag); there is no standardized "quench" for opportunistic forwarding. Anti-flooding in DTN remains academic/practice, not standards text (Gap G2).

### 1.2 Academic state of the art (DTN DoS)
- **Ansa, Cruickshank, Sun, Alshamrani — "A Security Scheme to Mitigate DoS Attacks in DTN" (J. Comput. Sci. Appl., 2017)**: the standard DTN DoS catalog: flood-based + resource-exhaustion DoS; their scheme = **ingress filtering (gateways) + rate limiting + lightweight bundle authentication ("DTNCookies")**; explicitly notes classic request-response DoS defenses are "highly interactive … assume persistent connectivity and hence not suitable for DTN". This validates IRIS's direction: stateless, single-pass, local filtering with no interactive handshakes. [Level 2/3, https://www.researchgate.net/publication/319398349]
- **Zekkori, Agoujil, Qaraai — "Effective Controlling Scheme to Mitigate Flood Attack in DTN" (IJACSA 12(10):749‑, 2021, DOI 10.14569/IJACSA.2021.0121083)**: survey of DTN flood control; highlights the **Claim-Carry-and-Check** scheme: each node has a per-interval **message-generation limit and per-message replica limit**; a violator generates a "claim"/alarm which receivers verify for inconsistency — i.e., *per-sender rate budgets enforced by verifiable claims*. ONE-simulator analysis shows buffer capacity/message lifetime/replicas dominate flood impact. Supports (a) IRIS per-sender budgets, (b) bounded replication factor, (c) storage bounds tied to TTL/lifetime. [Level 3]
- **"Epidemic Oracle" (Queen's University Belfast, IEEE ISCC 2025, DOI 10.1109/ISCC65549.2025.11326431)**: DoS mitigation by removing *delivered* messages from all buffers ("oracle") to free resources — a memory/CPU hygiene defense; validated against Epidemic and Spray-and-Wait under aggressive+stealthy DoS. Lesson for IRIS: delivery-receipt-driven cache eviction is a cheap DoS mitigator that complements rate limits. [Level 2]
- **MTF — "Mitigating Link Flooding Attacks in DTN" (IEEE, 2018)**: link-flooding (topology-harvesting) DoS treatment for DTN. Older, but the "flooding via relay links" mode maps to IRIS relay amplification. [Level 2/3, https://ieeexplore.ieee.org/document/8560242]
- **Altaweel, Aslam, Kamel — "Security attacks in Opportunistic Mobile Networks: A systematic literature review" (2024, JNCA; ScienceDirect S1084804523002011)**: systematically surveys **Blackhole, Wormhole, Sybil, DoS** in OMNs/DTNs (45 articles 2011-2023) and classifies defenses into Information-/Trust-/Crypto-/ML-/Statistical-/Filtering-/Graph-based; notes these four attacks are "easier to launch" in OMN and each has multiple modes. The best single 2024-vintage citation for the SEC-001 threat catalog. [Level 2]

### 1.3 LoRa-mesh practice (Meshtastic, Meshtastic CVEs, duty cycle)
- **Meshtastic is the closest deployed analog** (LoRa mesh, ESP32/nRF52, 256-byte packet limit, flood-with-suppression routing, dedup via (sender, packet_id) cache, CSMA/CAD before TX). [Level 4, https://meshtastic.org/docs/overview/mesh-algo/, https://meshtastic.org/docs/overview/security/]
- **Rate limiting is the deployed primitive, and its absence has been CVE'd**: **CVE-2024-47065 (fixed 2.5.1)**: traceroute responses were not rate-limited → a remote node could be made to respond continuously ("easily get 100 samples in ~2 minutes"; 2:1 reflected DoS). This is a Level-1 (NVD) confirmation that *per-request-response paths* must be rate-limited, not just message sends. [Level 1, https://nvd.nist.gov/, https://securityvulnerability.io/vulnerability/CVE-2024-47065]
- Community/implementation evidence of Meshtastic's per-message interval limiter: a firmware change imposed a ~2 s (implemented ~1.5 s) outbound message rate limit; BBS-style modules were observed dropping messages because of it — i.e., a *fixed per-node message cadence* is the existing LoRa-mesh answer to flood. [Level 4/5, https://github.com/SpudGunMan/meshing-around/issues/162]
- **Math of why LoRa-mesh flooding is self-limiting but CPU/buffer floods are not**: EU868 10% duty cycle (Meshtastic region docs; IRIS WPC 1% duty-cycle constraint per FAIL-0001/EMERG-001) bounds over-the-air volume; the residual DoS surface is **CPU (signature verify on garbage), buffer, and radio-wake**. [Level 4, https://meshtastic.org/docs/getting-started/initial-config]
- **Meshtastic CVEs as SEC-001 regression checklist** (all Level 1 advisory evidence): CVE-2025-24797 (buffer overflow via crafted protobuf → RCE, fixed 2.6.2 — *parser robustness is a DoS/CIA vector*); CVE-2025-55293 (packet amplification, fixed 2.5.6 — validation of header fields before rebroadcast); CVE-2025-21608 / CVE-2025-24798 (want_response=true crash — response triggering must be rate-gated); CVE-2025-52464 (cloned low-entropy keys — key hygiene); CVE-2026-42566 (NodeInfo forged via NodeID-not-key identity — see Q3). OpenCVE vendor list: https://app.opencve.io/cve/?vendor=meshtastic
- **LoRaWAN ADR**: adaptive data-rate is a *link-adaptation* mechanism (SF/airtime tuning), not a security rate limiter; ChirpStack/network-server join/ADR handling not verified in session → Gap G5. Do not cite ADR as a flood defense.

### 1.4 Proof-of-work — practical on LoRa-grade nodes?
- **No for the message TX path. Reasons (evidence-backed):**
  1. **Battery/CPU**: Hristozov, Huber, Sigl (Fraunhofer AISEC), "Protecting RESTful IoT Devices from Battery Exhaustion DoS Attacks" (arXiv 1911.08134): after analyzing puzzle schemes, "we consider puzzles unsuitable" — difficulty must match requester capability (weak devices can't solve, strong devices solve trivially) and puzzle outsourcing is possible; they prefer **per-requester rate limits (energy budget λ_th)** over PoW. [Level 2]
  2. **Measured crypto cost on constrained MCUs**: ECDSA signature generation measured at **~4.1 s on OpenMote**; exponentiation ~695 ms / 24.3 mA / ~13.7-16.9 mJ (Automated Analysis of Secure IoT Protocols, Tamarin/prover study). A "100 ms PoW" is already the budget of a signature; any meaningful PoW (100s of ms-s) is battery-hostile on coin-cell/farmer-class IRIS targets. [Level 2]
  3. **Duty-cycle coupling**: on IRIS's WPC 1%-duty-cycle LoRa the airtime itself is already the hard budget (FAIL-0001); PoW adds CPU cost without protecting the actual bottleneck unless verification is the cost — and signature verification is already the verifier cost. PoW would tax the *sender's* CPU while the defender's bottleneck is CPU+storage; a cheap-hash PoW (SHA-256 prefix) is asymmetric in the attacker's favor on botnet-class hardware and unfairly penalizes weak legitimate nodes. [Level 2 + Level 4 internal]
  4. **Client-puzzle literature for IoT confirms the same**: "Quantitative Analysis of DoS Attacks and Client Puzzles in IoT" (Springer 2017); Ralph Holz et al. comparison table (hash/cookie/time-lock/client-puzzle) notes client puzzles have linear communication overhead for hardness control and are problematic on 127-byte-MTU 802.15.4-class networks — the 512B IRIS envelope is the same regime. [Level 2]
- **Nuance that survives**: PoW as an *identity cost* (pay to mint an identity, not per message) is the path 2024-2026 research pursues — KeyChallenge (ICCTA 2024, PoW in key generation) and SyDeLP (2025, adaptive PoW, difficulty ↓ with reputation) (details in Q3). That variant costs little at message time and survives offline. **Defer to PROTO-001 v2; do not put per-message PoW in SEC-001.**
- **Token-bucket/leaky-bucket form on constrained nodes**: the standard form is a two-token-bucket "three-color marker" (srTCM RFC 2697: CIR/CBS/EBS; trTCM RFC 2698; RFC 4115 variant) — O(1) per arrival, two counters per (sender,class) bucket, no timers needed (refill computed lazily from elapsed time). This is exactly the shape IRIS's `SosRateLimiter` already uses (SingleSenderWindow) and generalizes to. [Level 1, RFC 2697/2698/4115]

## 2. Q2 — Replay protection beyond dedup (2024-2026 SOTA)

### 2.1 What dedup alone cannot do
- IRIS's current defense = message-id Bloom + exact LRU (`message_engine/dedup.rs`) — an *exact-content duplication* prevention with a tunable false-positive rate, not an *anti-replay* mechanism in the cryptographic sense:
  - **Reboot persistence**: `dedup.rs` Bloom persistence is explicitly **deferred to WP-2** ("Bloom-filter persistence to storage is a WP-2 follow-up (RES-0010 R5)", `message_engine/mod.rs:24`); REPLAY_PROTECTION.md's "serialized to SQLite on a background…" claim (line 81) is **NOT implemented** → [CONFLICT-3/4]. Across reboot, every previously-seen message-id is re-accepted by relays until re-observed via ForwardedCache (also memory-only).
  - **Not sender-scoped**: dedup is global (message-id), so it cannot detect *frequency* replay (same legitimate content replayed by the attacker at high rate after eviction, or replayed into a different relay chain).
  - **Message-id collision**: attacker-controlled message-id. Message-id is a truncated digest of the sealed envelope (≥128-bit SHA-256 truncation recommended; NIST SP 800-107 security-strength table: 128-bit truncation ≈ 2^64 birthday preimage resistance class; Bloom FP ~1% is the *acceptance* trade-off, already documented). An attacker can cheaply *collide within their own messages* (self-suppression → only harms attacker's own message; acceptable) but forging a collision against a *specific victim message* is second-preimage-class (2^128 for 128-bit truncation) — bounded by NIST SP 800-107 strengths. [Level 1, NIST SP 800-107 Rev.1 (2012); internal dedup.rs Level 4]
- **SOTA answer: layered replay defense = (1) exact dedup (fast path), (2) freshness window (timestamp skew budget), (3) per-sender monotonic sequence/counter where the sender is authenticated, (4) persistence of all three across reboot.**

### 2.2 Standards that supply the pieces
- **RFC 4303 (ESP) §3.4.3 + Appendix A — the canonical anti-replay sliding window**: receiver keeps window W; accepts seq only if > window and not already in bitstring; **"window size of 32 MUST be supported, 64 preferred"**; ESN (64-bit) Appendix A gives the high/low split + re-synchronization procedure (RFC 9827 renames the ESN transform type; RFC 6479 gives a bit-shift-free window implementation for high rate). **Applicability to mesh relays is limited**: IPsec windows are per unidirectional SA (single sender → single receiver with a shared key and per-SA counter). IRIS has no per-peer SAs; the *concept* transfers only to pairwise keyed links (LoRa neighbor links with a derived per-link key could use a 64-512 entry window). For store-carry-forward multi-hop without pairwise keys, per-sender *signed* counters + freshness is more faithful. [Level 1, RFC 4303, RFC 6479, RFC 9827]
- **RFC 9171 §4.2.7 — Creation Timestamp**: every bundle carries **"(bundle creation time, monotonically increasing sequence counter)"**; the seq counter MAY reset when the time advances by a millisecond — i.e., BPv7 itself defines the *time + monotonic-counter* lexica that make (time,seq) a globally unique replay-detectable identifier. IRIS message-id + timestamp already mirrors this; the missing piece is *verification of uniqueness at the endpoint* (not just relays) against a persisted high-water mark. [Level 1]
- **RFC 7181 (OLSRv2) §23.2 — replay of authenticated control traffic is explicitly identified (situation 9)** and the fix mandated: "to prevent routers from repeating old (and correctly authenticated) information … additional information is required (e.g., a timestamp or sequence number), allowing a router to positively identify such replayed messages." RFC 7182 (ICV + Timestamp TLVs) and **RFC 7183 (mandatory security = HMAC-SHA256 + timestamp TLV for NHDP/OLSRv2)** make timestamp+HMAC the *normative* MANET replay defense (Level 1, MANET). RFC 7859 extends to identity-based (non-shared-key) signatures. This is the single most transferable standard precedent: **sign the (message-id, timestamp, seq) triple** → relay verifies signature before honoring freshness (already IRIS verify-before-forward pattern).
- **MITRE EMB3D MID-037 (2026)**: timestamps reject "too old" data, "another indicator of a replayed message"; complements nonce caches (MID-036). Practice-level confirmation that freshness windows are a first-class control on embedded systems. [Level 3]
- **Webhook/nonce-cache practice (Level 5, corroborating)**: timestamp window alone is necessary-not-sufficient (replays inside the window succeed); nonce cache closes the window; **"no protection if the cache is cold after a restart"** — the same cold-cache-across-reboot hole IRIS has today. Persisting the nonce/dedup state is the standard fix. [Level 5, e.g., gethook.to webhook replay analysis 2026]

### 2.3 Replay across reboot → persistence requirements
- Persist, with crash-safe batching (flash-wear conscious, not per-message):
  1. **Dedup snapshot** (Bloom bit-array + LRU entries) — the already-deferred WP-2 item, promoted to a SEC-001 requirement. REPLAY_PROTECTION.md already specifies the serialization shape (Bloom + LRU → SQLite/WP-2 store); it must be *implemented and tested for reboot* (acceptance: replay after reboot rejected).
  2. **Per-trusted-sender high-water mark** = max (last timestamp, last seq) seen *accepted-and-verified* per sender identity; a message with (ts,seq) ≤ high-water is replay-dropped. This is a per-sender unidirectional "ESP window" bound to the identity key, not to a pairwise SA — RFC 4303 window logic without the SA machinery.
  3. **Freshness window τ** (e.g., signed timestamp within [now-τ, now+skew]): reject too-old (replay) and too-future (clock attack; DOS_RESISTANCE.md already has "timestamp > now+30min → DROP"). Time-source caution: IRIS is offline; τ must tolerate clock drift between reboots (per-source skew budget, RFC 9171 uses DTN time = arbitrary epoch precisely because wall-clock sync is not assumed — adopt DTN-time-like monotonic clock + signed offsets instead of demanding NTP-grade sync).
- Fragment replay (RFC 9171 fragment timestamp/offset; IRIS `fragment.rs` restores message_id at reassembly): reassembled fragments must re-enter the same dedup/freshness pipeline, otherwise a replayed fragment chain reassembles a replayed message after per-fragment dedup eviction. [Level 4 internal + Level 1 RFC 9171]

### Q2 adopt-defer-reject
- **ADOPT**: freshness window on every inbound message (pre-verify, cheap) with per-source skew budget.
- **ADOPT**: per-sender high-water (last signed (ts,seq)) for trusted identities — RFC 4303 window concept, RFC 9171 lexica, RFC 7181 §23.2 rationale.
- **ADOPT**: persist dedup snapshot + high-water marks (promote WP-2 item); crash-safe batched writes; test reboot replay.
- **ADOPT**: message-id = ≥128-bit SHA-256 truncation over sealed envelope + (ts,seq) — collision analysis per NIST SP 800-107; attacker self-collision acceptable, victim-second-preimage infeasible.
- **DEFER**: per-link pairwise SA + full IPsec ESN windows — only if IRIS later adds link-layer encryption; not needed now.
- **[CONFLICT-3/4]** REPLAY_PROTECTION.md SQLite-persistence claims vs `mod.rs` WP-2 deferral; Bloom "0% false negative" claim coexists with documented ~1% FP and 24h reset — docs must state the reset/window semantics precisely.

## 3. Q3 — Sybil mitigation for an open mesh (2024-2026 SOTA)

### 3.1 The fundamental result (confirmed, not just folklore)
- **Douceur, "The Sybil Attack", IPTPS 2002**: without a central identity authority or resource-tied identity cost, an adversary can create arbitrarily many identities; **any defense keyed on *per-identity* quotas or votes is defeated at cost ≈ 0**. This is the formal basis for rejecting "per-identity rate limits" as the *sole* Sybil defense — exactly what SYBIL_RESISTANCE.md already acknowledges ("attacker with 100 physical devices generates 300 SOS/hour…") and what SEC-001 must not regress to. [Level 2]
- **Consequence for IRIS (as requested)**: *confirmed* — per-identity rate limits (the Q6(a) limiter) are **necessary but not sufficient**; they become an *identity-cost* mechanism only when identity creation is expensive/bounded. [Level 2 derived]

### 3.2 SybilGuard/SybilLimit lineage and its successors
- **SybilGuard (Yu et al., SIGCOMM 2006)** and **SybilLimit (Yu et al., IEEE/ACM ToN 18(3) 2010, DOI 10.1109/TNET.2009.2034047)**: decentralized defenses assuming **social-network topology with fast mixing**; bound accepted Sybils per *attack edge* (SybilLimit O(log n) per attack edge). **Critical limitation for IRIS**: the guarantees rest on a *connected, fast-mixing honesty region*, attack-edge counting, and many verifier walks — none of which hold for a sparse, partitioned, emergency-time DTN mesh with few or zero social edges. 2024-2026 successors (e.g., SoK "evolution of sybil defense via social networks" catalogued in Altaweel 2024) keep the social-graph assumption. [Level 2]
- **KeyChallenge (Solat, ICCTA 2024, DOI 10.1145/3674558.3675767)**: Sybil mitigation by *proof-of-work during public-key generation* (constrained character ranges over ECC keys) — identity minting cost, no per-message cost, no server. Offline-compatible in principle. [Level 3]
- **SyDeLP (Mosqueda González et al., 2025, hal-05002718)**: **Adaptive PoW** — fresh identities pay high PoW, identities with accumulated good reputation pay less (blockchain-backed in their setting). Directionally right for IRIS (identity cost + reputation-based relaxation) but needs a ledger/consensus IRIS does not have → defer. [Level 3, cited via secondary; primary: https://hal.science/hal-05002718]
- **Ostra (Mislove, Post, Druschel, Gummadi — NSDI 2008)**: pairs each *trust link* with a **link credit balance**; a sender who sends unwanted traffic drains credits on links in its trust chain, and link formation is the costly/bounded resource. **This is the most IRIS-compatible Sybil-aware spam control**: it binds send capacity to *social links* (which IRIS's TOFU + verified pairing can approximate as "verified contacts"), not to identity count, and requires no global auth. Ostra explicitly rejects "strong user identities" (impossible offline). **Adopt as the conceptual model for budget = f(trusted links), not f(identity count)**. [Level 2, https://www.usenix.org/legacy/events/nsdi08/tech/full_papers/mislove/]
- **CAPTCHA-equivalents / badge servers offline**: CAPTCHAs require human round-trip + a challenge generator; badge/registration servers require an online authority at enrollment — both are operationally unavailable in IRIS's no-infrastructure scenario and are rejected by the DTN literature (interactive schemes unsuitable — Ansa et al.). Verified-pairing (below) is the offline-compatible substitute. [Level 2 consolidation + Level 3]

### 3.3 Trust bootstrapping as Sybil defense (2024-2026 practice)
- **Briar — Bramble QR Code Protocol (BQP)**: verified contact via **in-person QR scan** (commitment to ephemeral pubkey + transport descriptors, both parties scan, mutually derived key). This is the deployed *offline identity-cost* primitive: forging an identity costs a physical meeting. Briar's security audit (OTF 2024) flags **OTF-005**: contacts added remotely ("introduction"/links) cannot later be promoted to verified — a known trust-tier gap (adopt: annotate trust tiers; IRIS RED-0008 verify_chain cap 8 already tiers). ETH "Cryptography in the Wild: Briar" (thesis) formalizes BQP and notes the introduction-client MITM limits. [Level 3/2, https://www.opentech.fund/security-safety-audits/briar-security-audit/, https://ethz.ch/…report_YuanmingSong.pdf]
- **Meshtastic counter-example (why key-bound identity matters)**: Meshtastic node identity = NodeID from MAC, **not bound to the public key** → **CVE-2026-42566**: an attacker forges NodeInfo (HAM mode) to overwrite NodeDB, forcing DMs back to channel-PSK and hijacking node metadata (patched 2.7.6). Also **CVE-2025-52464**: cloned/low-entropy keys let attackers decrypt DMs. Lessons: (1) *identity must be the key* (IRIS IDENT-001 does this — good); (2) *key hygiene must be tested* (SEC-001 acceptance). [Level 1 advisory + Level 4]
- **TOFU + SPKI key-anchored chains (RFC 9804, 2025-06 re-ratifying SPKI/SDSI)**: subject = key "keyholder"; authorization chains are key-signed — IRIS IDENT-001 RED-0008 model is the correct Sybil *boundary* (it does not prevent identity creation, but it makes every identity a *key* with a verifiable chain, enabling per-key budgets and revocation). [Level 1]
- **D2D/NS (device-to-device network security) 2024-2026 results**: the OMN SLR (Altaweel 2024) catalogues Sybil defenses in D2D/OMN; no consensus-busting offline breakthrough found; the recurring viable pattern is *resource/identity cost + social/verified links + reputation*, exactly the IRIS-proposed stack. [Level 2]

## 4. Q4 — Spam/abuse resistance, reputation, emergency-only send permissions

### 4.1 Reputation for DTN without central authority
- **Watchdog + Pathrater (Marti, Giuli, Lai, Baker — MobiCom 2000)**: the foundational local misbehavior detection: promiscuous observation of neighbors' forwarding ("watchdog") + path rating. Direct observations are **hard in DTN** (intermittent contact, no always-on promiscuity) — the DTN-specific adaptation is *second-hand evidence with confidence weighting*:
  - **iTrust (Zhu, Xu, Liu et al., IEEE TPDS 2014)**: *probabilistic* misbehavior detection — nodes send destination-bound status / receive random audits; detection without continuous observation, exactly for DTN's contact scarcity (their "probabilistic check + detection probability" model). [Level 2]
  - **ITRM (Ayday & Fekri, ISIT 2009; journal version with DTN trust management)**: iterative reputation computation robust to malicious raters; explicitly evaluated in DTN vs Bayesian (CONFIDANT-style) and EigenTrust; shows DTN trust is buildable from *weighted indirect measurements* but converges slowly — reputations are *long horizon*, not instant access control. [Level 2]
  - **CONFIDANT (Buchegger & Le Boudec 2002)**: monitor + reputation + trust-manager + path-manager; exchanges of second-hand observations; **CORE (Michiardi & Molva 2002)** adds the important rule: *only positive observations are exchanged* (prevents false-frame DoS). Adopt CORE's "don't propagate negative gossip" rule. [Level 2]
  - **2024-2026 continuation**: Reputation-based AODV for blackhole/malfunction detection (Yaseen, Aldwairi & Manasrah, *Computers, Materials & Continua* 80(2) 2024, DOI 10.32604/cmc.2024.051179) — watchdog/pathrater aggregation with reputation tables + aggregators: modern evidence that *local watchdog + terse reputation exchange* still is the state of practice for mesh. [Level 2]
- **IRIS-fit conclusion**: reputation = (1) local forwarding observation where physically possible (watchdog), (2) second-hand scores exchanged only from *verified* peers with CORE-style positivity, (3) iTrust-style probabilistic audits as a lightweight alternative to continuous monitoring, (4) **routing weight input, not an admission gate** (a low-reputation relay in a disaster mesh must still be usable when it is the only path — otherwise the reputation system becomes a DoS tool). [Level 2 synthesis]

### 4.2 Bayesian spam filters for short messages
- SMS-scale evidence (140-160 char messages — same order as IRIS ≤512B): SVM outperforms Naive Bayes on SMS spam (bi-level SMS classification, IAJIT 14(4) 2017); **BERT+NaiveBayes reaches 97.31% accuracy with 0.3 s inference** (Oyeyemi & Ojo, arXiv 2406.06578, 2024); classic Bayesian short-message filtering has a persistent **false-positive problem** (Cormack, Hidalgo, Sánz, "Spam Filtering for Short Messages", CIKM 2007). [Level 2/3]
- **IRIS-fit conclusion**: content filtering is *possible* on 512B payloads but (a) costs CPU on every relay — and CPU is a DoS surface (see Q1); (b) FPs on emergency-adjacent content are intolerable. **Recommend: receiver-side/UI-only scoring (user-visible "likely spam" tag), never relay-side hard drops; keep the machine-filter class disjoint from P0-P3.** This matches the SPAM_RESISTANCE.md design spirit while fixing its implementation gap. [Level 2 + Level 4 internal]

### 4.3 Emergency-only send permissions — who may send alert-class messages
- **World practice is authority-gated signing, not capability gating**:
  - **CAP v1.2 (OASIS 2010)**: alert XML carries an XML-DSig `<signature>`; FEMA IPAWS and national systems sign CAP-alert payloads. [Level 1, https://docs.oasis-open.org/emergency/cap/v1.2/CAP-v1.2-os.html]
  - **EU-Alert / ETSI TS 102 900 §5.5**: Cell Broadcast provides **NO subscriber/UE authentication** — the reason spoofing persists; hence WEA literature. [Level 1]
  - **CACM 2023 — Ha et al., "Securing the Wireless Emergency Alerts System"**: practical WEA spoofing; mitigation = **Ed25519 signatures + pre-provisioned key**, ≈68 B overhead per alert — the same verified-at-every-relay + preloaded-anchor model IRIS already built (EMERG-001, RES-0017). [Level 2]
  - **SPKI / RFC 9804**: authority = key; chains of authorization (EMERGENCY_GOVERNANCE National→State→District→Local) are key-signed — the mechanism for "who may sign emergency-class", i.e., **RED-0002 ACL-1 = allowlist of authorized signing keys/roles, offline-verifiable, revocation via signed rotation** (IDENT-001 already implements rotation/revocation). [Level 1]
- **IRIS-fit conclusion**: emergency send authorization = **authority-anchored signing chains + per-role ACL-1 + rate-limited (authoritative broadcast cadence, non-authoritative SOS 3/hr) + mandatory relay only after chain+signature verify**; relay drops unverifiable emergency-class silently. This is already the implemented `emergency/authority.rs verify_authoritative` + `rate_limit.rs` + `broadcast.rs` pattern — SEC-001's job is to *extend the ACL-1 gate to all authority classes (P0 broadcast, P1 medical, P2 location-as-emergency)* and add the acceptance tests. [Level 1 + Level 4]

### Q4 adopt-defer-reject
- **ADOPT**: reputation = local watchdog + verified-second-hand + iTrust probabilistic audits; CORE positivity rule; **routing weight only**. Implementation: new `reputation.rs` scoring module (no global broadcast).
- **ADOPT**: receiver-side spam scoring (Bayesian/ML as UX tag, classes disjoint from P0-P3); no relay-side content drops.
- **ADOPT**: emergency ACL-1 = SPKI key-anchored allowlist + signed chains + verify-before-relay (already built; extend + test).
- **REJECT** (for now): global reputation consensus (ITRM-style iterative is per-node), EigenTrust-style global trust, reward/credit tokens (needs ledger).
- **[CONFLICT-5]** SYBIL_RESISTANCE.md/THREAT_MODEL.md describe reputation-based relay deprioritization and anomaly detection as if implemented — no reputation module exists; docs must be corrected when `reputation.rs` lands.

## 5. Q5 — Secure-position / wormhole / blackhole (2024-2026)

### 5.1 Wormhole / blackhole in MANET lineage (Level 2)
- **Systematic review 2024**: Altaweel et al. (OMN SLR, JNCA 2024) — Blackhole/Wormhole/Sybil/DoS in OMNs/DTNs; defense categories Information-/Trust-/Crypto-/ML-/Statistical-/Filtering-/Forbidden-topology-/Graph-based; multiple modes per attack. [Level 2]
- **Wormhole detection 2024-2026 (AODV-family)**: EAODV-ARP (Huang, Raad, Tubbal, Odeh — *JNCA* 243, 2025, DOI 10.1016/j.jnca.2025.104283): lightweight wormhole detection from ARP neighbor awareness (RTT/hop-count/DEV analysis), no extra hardware — note: **RTT-based detection is unusable in DTN** (no timely round-trips); the *structural* (neighbor-relationship) parts transfer. RL-based multi-attack detection (Chourasia & Tokekar, IC4 2024, DOI 10.1109/IC457434.2024.10486553) and Twofish+multi-factor (CCWC 2024) are crypto/heuristics variants — mostly not DTN-applicable. [Level 2]
- **Blackhole in DTN specifically**: "A Study of Black Hole Attacks in DTN" (Springer LNCS, 2021) catalogs blackhole variants in store-carry-forward; **reputation-based protocol against blackholes in DTN** (Dini & Lo Duca, *Ad Hoc Networks* 2012) — reputation + watchdog-style detection for DTN forwarding; iTrust (TPDS 2014) is the modern detection method under scarce contact. [Level 2/3]
- **OLSRv2/MP2P security — the standards layer (Level 1)**: RFC 7181 §23 (Security Considerations) + RFC 7182 (ICV + timestamp TLVs) + **RFC 7183 (MUST: HMAC-SHA256 + timestamp for control messages)** + RFC 7859 (identity-based signatures). For MPR-based flooding (MP2P), the mandatory security baseline is: *authenticated control traffic + replay freshness* — the two pieces IRIS already has for messages; if IRIS ever adds OLSRv2-style topology control messages, RFC 7183's HMAC+timestamp pattern is the conformance target. Note RFC 7183 itself assumes **router time synchronization** (POSIX time) — IRIS must substitute DTN-time/monotonic epochs for offline operation. [Level 1]

### 5.2 Attacks that transfer to a store-carry-forward mesh with NO GPS
- **Blackhole (drop-all) / gray-hole (selective)** — **transfers fully**; is the dominant DTN forwarding attack (drop after store). Mitigations that transfer: (1) multi-copy (replication) routing already inherent in IRIS gossip — the SLR repeatedly notes replication is the natural DTN resilience to blackholes; (2) delivery-Ack-based feedback (IRIS ack.rs; "delivered→evict" oracle pattern, Epidemic Oracle ISCC 2025); (3) reputation scoring of relays (Q4); (4) **detection is a *secondary* goal — the primary defense is not depending on any single relay** (ADVERSARY_MODEL.md already states this).
- **Wormhole / tunneling**: partially transfers. A wormhole *tunnel* between two far relays can attract traffic and replay it (bandwidth amplification) — but IRIS's flood-with-hop-limit + ForwardedCache dedup largely neutralize the topology-attraction benefit; and without GPS/round-trips the RTT/location detectors do not apply. What transfers: *neighbor-relationship plausibility* (announced neighbor sets verified by signed liveness exchanges) — defer; and *hop-count integrity* (signed hop count; an attacker cannot forge verified hops) — adopt as cheap invariant.
- **Secure-position schemes (SPS)**: literature (Capkun et al.; DelPHI; LiteWorp/MobiWorp) assumes location claims or ranging hardware; **IRIS explicitly has no GPS requirement** → SPS-direction = **reject**, except signal-based plausibility (SNR/geographic sanity of hops) which is defensive heuristic only (ROUTING_ATTACKS.md anomaly ideas) — mark as heuristics, not security guarantees.
- **Opportunistic hijacking (CollusiveHijack, Altaweel et al. 2022, IEEE TDSC)**: malicious relays steer traffic by colluding; in IRIS, bounded-hop gossip + dedup + addressability limits the damage; the SLR places it under trust-detection (reputation) classes. Adopt reputation-weighting as the counter.

### Q5 adopt-defer-reject
- **ADOPT**: blackhole/gray-hole resistance = replication + Ack-driven eviction + relay reputation weight (no single-relay dependency); acceptance: relay-drop adversarial tests.
- **ADOPT**: signed hop count / freshness on control-like messages; verify-before-forward (already core).
- **REJECT**: RTT/location-based wormhole detectors; SPS; GPS-derived plausibility as a guarantee (no-GPS requirement).
- **DEFER**: neighbor-relationship plausibility exchange (SAND-style signed neighbor validation, draft-ietf-dtn-bp-sand) to PROTO-001 v2; OLSRv2-style topology control messages to a future routing-security node.
- **ADOPT (doc)**: RFC 7181 §23/RFC 7183 as the conformance citation for control-message integrity IF IRIS adds topology control (note POSIX-time assumption vs DTN-time substitution).

## 6. Q6 — Practical integration into IRIS (minimal-evidence-backed design)

### 6(a) General in-engine per-message-class rate limiter (per-peer; P0 exempt from drops)
**Design**: token-bucket (srTCM, RFC 2697) per (sender_key, priority_class): bucket cap = 2× rate (burst), lazy refill from wall/monotonic time; silent drop on overflow (no error to sender, no negative-ack). Mapping: one bucket per (sender,class) pair is bounded by (contacts × classes) for trusted peers; unknown senders share a single "unknown" aggregate class bucket (this is where Sybil shows — see Q3). **P0/P1 exempt from dropping** (only queue/CPU priority + emergency SosRateLimiter 3/hr applies) per priority-isolation guarantee (P0-P2 reserved queue/storage; DO NOT remove the emergency guard).
**Prior art**:
- RFC 9171 §6.9 "CL MUST provide rate limiting or congestion control" [L1]
- RFC 2697/2698/4115 token-bucket markers [L1]
- DTNCookies rate limiting + ingress filtering, no-interaction (Ansa 2017) [L2/3]
- Claim-Carry-and-Check per-interval message/replica budgets (Zekkori 2021) [L3]
- Meshtastic per-message cadence (~2 s) + CVE-2024-47065 response rate-limit [L1/L4/5]
- Existing `SosRateLimiter` (emergency/rate_limit.rs) as the shape to generalize [L4]
**Verdict: ADOPT.** Deploy at message-engine ingest (all classes), before CPU-expensive verify where possible (length/class gates need no signature), conservatively after verify for trusted-sender budgets (attacker cannot burn buckets for others).

### 6(b) Cross-reboot replay persistence
**Design**: (1) promote dedup Bloom+LRU persistence from WP-2 to SEC-001 (batched, crash-safe writes; report REPLAY_PROTECTION.md's SQLite shape); (2) per-trusted-sender high-water mark (last verified (ts,seq)) — RFC 9171 creation-timestamp lexica; (3) freshness window τ with per-source skew budgets; (4) on restart: load snapshot → reject any message ≤ high-water or in-Bloom; cap window (e.g., last N reboots / T hours) to bound storage.
**Prior art**:
- RFC 9171 §4.2.7 (time,seq) lexica [L1]; RFC 4303 window + ESN resync [L1]; RFC 6479 [L1]
- RFC 7181 §23.2 / RFC 7183 replay-by-timestamp mandate [L1]
- Nonce-cache cold-after-restart problem (webhook practice) [L5 corroboration]
- MITRE EMB3D MID-037 timestamps [L3]
- Internal: `mod.rs` WP-2 deferral comment, `dedup.rs`, `fragment.rs` message_id restoration [L4]
**Verdict: ADOPT.** No new crypto; flash-wear via batched snapshots (DB row freight per batch, not per message).

### 6(c) Reputation scoring without central authority
**Design**: `reputation.rs` module: per-peer score = Bayesian update from (1) first-hand forwarding observation (watchdog where physically possible), (2) second-hand reports from *verified* contacts only (CORE positivity: negative scores never propagate — prevents frame-up DoS), (3) iTrust-style probabilistic audit checkpoints if delivery acks exist; score maps to *routing weight* (prefer high-score relays, still usable as last resort). No global broadcast, no consensus, no token/credit ledger.
**Prior art**:
- Marti Watchdog/Pathrater (MobiCom 2000) [L2]; CONFIDANT (2002) [L2]; CORE (2002) [L2]
- iTrust TPDS 2014 [L2]; ITRM ISIT 2009 [L2]; Rep-AODV CMC 2024 [L2]
- Reputation-based DTN protocol vs blackholes (Dini & Lo Duca, Ad Hoc Networks 2012) [L2]
- Ostra link-credit model for Sybil-aware budgets (NSDI 2008) [L2]
**Verdict: ADOPT (scoped)** — routing weight only; explicitly non-authoritative; never a hard admission gate (disaster-mesh availability > trust purity). Add parameter fuzz/adversarial tests (bad-mouthing, collusion, on-off).

### 6(d) Emergency-class send authorization (key-anchored, RED-0002 ACL-1)
**Design**: send permission = SPKI chain verify to a preloaded anchor (RFC 9804; EMERGENCY_GOVERNANCE) + **ACL-1 allowlist of authorized roles/keys per alert class** (P0 broadcast = authority roles; P1 medical = authority or certified responder keys; SOS = any verified identity, rate-limited 3/hr) + signed (message,ts,seq) + relay policy: verify chain+sig → dedup/freshness → forward; unverifiable emergency-class → silent drop (no relay). Already-implemented pieces: `authority.rs verify_authoritative`, `rate_limit.rs`, `broadcast.rs`, `provider.rs`. SEC-001 delta: materialize ACL-1 as data (per-class key/role allowlists), rotate/revoke per IDENT-001, and test negative cases (spoofed authority, revoked key, expired chain, replay of an old authority broadcast).
**Prior art**:
- CAP v1.2 XML DSig [L1]; ETSI TS 102 900 §5.5 no-UE-auth [L1]; WEA CACM 2023 Ed25519 mitigation [L2]
- SPKI RFC 9804 key-anchored chains [L1]; RFC 9172 BPSec verify-before-forward [L1]
- Meshtastic CVE-2025-52464 (key hygiene), CVE-2026-42566 (identity-not-key) [L1]
- Internal RES-0017 EMERG-001 findings [L4]
**Verdict: ADOPT.** This closes the "who may send alert-class" gate with standards-level precedent and zero new primitives.

### 6(e) New-crypto-primitive flags (IRIS policy: NO new crypto crates)
- None of 6(a)-(d) require a new primitive: SHA-256 (message-id), Ed25519 (sign/chains), HMAC-SHA256 (RFC 7183 pattern if control messages are added) are already in the stack. [L4 internal]
- Candidates requiring NEW primitives (defer to PROTO-001 v2): (1) identity-mint PoW (KeyChallenge keygen range-PoW; SyDeLP adaptive PoW — hash-based but needs protocol design); (2) VDF-based identity cost (SyDeLP future direction — sequential PoW); (3) identity-based signatures (RFC 7859 — needs IBE pairing math, NOT recommended); (4) link-layer per-peer SA + ESN windows (RFC 4303/6479 — needs key derivation/SA machinery). All four are documented as DEFER.
