# RES-0034 — Android Internet/LAN relay recovery research

- **Date:** 2026-09-08
- **Node:** INTERNET-ANDROID-001
- **Trigger:** FAIL-0009
- **Verdict:** PROCEED WITH SECURITY AND HARDWARE GATES
- **Maturity:** L1 standards/platform documentation + L4 direct implementation audit

## Questions and evidence

### RQ-1 — What does Android “Internet available” mean?

**ADOPT.** `NET_CAPABILITY_INTERNET` means a network is configured for Internet
access; it does not prove reachability. `NET_CAPABILITY_VALIDATED` means Android
successfully validated public Internet access. Network state is asynchronous and
must be driven from `NetworkCallback`; capabilities supplied to
`onCapabilitiesChanged` are the authoritative event value. Calling synchronous
`getNetworkCapabilities()` from `onAvailable()` introduces a documented race.

Primary sources:

- https://developer.android.com/reference/android/net/NetworkCapabilities
- https://developer.android.com/develop/connectivity/network-ops/reading-network-state
- https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback

Decision: track WAN validation independently from local Wi-Fi/LAN viability and
publish reasoned state instead of a single ambiguous boolean.

### RQ-2 — What is required for Android DNS-SD/mDNS?

**ADOPT WITH VERSION CONDITIONS.** `NsdManager` is asynchronous. On releases before
the platform's tracked discovery API, the application owns discovery lifecycle;
Android documentation calls out acquiring a `WifiManager.MulticastLock` for
multicast reception on affected versions. Android 17 / target SDK 37 introduces
local-network permission constraints already carried by ANDROID-001.

Primary sources:

- https://developer.android.com/develop/connectivity/wifi/use-nsd
- https://developer.android.com/reference/android/net/nsd/NsdManager
- https://www.rfc-editor.org/rfc/rfc6762
- https://www.rfc-editor.org/rfc/rfc6763
- https://www.rfc-editor.org/rfc/rfc8882

Decision: declare multicast permission, hold/release a bounded multicast lock,
serialize resolution, remove lost peers, validate version/identity fields, and
format IPv6 socket addresses correctly.

### RQ-3 — What is the relay TLS minimum?

**ADOPT.** Require TLS 1.3, CA/explicit trust-anchor validation, reference-identity
verification through DNS SAN, exact ALPN `iris-relay/1`, and no embedded production
private key. A self-signed certificate is allowed only as a test fixture with an
explicit test trust store. TLS authenticates the relay endpoint, not peer claims.

Primary sources:

- https://www.rfc-editor.org/rfc/rfc8446
- https://www.rfc-editor.org/rfc/rfc9325
- https://www.rfc-editor.org/rfc/rfc9525
- https://www.rfc-editor.org/rfc/rfc7301
- https://docs.rs/rustls/latest/rustls/struct.ConfigBuilder.html
- https://docs.rs/tokio-rustls/latest/tokio_rustls/client/struct.TlsConnector.html

Decision: configure relay address and TLS server name together; fail closed on
certificate/name/ALPN mismatch; load server certificate/key at runtime.

### RQ-4 — How should reconnect and dual-stack behavior work?

**ADOPT WITH BOUNDS.** Connection attempts require per-endpoint state, bounded
exponential backoff with jitter, connection/TLS/register timeouts, liveness
heartbeats, and clean invalidation of dead pooled writers. Address racing should
follow Happy Eyeballs principles rather than permanently selecting the first
candidate.

Primary sources:

- https://www.rfc-editor.org/rfc/rfc8305
- https://www.rfc-editor.org/rfc/rfc9293
- https://www.rfc-editor.org/rfc/rfc9171

Decision: implement deterministic bounded retry and honest delivery receipts;
retain messages above the transport until an application/relay acknowledgement.

## Direct audit findings

The implementation audit found six P0 functional blockers from FAIL-0009 plus:
stale NSD mappings, no relay fallback after LAN failure, IPv6 address formatting
failure, idle timeout mismatch, dead-listener restart state, global rather than
per-endpoint backoff, and relay authorization gaps (unproved PeerId registration,
unbound route source, duplicate-registration race, unbounded connections/tasks,
router lock held across awaited writes, no target ACK/store-and-forward).

## Design inputs

1. Separate local-LAN and validated-WAN state and expose diagnostic reasons.
2. Count Internet as a first-class transport in engine startup/status.
3. Feed trusted NSD peers into DiscoveryManager and remove them on service loss.
4. Bootstrap already-trusted contacts through relay registration after startup and
   connectivity recovery; discovery must never create trust.
5. Prefer LAN for a known peer, fall back to configured relay on a stale/direct
   failure, and retain DTN messages when neither path confirms delivery.
6. Remove production secrets from the relay binary and harden registration,
   source binding, duplicate sessions, resource limits, timeouts, and ALPN.
7. Test core codecs/state/reconnect/adversarial cases on host; test Android API
   31/34 lifecycle and actual bidirectional LAN/WAN delivery on two phones.
