# RES-0002: DTN Time and Bundle Identification

**Type**: Research
**Date**: 2026-08-11
**Node**: PROTO-001
**Author**: Protocol Agent
**Status**: ACTIVE

## Question

How should IRIS identify bundles uniquely, and what time representation should it use?

## Source

RFC 9171, Sections 4.2.6 (DTN Time), 4.2.7 (Creation Timestamp), 4.2.5 (Identifiers)
RFC 4838, Section 3.7 (Primary Bundle Fields)

## Finding

BPv7 uses two-part identification:
1. **DTN Time**: Milliseconds since 2000-01-01 00:00:00 UTC. CBOR unsigned integer.
2. **Creation Timestamp**: Array of [bundle creation time (DTN time), sequence number]. Sequence number is monotonically increasing per source, may reset each millisecond.

**Bundle uniqueness** is determined by: source node ID + creation timestamp.

BPv7 uses Endpoint IDs (EIDs) as URIs:
- `dtn://node-name/service` (human-readable, variable length)
- `ipn:node-nbr.service-nbr` (compact, numeric)

IRIS currently uses:
- Unix epoch seconds (4 bytes)
- UUIDv7 (16 bytes) for message_id
- BLAKE3 hash (32 bytes) for node_id

## Analysis

| Dimension | BPv7 | IRIS |
|-----------|------|------|
| Time resolution | 1 millisecond | 1 second |
| Time epoch | 2000-01-01 | 1970-01-01 |
| Time size | Variable (often >4 bytes) | 4 bytes fixed |
| Uniqueness mechanism | [DTN time, seq_num] + source | UUIDv7 (random) |
| Address format | URI (variable, 10-100+ bytes) | 32-byte hash (fixed) |
| Address human-readability | Yes (dtn scheme) | No (hash only) |
| Collision probability | Sequence-based (deterministic) | Random (2^-128) |

## Implications

BPv7's DTN time (milliseconds since 2000) requires >32 bits (CBOR unsigned integer automatically grows). This is fine for BPv7 but adds overhead for IRIS's constrained LoRa messages.

BPv7's [time, seq_num] approach provides deterministic uniqueness without randomness requirements. IRIS's UUIDv7 relies on random number generation quality — in a disaster scenario with low entropy, this could be problematic.

IRIS's 32-byte BLAKE3 hash addresses are compact and self-certifying but not human-readable and not routable without additional infrastructure.

## Recommendation Direction

For IRIS's P0 LoRa constraint (255 bytes):
- BPv7's variable-length time + seq approach adds ~6-10 bytes
- IRIS's fixed 4-byte timestamp + 16-byte UUIDv7 = 20 bytes
- But UUIDv7 requires entropy; timestamp+seq does not

For interoperability:
- IRIS should define an EID-compatible addressing scheme
- Or implement a gateway that translates between IRIS addresses and BPv7 EIDs
