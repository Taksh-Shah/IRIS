# RES-0031 — Tier-5 Android LAN and Internet transport research

- **Date:** 2026-09-07
- **Node:** INTERNET-001 / hardware-verification Tier 5 (HV-42..45)
- **Maturity:** L2 — official Android and IETF primary sources; repository code audit
- **Question:** What is the smallest safe design that gives Android both same-LAN and cross-network IRIS delivery?

## Evidence

1. Android `ConnectivityManager` and `NetworkCallback` expose the active network,
   validation/capabilities, and metered status. The app must treat callbacks as
   hints for transport availability and cost, not as proof that a peer is reachable.
2. RFC 6762 defines mDNS as DNS-like resolution on the local link without a managed
   DNS server. RFC 6763 defines DNS-SD service instances and records. Android NSD
   is the platform integration point for this local service discovery.
3. RFC 8489 STUN discovers a NAT-mapped address and checks reachability; RFC 8445
   ICE coordinates candidate checks. These do not guarantee connectivity through
   carrier-grade or symmetric NAT. RFC 8656 (successor to RFC 5766) defines TURN
   relay allocation for cases where direct paths fail.
4. The existing `iris-core` `InternetTransport` already provides TCP framing,
   pooling, retry backoff, and per-peer relay binding, but it is plaintext and
   has no Android registration or platform network signal. `NodeAdvertisement`
   does not currently provide a complete Android discovery path.

## Decision

- **LAN:** implement Android NSD/DNS-SD advertisement and discovery for `_iris._tcp`.
  Resolved endpoints become explicit `internet` transport addresses; the existing
  signed IRIS envelope remains the identity/authentication boundary.
- **Internet:** implement an outbound relay client path first. Do not expose direct
  inbound sockets or assume NAT hole-punching. A deployed relay/rendezvous service
  is a separate infrastructure gate (HV-44), not something to fake in the phone.
- **Security:** plaintext TCP is not acceptable for production internet transport.
  The design must add authenticated TLS with relay identity pinning or an equally
  explicit trust mechanism before a production acceptance claim.
- **Network state:** use `ConnectivityManager.NetworkCallback` to feed online,
  validated, metered/unmetered state into the Android transport seam and selection
  cost. Network loss must tear down or degrade the transport deterministically.
- **Scope:** land the design and testable seams first; hardware acceptance requires
  two phones on one LAN with BLE/Wi-Fi Direct disabled, then two different networks
  for relay verification. HV-44 remains server-gated.

## Alternatives rejected

- Direct phone-to-phone TCP as the only internet path: fails under common CGNAT.
- STUN-only hole punching: no reliable fallback for restrictive/symmetric NAT.
- Treating `ConnectivityManager` online as peer reachability: conflates local link
  state with application connectivity.
