## Question

What are the newest standards and best-in-class practices for DTN message handling — lifecycle, priority queues, TTL/expiry, deduplication, and ACK/custody/retry — and exactly what should MSG-001 implement, mapped to `docs/implementation/MSG_DESIGN.md`?

## Method & Scope

Web research (RFC Editor, IETF Datatracker, IEEE, arXiv, Bluetooth SIG, industry) conducted 2026-08-13. Evidence levels follow `engineering/RESEARCH_POLICY.yaml`: **SPEC_RFC** (IETF/standards), **IEEE** (peer-reviewed), **ACADEMIC** (peer-reviewed / preprint), **INDUSTRY** (reputable technical material), **EXPERIMENTAL** (working drafts / prototypes). Prior records RES-0001 (BPv7 vs flat envelope) and RES-0002 (DTN time/IDs) are assumed read; this record focuses on *message engine behavior*, not envelope syntax.

## 2. Topic Findings

### A. Message Lifecycle

**F1.** BPv7 specifies a complete bundle-agent lifecycle: transmission (§5.2), dispatching (§5.3), forwarding (§5.4), expiration (§5.5), reception (§5.6), local delivery (§5.7), fragmentation (§5.8), ADU reassembly (§5.9), deletion (§5.10), discarding (§5.11), canceling (§5.12). Source: RFC 9171. *(SPEC_RFC, HIGH)*

**F2.** On reception the BPA MUST add the retention constraint "Dispatch pending" (RFC 9171 §5.6 Step 1) — this is the BPv7 equivalent of IRIS `PENDING_SEND`. Source: RFC 9171. *(SPEC_RFC, HIGH)*

**F3.** "Bundle expiration MAY occur at any point in the processing of a bundle. When a bundle expires, the BPA MUST delete the bundle" with reason "Lifetime expired" (or "Traffic pared" for a BPA-imposed lifetime override), following the deletion procedure (§5.10). Expiry → storage slot freed is mandatory, not optional. Source: RFC 9171 §5.5. *(SPEC_RFC, HIGH)*

**F4.** RFC 4838 §3.10: "The most basic service provided by the bundle layer is unacknowledged, prioritized (but not guaranteed) unicast message delivery," with two reliability options: end-to-end acknowledgments and custody transfer. Source: RFC 4838. *(SPEC_RFC, HIGH)*

**F5.** RFC 4838 §3.1 frames the whole architecture as "virtual message switching using store-and-forward operation" — exactly IRIS's message engine role. Source: RFC 4838. *(SPEC_RFC, HIGH)*

**F6.** BPv7 status reports are administrative records with flags for reception / forwarding / delivery / deletion and IANA reason codes (e.g., 1 = "Lifetime expired", 2 = "Forwarded over unidirectional link"). Source: RFC 9171 §6.1.1, §9.5. *(SPEC_RFC, HIGH)*

**Implication for MSG-001**: the designed lifecycle (`CREATED → PENDING_SEND → IN_TRANSIT → DELIVERED → ACKNOWLEDGED`, with `EXPIRED`/`DELIVERY_FAILED`) is a faithful simplification of BPv7 §5.x. Add explicit **deletion on expiry** (free storage slot) as first-class behavior, and expose the six BPv7 status-report reasons as local observability events.
**Decision**: keep the simplified IRIS state machine; add `EXPIRED → DELETE + evict` as an explicit transition (already implied by `evict_expired` in the `MessageStorage` trait); record BPv7 reason codes in metrics.

### B. Priority Queue Patterns (P0 never evicted)

**F7.** RFC 4838/5050 defined three "cardinal priorities" (expedited, normal, bulk) carried in 2 Class-of-Service bits of the BPv6 primary block; **BPv7 removed them from the primary block** — QoS moved to a dedicated extension block. Source: RFC 9171 IANA processing-control-flags table (bits 7–8 listed for v6 only); SpaceOps-2025 paper. *(SPEC_RFC, HIGH)*

**F8.** The proposed BP QoS extension block (UQEB, "User QoS Extension Block") defines four keys: **Traffic Prioritization (0), Retransmission (1), Latest-Only Delivery (2), Bundle Retention / storage class (3)**. The UQEB "is added at the source node, and must not be altered during transit" — priority is immutable in transit, matching `PRIORITY_MODEL.md`. Source: IETF 124 slides (Algarra Ulierte & Flentge, 2025-11-06); SpaceOps-2025 paper #252. *(EXPERIMENTAL/SPEC_RFC-draft, MEDIUM-HIGH)*

**F9.** Strict priority scheduling causes **data starvation** of lower classes; the proposal uses a **volume-based nested-interleaving schedule**: "If the allocated volume is surpassed, the priority level must 'make up for it'" using borrowed/skipped slots, preventing extreme delays for low-priority traffic. Source: SpaceOps-2025 paper; IETF 124 slides; simulation shown vs strict-priority and round-robin benchmarks. *(EXPERIMENTAL, MEDIUM-HIGH)*

**F10.** Storage-class semantics in the QoS block: "Bundle classes are deleted starting from the bottom. Within the same class, deletion is performed according to the TTL left, with the shortest TTL first." Default class 11 if unspecified. This is the protocol-level echo of IRIS's eviction rule `(priority DESC, expires_at ASC)` in `STORAGE.md`. Source: SpaceOps-2025 paper §4. *(EXPERIMENTAL, MEDIUM-HIGH)*

**F11.** Block processing flags for the UQEB: Bit 0 = replicate in every fragment; Bits 1/2/4 = 0 so non-supporting nodes pass it through transparently (forward-compatible). Source: SpaceOps-2025 paper. *(EXPERIMENTAL, MEDIUM)*

**F12.** BPv7 "lacks support for Quality of Service (QoS), which is essential for ensuring reliable and timely data transfer" — a recognized gap the WG is filling. Source: SpaceOps-2025 paper abstract. *(EXPERIMENTAL, MEDIUM-HIGH)*

**Implication**: IRIS's 8-level P0–P7 queue with P0 never evicted (INV-ROUTE-003) is *more* granular than any standardized DTN priority scheme (BPv6: 3 classes; QoS block: Expected/Normal/Bulk + storage classes). No standard forbids P0-never-evict; it is a policy IRIS can defend as stricter-than-standard emergency handling. The 60 s starvation timer should be upgraded to a **volume-aware budget** (borrow/skip accounting) so lower priorities are guaranteed *some* airtime.
**Decision**: keep P0–P7 and P0-never-evict; implement starvation prevention as weighted-budget scheduling (each priority gets a guaranteed share of transmission slots within a 60 s window), which subsumes the current "insert one P1-or-lower message" heuristic.

### C. TTL / Expiry and STORE-001

**F13.** BPv7 lifetime is an *age* (relative lifetime in the primary block), not an absolute time; expiration can occur at any processing point; the BPA MUST delete on expiry (§5.5). For nodes without accurate clocks, BPv7 defines the **Bundle Age extension block** (`ext-data-bundle-age`). Source: RFC 9171 §5.5, §4.2, §4.3/Appendix extension blocks. *(SPEC_RFC, HIGH)*

**F14.** RFC 4838 §3.12: DTN depends on time synchronization for four purposes — bundle identification, routing with scheduled/predicted contacts, **bundle expiration time computations**, and registration expiration. Absolute expiry (IRIS `expires_at_unix`) is the standard-compatible representation. Source: RFC 4838 §3.12. *(SPEC_RFC, HIGH)*

**F15.** Buffer/drop-policy research (foundational): Krifa, Barakat & Spyropoulos, "Optimal Buffer Management Policies for DTN" (IEEE SECON 2008): "In case of congestion, a DTN node should take a drop decision that leads to the best gain in the global delivery ratio"; TTL is a first-class input to the drop decision; source keeps a copy during the whole TTL, intermediate nodes are not obliged to. Source: OBMP paper. *(ACADEMIC/IEEE, HIGH)*

**F16.** TTL-based drop policy E-DROP "drops the message having the lowest TTL value" — the common local-knowledge baseline. Source: E-DROP (Rashid et al. 2011); IJIRT survey 2022. *(ACADEMIC, MEDIUM)*

**F17.** PQB-R (Priority-Queue-Based Reactive buffer policy, PLOS ONE 2018): computes a drop priority from residual TTL, hop count, message size, and created time; notes "ttl has a direct impact on message delivery because a message with highest ttl gets more transmission opportunities"; TTL expiry auto-removes messages from relay buffers. Source: PLOS ONE. *(ACADEMIC, MEDIUM-HIGH)*

**F18.** Recent work continues this line — "Range aware message drop policy for delay tolerant networks" (2024) surveys DRA/DLR/DOA/DLE and proposes delivery-probability-aware dropping. Source: PMC11323192. *(ACADEMIC, MEDIUM)*

**F19.** IEEE Access 2024 (Cotrim et al.), *LoRaWAN duty cycle effects on multihop networks: Make or Break?*: under duty-cycle constraints, packets enqueued in intermediate buffers experience delay "for unfeasible values" and delivery ratio decreases; larger buffers trade loss for delay. This is the *physical* argument for TTL enforcement at relay nodes: an expired message occupying a LoRa relay buffer is actively harmful. Source: IEEE Access Vol. 12, Nov 2024. *(IEEE/ACADEMIC, HIGH)*

**Implication**: IRIS's absolute `expires_at_unix` + 300 s clock-skew budget is the correct standard-aligned design (F13, F14). TTL-aware eviction (F15–F18) and the QoS storage-class rule (F10) both validate `STORAGE.md`'s `(priority DESC, expires_at ASC)` eviction. The one non-standard IRIS choice — P0 retained in storage even past TTL until explicitly cleared (`TTL.md` §"Storage and TTL") — must be reconciled with F3 (MUST delete on expiry); recommend P0 also expires but is *re-propagatable* by the originator within the 72 h window, or explicitly gated in `known_limitations`.
**Decision**: enforce TTL at insertion, dequeue, and relay (as designed); on expiry, delete + free storage; keep the 300 s skew budget with per-peer observed-skew tracking; document the P0-expiry exception in `known_limitations`.

### D. Deduplication via message_id

**F20.** BPv7 bundle identity = source endpoint + creation timestamp (+ fragment offset/length); RFC 5050 §5.2 Step 4 dedups on exactly this tuple: "the bundle has the same source endpoint ID, creation timestamp, and (if a fragment) fragment offset and payload length as another bundle". Source: RFC 9171 §4.2.7; RFC 5050 §5.2. *(SPEC_RFC, HIGH)*

**F21.** Deduplication is intrinsic to DTN: epidemic/opportunistic routing deliberately floods copies via multiple paths, so the same message arrives at a node repeatedly; without dedup, relays amplify floods and storage fills with duplicates. Source: "Cache to the Future: A Distributed Webpage Archive for Internet Blackouts" (arXiv 2026) survey of blackout-resistant apps; RFC 4838 §3.9 (fragmentation/reassembly for efficient contact utilization). *(ACADEMIC, MEDIUM-HIGH)*

**F22.** Bloom filters are the *de facto* DTN dedup mechanism: "1am, Amigo, Anix, and Perry et al. all consider using Bloom filters... Bloom filters allow users to send others a short digest of their stored messages. The digest can help prevent users forwarding messages the other user has already received" (Briar/Bridgefy/NewNode don't publish details). Source: arXiv 2606.17245 (2026). *(ACADEMIC, MEDIUM-HIGH)*

**F23.** Marandi et al. analyzed Bloom-filter parameter optimization specifically for epidemic forwarding in DTNs — confirming the design space IRIS uses (capacity × false-positive rate). Source: arXiv:1208.3871 (2012); HAL hal-01054039 (2014). *(ACADEMIC, MEDIUM)*

**F24.** Disaster-oriented opportunistic system (IPSJ JIP 2014): per-message Bloom filters are constructed to prevent **duplicate counting** when aggregating disaster reports — the same double-purpose IRIS serves (relay dedup + recipient dedup). Source: J-stage IPSJ-JIP 22(2). *(ACADEMIC, MEDIUM)*

**F25.** Bloom-filter properties: false positives possible, **false negatives impossible**; memory scales as ~1.44×n×log2(1/p). At 100 k entries / 0.1 % FPR: ≈1.8 MB, ~10 hash functions (DEDUPLICATION.md's 1.44 MB estimate is in the right range). Source: standard Bloom filter literature; OneUptime/Redis guides. *(INDUSTRY/ACADEMIC, MEDIUM-HIGH)*

**F26.** ⚠️ **IRIS internal contradiction**: `message_id` is 16 bytes (UUIDv7, `MESSAGE_ENVELOPE.md`), 24 bytes (BLAKE3 truncated, `DEDUPLICATION.md`), 32 bytes (`crates/iris-core/src/message.rs` `SerializedMessage.message_id`), and hex TEXT (UUIDv7, `STORAGE.md`). This must be normalized before implementation; wire format should win (16-byte UUIDv7 per RFC 9562, CBOR-compact). *(internal, HIGH)*

**Implication**: the two-tier design (relay Bloom filter, probabilistic; recipient exact DB dedup, zero-FP) is exactly the standard pattern (F22, F25). The 144 h retention window > max TTL (72 h) preserves the invariant "dedup window > max TTL". Persisting `seen_messages` in SQLite (STORAGE.md) is *stronger* than the blackout-app norm (in-memory filters).
**Decision**: implement two-tier dedup as designed; normalize `message_id` to a single 16-byte UUIDv7 wire type (update docs + code constant); keep the exact `seen_messages` table at recipient + relay-forward gating via Bloom filter; keep the 144 h window.

### E. ACK / NACK Retry Backoff and Custody

**F27.** BPv7 removed custody transfer from the processing-control flags (bit 3 exists only in BPv6; the RFC 9171 IANA table shows "6" only). Custody signalling must be re-provided by other means. Source: RFC 9171 §9.3 table; IETF 124 minutes. *(SPEC_RFC, HIGH)*

**F28.** BPv6 custody semantics (still the reference for the concept): "If the custody transfer requested flag is 1, then the sending node requests that the receiving node accept custody of the bundle"; custody signals are Succeeded/Failed; a custody countdown timer is allowed; **on custody failure the agent "might choose to re-forward the bundle, possibly on a different route"** (§5.12). Source: RFC 5050 §5.2, §5.10, §5.12. *(SPEC_RFC, HIGH)*

**F29.** RFC 4838 §3.10: custody transfer "only specifies a [responsibility]" and **not all nodes are required to accept custody**; nodes may decline when congested/low-power; custody affects routing ("it may be beneficial to move a bundle to a custodian as quickly as possible even if the custodian is further away"). Source: RFC 4838 §3.10. *(SPEC_RFC, HIGH)*

**F30.** Current IETF direction (IETF 124, 2025-11-06): "BPV7 Custody Transfer and Compressed Status Reporting" (Wobbe et al.) — custody via a **Custody Transfer extension block (CTAB)** + compressed bundle reporting (CBR); "Any node can request custody, decision to take or refuse is mission or network specific"; bundles carrying CTAB/CBR "should not be fragmented"; prototyped in dtn.eisen and validated in lunar scenarios; being split into three drafts (Bundle Sequence IDs, BPV7 Custody Signaling, Compressed Bundle Status Reporting). Source: ietfminutes.org IETF 124 minutes. *(EXPERIMENTAL, MEDIUM)*

**F31.** Retransmission policy is becoming an explicit per-bundle QoS parameter: UQEB key 1 "Retransmission" with values from "NO RETRANSMISSION ALLOWED (−1)" through "RETRANSMISSION REQUIRED (1)" / "RETRANSMISSION IF POSSIBLE (2)" — i.e., retry behavior is a source-declared property, matching IRIS delivery policies. Source: IETF 124 QoS slides; SpaceOps-2025 paper. *(EXPERIMENTAL, MEDIUM-HIGH)*

**F32.** Status reports (F6) are the standard basis for retry decisions: reception/forwarding/delivery/deletion events with reason codes; IRIS's simplified E2E-ACK/C-ACK/GW-ACK (`ACKNOWLEDGEMENTS.md`) is a valid projection of BPv7 status reports + custody signals. Source: RFC 9171 §6.1.1/§9.5. *(SPEC_RFC, HIGH)*

**F33.** Backoff-with-jitter is the accepted retry pattern to prevent "thundering herd" re-connection storms (e.g., when a gateway returns): full-jitter exponential backoff is standard industry practice. Source: IRIS `RETRIES.md`; AWS Architecture Blog "Exponential Backoff and Jitter" (industry). *(INDUSTRY, MEDIUM-HIGH)*

**F34.** Retry-until-TTL for P0/P1 is a *policy* choice: the QoS block's "Timely" retransmission class (negative integer values) encodes "retransmit promptly," while the standard engineering guard is to bound total retransmissions by the message TTL — which IRIS already does. The unbound relay-side risk (a P0 flood filling relay queues) is documented in `RETRIES.md` Known Limitations. Source: QoS slides; IRIS RETRIES.md. *(EXPERIMENTAL/INDUSTRY, MEDIUM)*

**Implication**: IRIS's C-ACK design matches the *emerging* standard (custody via extension block) rather than the removed BPv6 flag — keep the ACK wire format (F32) and make the custody-request/accept semantics explicit and **policy-controlled** (F29: relays may refuse custody when congested). Backoff parameters should respect per-transport airtime budgets on LoRa (F19, INV-EMERG-002).
**Decision**: implement E2E-ACK/C-ACK/GW-ACK per `ACKNOWLEDGEMENTS.md`; add a custody accept/refuse policy hook at relays (refuse when queue > 80 %); never fragment ACK/custody payloads (F30); keep P0/P1 constant-interval retry until TTL but gate it through the transport scheduler so LoRa duty cycle is never bypassed.

### F. Constrained-Node / LoRa Constraints

**F35.** RFC 7228: constrained nodes have "hard upper bounds on state, code space, and processing cycles"; constrained networks have "low achievable bitrate/throughput (including limits on duty cycle), high packet loss and high variability of packet loss, [and] severe penalties for using larger packets". Source: RFC 7228 §2.1–2.2. *(SPEC_RFC, HIGH)*

**F36.** LoRaWAN duty cycle: EU868 = 1 % → 864 s/day airtime; 0.1 % → 86 s/day; duty cycle is a *regulatory* constraint that applies to private networks too; LoRa Alliance RP002-1.0.5 (2025-10-08) is the current regional-parameters reference. Source: Lansitec duty-cycle guide (2026); LoRa Alliance RP002. *(INDUSTRY, MEDIUM-HIGH)*

**F37.** Multihop LoRaWAN under duty cycle (IEEE Access 2024): DC increases delay "for unfeasible values" and decreases PDR; buffer size is the control knob; relays are under the same DC restrictions. Source: IEEE Access 10.1109/ACCESS.2024.3494038. *(IEEE/ACADEMIC, HIGH)*

**F38.** IRIS P0 constraint (255 B LoRa payload) is validated by F35 ("severe penalties for larger packets") and by RES-0003's LoRa payload analysis (India 865–867 MHz). Retries for P0/P1 (F34) directly consume the daily airtime budget — duty cycle and retry scheduler must be coupled. Source: RES-0003; MESSAGE_ENVELOPE.md size budget. *(internal + SPEC_RFC, HIGH)*

**Implication**: MSG-001 must treat the transport as the authority on what can be sent when. The retry/backoff scheduler (R7 below) needs an airtime-budget abstraction — even if LORA-001 isn't implemented yet, the scheduler API should accept a per-transport "send window" hint.
**Decision**: add `next_send_window(transport)` to the transport interface (or a scheduler budget) so retries never exceed duty cycle; P0 *preempts* but never bypasses the budget (INV-EMERG-002).

## 4. Ordered Recommendation List for MSG-001 (mapped to MSG_DESIGN.md)

1. **R1 — Lifecycle: adopt BPv7 §5.x semantics (F1–F3).** Map: `Message Lifecycle`. Add `EXPIRED → delete + free storage` as an explicit transition; on reception set `PENDING_SEND` ("Dispatch pending" analog). *Evidence: RFC 9171 §5.5/§5.6.*
2. **R2 — Priority queue: keep P0–P7, P0 never evicted; implement volume-aware fair scheduling (F8–F10).** Map: `Priority Queue` + `Starvation Prevention`. Replace the bare 60 s heuristic with guaranteed per-priority budget slots (borrow/skip accounting) in the 60 s window. *Evidence: SpaceOps-2025/IETF 124 QoS block.*
3. **R3 — TTL: absolute `expires_at`, enforced at insert/dequeue/relay; 300 s skew budget per peer (F13–F14).** Map: `TTL Enforcer`. *Evidence: RFC 9171 §5.5, RFC 4838 §3.12, TTL.md.*
4. **R4 — Eviction: expired-first, then `(priority DESC, expires_at ASC)`; P0 exempt (F10, F15–F17).** Map: `MessageStorage::evict_by_priority`, acceptance #9. Keep the "P0 full → reject P1–P7" rule from PRIORITY_MODEL.md. *Evidence: QoS storage classes + OBMP/PQB-R.*
5. **R5 — Dedup: two-tier Bloom (relay) + exact table (recipient); normalize `message_id` (F22–F26).** Map: `Dedup Engine`, acceptance #4. Persist `seen_messages` 144 h; add FP-rate metric. *Evidence: arXiv 2026 blackout survey; F25; C1.*
6. **R6 — ACK: E2E-ACK + C-ACK + GW-ACK per ACKNOWLEDGEMENTS.md; relays may REFUSE custody (F28–F30).** Map: `ACK Tracker`. Never fragment ACK payloads. *Evidence: RFC 9171 §6.1.1, RFC 5050 §5.2, RFC 4838 §3.10, IETF 124.*
7. **R7 — Retry: per-priority exponential backoff with jitter; P0/P1 constant until TTL — gated by per-transport airtime budget (F33–F37).** Map: `Retry Strategy` + `Transport select`. Add `next_send_window` budget abstraction; LoRa duty cycle is never bypassed (INV-EMERG-002). *Evidence: RETRIES.md, IEEE Access 2024, RFC 7228.*
8. **R8 — Fragmentation: 30 s reassembly timeout as floor; per-priority timeout up to TTL remainder; never fragment ACK/custody bundles (F30).** Map: `Fragment Reassembler`. *Evidence: IETF 124 CTAB policy.*
9. **R9 — Storage-backed queue: re-queue in priority order on restart via `idx_messages_priority` (F2).** Map: `Storage Interface` + thread-safety section. `PENDING_SEND` is the durable retention constraint. *Evidence: RFC 9171 §5.6, STORAGE.md schema.*
10. **R10 — Observability: per-priority queue depth, TTL-expiry count, dedup FP rate, retry/custody accept-refuse counters (F6, F32).** Map: acceptance #10. *Evidence: RFC 9171 status-report reasons; DTN-WG DTNMA direction.*
