## Headline findings

1. **`tracing` is the right substrate, and iris-core should emit events directly with the macros — but under a strict, documented event registry.** Disabled callsites are near-zero-cost (interest cache: an event never constructed when no subscriber is interested — no allocation, no string formatting). Enabled overhead is small but proportional to span count and field formatting; the correct discipline is coarse spans, fixed field sets, allow-listed attribute names. A thin wrapper macro around `tracing` is NOT needed for v1; the wrapper adds maintenance cost, and tracing already gives level+target filtering, structured fields, timestamps, and async span instrumentation (`.instrument` on futures) that the async tokio engine needs. Instead, centralize event names + attribute keys as typed constants and helper fns (e.g. `MessageId::short()`) so privacy and taxonomy live in one place.
2. **Adopt the OTel *mental model* (signals, instrument types, naming grammar, semconv vocabulary) but NOT the OTel SDK/OTLP stack for v1.** OTel messaging semconv is still `[Development]` (not stable) and mixes reserved (Kafka/RabbitMQ/MQTT) conventions that don't fit a DTN mesh; the metrics API is stable and its instrument taxonomy (counter / updowncounter / histogram / gauge) is exactly what iris-core needs. Full OTel = a heavy dependency tree + an always-available network exporter — the wrong direction for battery-constrained, offline-first nodes. Recommended: typed events + lock-free AtomicU64 counters + bounded ring buffer (events OR metrics) + batch flush on contact.
3. **RFC 9171 has a first-class observability vocabulary that maps 1:1 onto IRIS lifecycle seams: the Bundle Status Report (BSR).** BPv7 keeps RFC 5050's four status assertions (received/forwarded/delivered/deleted), each with an optional status time, plus a **reason code registry** (0 no-info, 1 lifetime expired, 2 unidirectional link, 3 transmission canceled, 4 depleted storage, 5 dest endpoint unavailable, 6 no known route, 7 no timely contact). RFC 9171 §6.2: *generation of status reports MUST be disabled by default* — a direct precedent for "telemetry off unless configured". RFC 9173 (BPSec) adds no observability requirements of its own. IRIS lifecycle events should reuse this vocabulary: reason codes map onto `DropReason` (TtlExpired=1, StorageFull/Evicted=4, route-less Store=6, SCF AwaitingContact=7).
4. **Privacy is a design-time property, not a processor.** Best-in-class practice (OTel redaction guides, OneUptime PII playbook, OpenObserve tiering) is: default-deny attribute allow-lists, redact-at-source, hash only when correlation is needed, drop when regulated. Under DPDPA 2023 §4(1)(b) data minimization + §6(1) privacy-by-design, "collect less, structure more" is the compliance path; pseudonymized (hashed) data is still personal data (GDPR article 4(5) semantics, echoed in India's Rules commentary) — so IRIS remote telemetry must be opt-in with bounded retention. Payload exclusion by default is already in `docs/implementation/OBSERVABILITY.md`; this record makes it a hard seam rule.
5. **Reference implementations for constrained telemetry all converge on the same pattern: interval/event batching, congestion-aware sampling, small fixed structures, off-by-default reporting.** Meshtastic: telemetry frames are small, fixed-schema protobufs, sent on minutes-to-hours intervals, with channel-utilization scaling (25% regular, 40% router) — telemetry is *airtime budgeted*. ION: `bpstats`/`bptrace` show status-report-driven per-bundle tracing is the DTN-native way. μD3TN/IBR-DTN: embedded DTN keeps persistent state in SQLite and lean modules. `tracing-cache` shows the bounded in-memory ring buffer + background-driver pattern. IRIS v1 should do the same locally (ring buffer → flush on connectivity), deferring any network export.

## A. Recommended telemetry model for iris-core v1

**Three signals, all emitted via `tracing`:**

| Signal | Mechanism | OTel analog | Notes for IRIS |
|---|---|---|---|
| **Events** (primary) | `tracing` events at fixed levels with allow-listed fields | Logs signal | One event per meaningful seam transition (lifecycle, routing decision, SCF status, gateway health). Event name = dotted namespace (`msg.*`, `route.*`, `scf.*`, `gw.*`, `topo.*`). |
| **Spans** (secondary) | Coarse `.instrument()` spans on message lifecycle and gateway/SCF operations | Traces signal | Per-*message* span around the engine's send path and accept path; **not** per-hop, not per-flood-recipient. message_id is the correlation key (matches RFC 9171: bundles are correlated by (source, creation timestamp), and IRIS already has 16-byte UUIDv7 id). |
| **Metrics** | Lock-free `AtomicU64`/lock-free histogram buckets in a `MetricsRegistry` (no global state — injected like the existing `EngineMetrics`), read on demand | Metrics signal | Counter / UpDownCounter / Gauge / Histogram. No per-event metric writes from the hot path; metrics are read at flush time (interval or on contact). Reuses `EngineMetrics` (6 AtomicU64) + `SimMetrics` vocabulary. |

**Mapping OTel concepts → IRIS vocab:**

- **messaging.message.id** → `message_id` (truncated 8-byte/16-hex prefix in all *exported/local-text* output; full id only in memory). OTel defines `messaging.message.id` as the recommended per-message identifier (development-semconv).
- **messaging.system** → `iris.mesh` (we are the system; no reserved-name mapping).
- **messaging.destination.name** → `dest` peer id (truncated); OTel warns destination is high-cardinality and must not be used as template — mirrored by our truncation rule.
- **messaging.operation.type** (publish/process/receive) → our lifecycle verbs: `send`, `receive`, `relay`, `deliver`, `expire`, `delete`.
- **status assertion + status time + reason code (RFC 9171 BSR)** → `msg.status`, `state_age_ms`, `reason` — the BSR is the DTN-native "message lifecycle telemetry" and our event fields are its local-only projection.
- **Resource attributes** → a small constant set attached to every event/metric batch: `service.name=iris`, `service.version` (crate version), `node.id` (truncated PeerId), `device.class` (Phone/Relay/Edge/Desktop — already a `DeviceClass` enum in SCF), `battery.level` when available. OTel requires `service.name` (stable) and recommends host/device attrs (device.model.* stable).

**Timestamps**: events carry monotonic `Instant`-derived timestamps (wall-clock skew is a known DTN problem; RFC 9171 DTN-time allows "time unknown" and IRIS uses arrival-time TTL semantics per RES-0010). Log stream gets wall-clock at sink time (fmt layer), but `age_ms`/`latency_ms` fields are always monotonic deltas.

## D. Privacy design

Rules (all enforced at the emission site — redact-at-source, not post hoc):

- **P1 Payload exclusion by default**: payload bytes never appear in any event/span field, encrypted or not. Only `size_bytes` and `content_type` may be logged. (Confirms + hardens existing OBSERVABILITY.md rule; lowest-cost, highest-value control.)
- **P2 Identifier truncation**: `MessageId` and `PeerId` display in telemetry as **first 8 bytes** (16 hex chars). Existing `Display` prints full hex — add `short()`/abbreviated formatting specifically for the obs layer (repo already plans this: "use 8-byte prefix for correlation only"). Full ids exist in memory only.
- **P3 Keyed hashing for any cross-node/exported correlation**: if an identifier must be correlated beyond local debugging, use **HMAC-SHA256 (or BLAKE3 keyed) with a per-installation random salt**, truncated to 8 bytes; rotate salt at retention windows. Plain SHA-256 of low-entropy values is not pseudonymization. (Microsoft LDP notes simple hashing isn't DP; OpenObserve/OneUptime: hash preserves cardinality without exposing value.)
- **P4 Default-deny attribute allow-list**: every event in §B is the complete set of attribute keys an emit site may use. Any new key requires a change to the registry (a small match on `&'static str` consts). This is the OTel-redaction/allow-list pattern applied at compile-time.
- **P5 Payload/crypto/material deny-list**: keys, crypto key material, full contact lists, address books → compile-time unrepresentable (no helper exists; attribute keys not in registry can't be emitted).
- **P6 Sampling and severity tiers**: ERROR/WARN always emitted (no sampling); INFO sampled (default 1:1 locally, 1:10 batched/exported); DEBUG sampled (1:100, dev-only); TRACE never in production (hard rule, existing design). P0/SOS path: never sampled below WARN semantics; P0 events are always retained for the local ring buffer.
- **P7 Metric aggregation instead of raw recordings**: metrics carried as counters/summaries; no per-message telemetry export (only event stream for diagnostics, and it's truncated by P2).
- **P8 Bounded retention + off-by-default remote export**: local ring buffer bounded (§E); any remote telemetry (via gateway) is **opt-in**, batch-only, and retention-capped. RFC 9171 §6.2 precedent: status reports MUST be disabled by default.
- **P9 DPDPA/GDPR posture (research input for LEGAL-001)**: DPDPA §4(1)(b) data minimization and §6(1) privacy-by-design make "collect fewer fields, structured, bounded" the compliant default. Pseudonymized telemetry (P2/P3) remains *personal data* if it can be linked to an individual — so IRIS telemetry is personal-data-capable; remote export requires consent/legal basis. DPDP Rules 2025 require retaining logs ≥1 year for breach investigation only where personal data is processed by government/law — for standalone consumer mesh nodes, retention stays bounded (P8) and minimal. Hash ≠ anonymize (Fedora/LWN and Pseudonymization commentary) — record this in the privacy design doc.

## E. Overhead + battery-aware design

**What to use (evidence-backed low-cost primitives):**
- **`tracing` macros only; zero-cost when disabled.** The interest cache means disabled callsites are never constructed (no allocation, no formatting). Enabled cost is proportional to enabled level + span count — so prod runs `INFO`, and the engine's hot paths (dedup check, queue insert) emit DEBUG that is filtered out at the subscriber unless `RUST_LOG/tracing max level` raises it. (tracing docs; tokio tracing guide.)
- **Ring buffer, not unbounded logs.** `tracing-cache` pattern: bounded in-memory span/event ring (e.g. 4-16 KiB/event cap; 1,024-4,096 events or 2-10 min retention), flushed **on contact/connectivity** (matches DTN batching; matches Meshtastic's interval+batching). `tracing-appender`'s `non_blocking` file writer for desktop/relay logging (dedicated worker thread, bounded channel — never blocks the async engine).
- **Batch metrics reads** on a 30-60 s interval or on flush, not per-event writes. Clock-driven, not event-driven.
- **Sampling / airtime budget discipline from Meshtastic**: telemetry volume scales with channel utilization / duty cycle (India LoRa 865-868 MHz; DISC-0004/0005 — duty cycle applies to *all* messages). Batch size ≤ gateway contact budget (reuse `bandwidth_limit`/`deferred` logic in SCF-001); drop-batch-on-backlog rather than queueing unbounded.
- **Fixed small structures**: enum-as-u8 instead of String labels in metrics (`algorithm`, `reason`, `priority`, `health_state`) — lower cardinality, no per-event String allocation. OTel's low-cardinality-attribute guidance.
- **Coarse spans**: one span per message lifecycle, `.instrument()` over the async body (handles `.await` boundaries correctly — `Span::enter` across awaits is a footgun, docs warn against it). Never per-hop flood spans; relay hops already have `msg.sent`/`route.*` events.

**What to avoid:**
1. Full OTel SDK + OTLP exporter in core (dependency weight, background network I/O, exporter lifetime/retry machinery) — v1 has no always-on network path anyway.
2. Per-message `String` formatting of ids in hot paths (format only in the subscriber when enabled; pass `%message.short` / typed values as tracing fields).
3. Unbounded or sync file writes on the engine task (flash wear + latency — use `tracing-appender` non-blocking or the ring buffer).
4. TRACE-level instrumentation in production (per-packet CBOR/hex dumps — existing OBSERVABILITY.md already forbids).
5. Span explosion (instrumenting every helper fn — docs.rs/tracing guidance: instrument logical units of work only).
6. High-cardinality metric labels (don't put raw PeerId/MessageId into metric attribute sets — metrics cardinality blows up storage; OTel guidance).

**Budgets (proposed):** max event rate at INFO ≈ 10-50 ev/s per node (engine msgs + routing + gateway transitions); ring buffer 4,096 events (~256 KiB) or 10 min; flush batch ≤ 512 events; DEBUG only under dev builds/RUST_LOG override.

## F. Deliberate divergences from vanilla OTel (and why)

| # | Divergence | Rationale |
|---|---|---|
| 1 | **No OTLP exporter, no opentelemetry SDK in v1** | Battery/offline-first: no network endpoint to export to; OTLP adds background threads, retry/backoff, and dependency weight. Metrics/events stay local; export seam is a *future* trait behind a flush-on-connectivity boundary (can land as `opentelemetry-otlp` behind a feature when gateways are reliable). |
| 2 | **Typed event registry over free-form log lines** | Fixed event names + allow-listed attrs are greppable, filterable, schema-checkable, and privacy-enforceable at compile time. Free-form `info!` text invites PII drift (P4/P5 make drift a compile error). |
| 3 | **Localized semconv vocabulary, not OTel messaging semconv verbatim** | OTel messaging family is still `[Development]` (opt-in stability flag required by spec; reserved-name conventions target Kafka/RabbitMQ/MQTT and don't fit store-carry-forward mesh). We borrow attribute *concepts* (`messaging.message.id`, operation types, destination) but emit `iris.*` namespaced fields; migration to stable semconv later is a rename at the subscriber, not a re-instrumentation — because the *field values and labels* are already OTel-shaped. |
| 4 | **Unit suffix in metric names (`_total`, `_ms`, `_bytes`, `_ratio`)** | OTel keeps units as metadata (UCUM) and appends only at Prometheus export; on-device, self-describing names require no schema/metadata to decode (repo precedent: `SimMetrics`). Prometheus translation remains trivial. |
| 5 | **No W3C trace-context propagation on the wire** | DTN messages arrive seconds-to-days later over a message-id-based protocol (RFC 9171 correlates by bundle identity, not trace headers). `message_id` IS the trace correlation key — spans are tree-graphs within a node keyed by message_id, joined across nodes by the message_id in msg.* events. OTel context propagation would add block overhead to a ≤255-byte envelope (DISC-0008: 84 B payload ceiling) for no DTN-native benefit. |
| 6 | **Coarse lifecycle spans, no auto-instrumented async span per fn** | Battery/CPU discipline + tracing docs warning against `Span::enter` across awaits; `#[instrument]` on the message lifecycle functions, manual span for batch flush. |
| 7 | **Metrics Registry injected, no global `metrics` crate** | Repo rule: "metrics counters/gauges without global state" (ACTIVE_NODE.md). `EngineMetrics`-style structs satisfy test determinism and the existing no-global-state convention; a global `metrics` crate registry would fight the sim/test architecture. |
